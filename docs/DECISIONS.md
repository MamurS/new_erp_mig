# Решения, принятые по ходу сборки

Одна строка — одно решение. Формат: что решено — почему.

## Стек и зависимости

- Версии: React 19.2, Vite 7.3, TypeScript 5.9, Tailwind 3.4 (позже обновлён до 4, см. «Навигация и рабочий стол по ролям»), zod 3, msw 2, ESLint 9, Vitest 3 — выбраны стабильные мажорные ветки, совместимые с shadcn/ui, вместо самых новых (Vite 8, TS 7, Tailwind 4, zod 4, msw 3).
- React, react-dom, react-router-dom, msw, vite зафиксированы без `^` (SPEC §9.6); остальные — с `^`, версии держит `package-lock.json`.
- Добавлены `clsx`, `tailwind-merge`, `class-variance-authority` — стандартные утилиты shadcn/ui, без них компоненты shadcn не собираются.
- Добавлены `@radix-ui/react-{dialog,dropdown-menu,tooltip,tabs,popover,checkbox,slot}` — это Radix-примитивы, на которых стоят компоненты shadcn/ui.
- shadcn/ui подключён как исходники в `src/shared/ui/` (так работает shadcn), без CLI — CLI требует интерактива и сети.
- Тосты сделаны своим маленьким стором с `aria-live`, а не через `sonner` — чтобы не добавлять лишнюю зависимость.
- Селекты — нативные `<select>` в стиле shadcn: доступнее на мобильных и без лишней зависимости `@radix-ui/react-select`.
- `npm audit` показывает 4 уязвимости уровня moderate (react-router 6, vitest 3); уровня high нет, `--audit-level=high` проходит. Открытый редирект react-router закрыт собственной проверкой `safeNext()`.
- Node в контейнере — 22, CI использует Node 20 (`engines: >=20`); jsdom закреплён на ^29, потому что jsdom 30 требует Node 22+.

- Dependabot: все minor и patch обновления npm приходят одним еженедельным PR (группа `npm-minor-and-patch`); обновления GitHub Actions — отдельным еженедельным групповым PR (группа `github-actions`); мажорные версии пока игнорируются и в npm, и в Actions — они требуют миграции кода и планируются вручную (пример: ESLint 10 ломал `npm ci`, `eslint-plugin-react` ещё не поддерживает его).

## Окружение и сборка

- `VITE_USE_MOCKS` по умолчанию `true` (бэкенда пока нет); явное `false` отключает мок. `VITE_DEMO_MODE` по умолчанию `true` только в `npm run dev`, в сборке он включается только явно.
- `.env.*` в `.gitignore`, поэтому значения для `dev` заданы в `vite.config.ts`, а не в `.env.development`.
- `vite preview` применяет заголовки из `public/_headers` плагином; HSTS и `upgrade-insecure-requests` в preview отключены, иначе http://localhost не работает.
- E2E собирают отдельную сборку в `dist-e2e` с `VITE_DEMO_MODE=true VITE_SEED_XSS=true` и поднимают её через `vite preview` на порту 4174.
- Playwright: в контейнере используется предустановленный Chromium (`/opt/pw-browsers/chromium`), в CI — `playwright install`.

- К репозиторию подключены Cloudflare Workers Builds (а не Pages): добавлен `wrangler.jsonc` — статика из `dist`, SPA-фолбэк, сборка `npm run build`; `_headers` применяются так же. `public/_redirects` из SPEC §9.3 удалён: Workers отклоняют правило `/* /index.html 200` (ошибка 100324, «Infinite loop»), а SPA-фолбэк делает `not_found_handling: single-page-application`.

## Мок-сервер

- Состояние мок-сервера (БД и сессии) сохраняется в `sessionStorage` вкладки (`src/mocks/persist.ts`, отдельное исключение в ESLint), чтобы перезагрузка не выкидывала пользователя и не теряла изменения. Это эмуляция серверной БД, а не клиентская сессия; байты загруженных файлов не сохраняются.
- Каждая вкладка — отдельный «сервер» (MSW работает в странице); синхронизация выхода между вкладками идёт через `BroadcastChannel('mig-auth')`.
- Мок проверяет тайм-аут неактивности сессии сам (как бэкенд): 15/30 минут + 1 минута запаса.
- Для неизвестного телефона мок всё равно выдаёт `challengeId`, который никогда не подтвердится, — ответ не раскрывает, есть ли такой номер.
- Коэффициенты программ относительно «Стандарт+»: Базовая ×0,4, Стандарт ×0,7, Премиум ×2.
- Убыточность клиента хранится в seed как показатель (0,25–1,3), а не считается из 600 убытков — иначе при реальной премии все клиенты были бы ниже 15%.
- Медкарта не хранится в БД, а детерминированно генерируется из id застрахованного (МКБ-10 вымышленные сочетания).
- Изображения чеков из seed рисуются на canvas при запросе `/api/files/:id` и отдаются как PNG.
- Дополнительные эндпоинты, которых не было в SPEC §6.2: `POST /api/auth/resend`, `GET /api/dashboard/medical-access`, `GET /api/clients/:id/history`, `POST /api/clients/:id/hr-letter`, `GET /api/insured/:id/{claims,documents,access-log}`, `POST /api/insured/:id/reveal-copied` (аудит копирования), `POST /api/insured/:id/guarantee-letters`, `POST /api/claims` и `POST /api/appointments` (оператор), `GET /api/hr/employees/:id`, `POST /api/__demo/{reset,failures}` (только в демо).
- Импорт HR идёт в два шага: `POST /api/hr/employees/import` без `commit` только проверяет файл, с `?commit=1` добавляет корректные строки.
- Экспорты дополнены типами `loss_ratio`, `claims_by_category`, `premium_by_month` — для CSV по каждому графику отчётов.
- Правило «чужое не существует» реализовано через `requireOwn()`/`notFound()`: чужой ресурс — 404, отсутствие права на действие — 403.
- Реквизиты демо-аккаунтов лежат в `src/mocks/credentials.ts`; сборка без демо-режима и без моков их не содержит (проверяется тестом).

## Данные и контракт

- DTO экранов вынесены в `src/shared/types/dto.ts`; `index.ts` скопирован из SPEC §5 без изменений.
- Бизнес-правила (переходы убытков, медэкспертиза, «четыре глаза») лежат в `src/shared/domain/` и используются и UI, и моком; сервер отдаёт в `ClaimDetail` готовые `allowedTransitions` и `blockedTransitions` с причинами.
- Ответы API валидируются zod-схемами из `src/shared/api/schemas.ts`; формы и мок используют одни схемы из `src/shared/schemas/forms.ts`.
- `hrEmployeeSchema.birthDate` проверяется через `.pipe()`, чтобы некорректная дата давала ошибку поля, а не исключение.
- Даты в формах вводятся как `ДД.ММ.ГГГГ` и нормализуются схемой в ISO.

## Безопасность

- В URL попадают только статусы, id и числа (`useUrlFilters` отбрасывает остальное); строка поиска `q` живёт в состоянии компонента.
- `document.title` всегда без ПДн: «Карточка застрахованного · MIG».
- Изображения вложений загружаются `fetch` с Bearer и показываются через `blob:` URL — `<img src>` не умеет передавать токен.
- Значение `reveal` живёт только в состоянии компонента 30 секунд; `grantId` медкарты — только в состоянии компонента 15 минут, запрос медкарты с `gcTime: 0`.
- QR-токен запрашивается с `gcTime: 0` и обновляется каждые 60 секунд.
- Тест «нет демо-кода в сборке» собирает с `VITE_DEMO_MODE=false` и `VITE_USE_MOCKS=false`; `000000` ищется как отдельный токен, потому что hex-цвета вроде `#000000ff` есть в коде библиотек (qrcode).
- `javascript:`-строки в тестах и XSS-данных seed разрешены точечно (`no-script-url` выключено только для тестов, в seed — `eslint-disable-next-line` с пояснением).
- В `.gitleaks.toml` в allowlist добавлен вымышленный демо-пароль `Demo-2026!` из SPEC §2.

## UX

- Верхняя панель портала сотрудников получает хлебные крошки и главное действие от страницы через `useTopbar()`.
- Строка очереди после «Подтвердить» остаётся на месте со статусом «Подтверждена», а не исчезает; очередь показывает первые 15 задач и кнопку «Показать все».
- Приветствие на рабочем столе зависит от времени в Ташкенте: «Доброе утро / Добрый день / Добрый вечер».
- Боковая панель клиента открывается параметром `?panel=<id>` (id — допустимое значение URL), поэтому «Назад» возвращает к той же панели и фильтрам.
- Предупреждение о неактивности в HR и приложении показывается за 2 минуты до выхода (для сотрудников — на 13-й минуте, по SPEC).
- Пока открыто предупреждение о неактивности, клики вне модалки не продлевают сессию — только кнопка «Продолжить работу».
- OTP-поля не ограничены `maxLength=1`: браузерный автоввод `one-time-code` вставляет весь код в первое поле, он распределяется по ячейкам.
- «Записать к врачу» из карточки застрахованного создаёт сразу подтверждённую запись (её делает оператор).
- Роль admin видит «Клиентов» и «Клиники», но вкладка «Полисы» в карточке клиента скрыта (нет `policies.read`).
- Бухгалтер видит ФИО застрахованных, но не может открыть карточку застрахованного (маршрут закрыт по SPEC §3).
- Глобальный баннер «Нет соединения» скрыт на `/app`: там показывается свой переведённый баннер.

## HR-кабинет

- PDF-заглушки счетов и документов генерируются на клиенте латиницей (кириллица транслитерируется), чтобы не встраивать шрифт; в них нет данных сотрудников.
- Имена файлов: `invoice-YYYY-MM-DD.pdf`, `document-YYYY-MM-DD.pdf`, шаблон — `employees-template.csv`.
- В предпросмотре импорта ПИНФЛ и телефон показываются только последними 4 цифрами.
- Пример телефона в шаблоне CSV без `+`, чтобы защита от CSV-инъекций не добавляла `'`.
- «Отмена» и «Назад» возвращают на предыдущий экран, если он есть, иначе на `/hr`.
- «Напомнить всем» неактивна, если все уже в приложении; дата исключения вводится как ДД.ММ.ГГГГ, по умолчанию сегодня.
- Разрезы статистики показаны полосками, без графиков recharts — агрегатов мало, полоски читаются проще.

## Приложение застрахованного

- Пока открыт `/app`, `data-theme="client"` ставится и на `<html>`, чтобы модалки в портале Radix получали клиентские цвета.
- «Записаться сюда» передаёт клинику и специальность через `state` роутера; мастер также принимает `?clinicId=<uuid>&specialty=<enum>` с проверкой значений.
- Мастер записи показывает до 6 клиник рядом и до 8 слотов у каждой; день по умолчанию — сегодня.
- В предупреждениях о лимите категории стоят в винительном падеже («На стоматологию осталось…»).
- Повторная отправка SMS-кода — повторный вызов `/api/auth/phone` с номером из `state` роутера; номер в URL не попадает.
- Распознавание чека запускается только по первому перекодированному фото и заполняет только пустые поля.
- Ошибки zod в форме возмещения показываются переведёнными сообщениями.
- «Выйти на всех устройствах» в прототипе вызывает тот же `logout()`.
- Серверные тексты (ошибки API, причина отказа, сообщение о завершении сессии) и модалка неактивности остаются на русском и в UZ-режиме — их переведёт бэкенд.

## Тесты

- E2E-проверка API идёт через `fetch` внутри страницы: мок работает в service worker страницы, а `page.request` его обходит и попал бы на статический сервер.
- Проверка «загруженный файл без EXIF» скачивает сохранённое вложение через API под ролью оператора (переключение «Войти как…» в той же вкладке) и ищет в нём маркер `Exif` и GPS-строку.
- Проверка журнала аудита после reveal в E2E делается через «Войти как… Администратор» в той же вкладке: у другой вкладки была бы своя БД мока.
- CSP-тест ловит сообщения CSP в консоли и события `securitypolicyviolation`; редкий отказ MSW при фоновом обновлении воркера во время навигации к CSP не относится и не считается.

## Коммерческое предложение (docs/KP_SPEC.md)

- **Исключение для `KpFrame`:** HTML-строка КП выводится только в `src/features/kp/KpFrame.tsx` через `<iframe sandbox="allow-same-origin allow-modals" srcDoc>` без `allow-scripts`; ESLint запрещает `srcDoc`/`srcdoc` во всём остальном коде, `dangerouslySetInnerHTML` и прочие HTML-синки запрещены по-прежнему, в том числе в `KpFrame`.
- Исходный генератор лежит в `vendor/gold-brochure-generator/` без изменений (ESLint и Prettier его не трогают); `KP_SPEC.md` перенесён из корня в `docs/`.
- `src/features/kp/templates/gold.ts` генерирует `scripts/import-gold-templates.mjs`: `templates.js` разбирается как JSON, а не выполняется; скрипт проверяет 6 наборов × 16 страниц и отсутствие `<script>`, `on*=` и `javascript:`.
- Целостность брошюры: тест сверяет SHA-256 `GOLD_TEMPLATES` с зафиксированным значением и сравнивает модуль с `vendor/…/templates.js` постранично.
- Версия шаблона продублирована в `KP_TEMPLATE_VERSION` (`src/shared/domain/kp.ts`), чтобы мок не тянул 0,9 МБ шаблонов в стартовый бандл; тест проверяет, что она совпадает с `GOLD_TEMPLATE_VERSION`.
- Шаблоны и рендер грузятся только на экране КП и по нажатию «Скачать PDF» (динамический импорт), а не с карточкой клиента или кабинетом HR.
- В `KpDocument` добавлены `clientLegalForm`, `clientInn`, `createdByEmail`: они нужны странице-письму, а HR не может читать карточку клиента и профиль сотрудника.
- `GET /api/clients/:id/kp-defaults` возвращает `{ params, letter }`, а не голые `KpParams`: письму в предпросмотре нужны реквизиты клиента и почта андеррайтера ещё до сохранения.
- Предзаполнение: премия на человека = премия полиса / число застрахованных по полису с округлением до 1000; страховая сумма = сумма лимитов программы клиента (без программы — 200 000 000, как в генераторе); условия оплаты — поквартально.
- Права: `kp.create` — создать и изменить черновик, `kp.send` — отправить и отозвать (только `underwriter`); `kp.read` — роли с `clients.read` и HR своей компании. HR получает только отправленные КП, черновик, отозванное и чужое КП — 404.
- Отправить можно только черновик с неистёкшим сроком действия, отозвать — черновик или отправленное; остальное — 409.
- Номер КП присваивается при сохранении: в предпросмотре нового КП в письме стоит «—», а «Скачать PDF» доступна только после сохранения, чтобы не было PDF без номера и без записи в аудите.
- Событие `kp_downloaded` пишется до открытия окна печати; если запись не удалась, печать не открывается.
- В документе iframe пути к картинкам и `fonts.css` абсолютные (`/kp/gold/…`): Chrome при первой загрузке `about:srcdoc` резолвит их от адреса страницы, не дожидаясь `<base>`. `<base href="/kp/gold/">` оставлен.
- Старая форма «Подготовить КП на продление», эндпоинт `POST /api/policies/:id/renewal-offer` и таблица `renewalOffers` удалены; «КП готово / Нет КП» в очереди считается по черновикам и отправленным КП клиента.
- «Подготовить КП» доступна и клиенту без действующего полиса (КП для новых клиентов); тогда период — с завтрашнего дня.
- КП показываются во вкладке «Документы» одним списком с обычными документами; у обычных документов колонки КП пустые («—»). Вкладка и подсветка строки передаются в URL: `?tab=documents&highlight=<id>`.
- События аудита по КП видны в «Истории» клиента; в «Активности» — создание и отправка.
- HR открывает КП на `/hr/kp/:kpId` (только просмотр и «Скачать PDF»); в «Документах полиса» КП не дублируются.
- Seed: псевдодокумент «Коммерческое предложение (черновик)» у клиентов в переговорах убран (вызов генератора оставлен, чтобы остальной seed не сдвинулся); добавлен HR `hr@renewal.example.uz` компании с ближайшим продлением (фиксированный id) — для e2e «HR этой компании видит КП».
- Мок сохраняет БД в `sessionStorage` также на `pagehide`, чтобы перезагрузка сразу после изменения его не теряла.
- `templateVersion` фиксируется в документе, но шаблоны в прототипе хранятся только в текущей версии; воспроизведение старой версии после обновления брошюры — задача бэкенда (хранить шаблоны по версиям или готовый PDF).
- Порядок страниц КП: обложка брошюры, страница-письмо, страницы брошюры 2–16. Он задаётся одной функцией в `renderKp` (`src/features/kp/render.ts`); предпросмотр, счётчик, печать и открытие сохранённых КП берут его оттуда.
- Уже сохранённые КП хранят только параметры и версию шаблона, поэтому после смены порядка сами открываются и печатаются в новом порядке; миграция данных не нужна.
- Письмо оформлено как внутренняя страница брошюры (шапка и правовая строка — как на странице 2 шаблона, в чёрном издании графит заменён на чёрный) и не имеет печатного номера: номера брошюры не пересчитываются, чтобы её ссылки вида «на стр. 6» оставались верными. Счётчик «Страница N из 17» в предпросмотре считает листы документа и может не совпадать с печатными номерами брошюры.
- Плашка «Подробные условия программы GOLD — на следующих страницах» на письме стала персиковой (`#FDE7D3`), как информационные плашки на внутренних страницах брошюры, вместо оранжевой.

## Клиники (docs/CLINIC_SPEC.md)

- Новая зависимость `jsqr` (runtime): чтение QR с камеры в «Проверке пациента». `BarcodeDetector` есть не во всех браузерах (нет в Safari и Firefox), а своя реализация распознавания — лишний риск. Кадры обрабатываются в браузере, на сервер не уходят.
- Новая dev-зависимость `@asteasolutions/zod-to-openapi`: OpenAPI строится из тех же zod-схем, что проверяют запросы и ответы API в моке, поэтому контракт не расходится с кодом. В приложение библиотека не попадает — только в `scripts/build-openapi.mjs` и тест свежести.
- YAML пишется своим маленьким детерминированным эмиттером (`src/shared/integration/openapi-files.ts`), без зависимости `yaml`. TS-исходники скрипт загружает через `ssrLoadModule` Vite, чтобы работали алиасы `@/…`.
- Тест `src/shared/integration/openapi.test.ts` падает, если `docs/integration/openapi.yaml` или `public/docs/integration/openapi.json` устарели; обновление — `npm run build:openapi`.
- Вкладка «Документация» читает `public/docs/integration/openapi.json` и рисует его как текст (без HTML из документа); примеры проверки подписи — Python, C#, PHP.
- Клиентские пользователи входят на тот же `/login` с MFA; `homeFor` отправляет их в `/clinic`. Тайм-аут бездействия 15 минут (предупреждение на 13-й).
- Короткий код под QR — 8 символов из 32-символьного алфавита без похожих знаков (`0/O`, `1/I`), показывается как `XXXX-XXXX`. Живёт вместе с QR-токеном (60 секунд) и одноразовый: код и токен — две записи одной строки `cardTokens`.
- Лимит 30 проверок в час и блокировка после 10 неудач подряд считаются только для проверок по полису и ПИНФЛ; проверка по одноразовому коду в лимит не входит (её нельзя перебрать: код живёт 60 секунд). Повтор использованного кода — 410 и запись в аудит.
- Визит открывается любой успешной проверкой и живёт 24 часа; все данные пациента в кабинете и в API — только через `visitId` своей клиники, иначе 404.
- Секреты ключей API хранятся в моке как SHA-256 и показываются один раз. Секрет подписи вебхука мок хранит открытым, потому что им надо подписывать; бэкенд должен хранить его зашифрованным (KMS), в ответах — только последние 4 символа.
- Песочница и симулятор МИС секретов не сохраняют: в песочницу `client_secret` вставляют вручную, симулятор создаёт себе ключ «Демо-МИС» и держит его только в памяти вкладки.
- Симулятор МИС получает код карты демо-застрахованного через демо-эндпоинт `POST /api/__demo/mis-card` (только `clinic_admin` и только в демо-сборке): у МИС нет телефона пациента.
- Список разрешённых IP ключа мок проверяет по заголовку `X-Test-Client-IP` (в браузере настоящего IP нет); бэкенд берёт адрес соединения за доверенным прокси.
- Доставка вебхука в моке имитируется: адрес, содержащий `fail`, отвечает 500, остальные — 200. Расписание повторов (1, 5, 30 минут, 2 и 12 часов) записывается в `nextAttemptAt`, но в моке повтор выполняется только кнопкой «Повторить»; автоматические повторы — задача бэкенда (очередь).
- Лимит API 60 запросов в минуту и ключи идемпотентности (24 часа) хранятся в памяти мока; ответы API проверяются zod-схемами контракта прямо в моке (при расхождении — 500 и ошибка в тесте).
- В журнале API только метод, шаблон пути (`/visits/{visitId}`), код ответа, задержка и `X-Request-Id` — без тел запросов, параметров и токенов.
- `POST /registries` в API сразу создаёт и отправляет реестр (источник `api`); черновики есть только в кабинете (сборка из визитов, ручные строки, CSV).
- Заявки, по которым клиника не ответила за `responseSlaMinutes` (по умолчанию 120), попадают в очередь как «Клиника не ответила»; вкладка «Записи» рабочего стола показывает их вместе с обычными.
- Оператор МИГ по-прежнему может подтвердить или отклонить заявку за клинику (запасной путь); тогда в записи `respondedBy: 'operator'`, и приложение пишет «Подтвердил оператор МИГ».
- Правило четырёх глаз: сумма одобрения выше `GUARANTEE_DUAL_APPROVAL_THRESHOLD` (20 000 000 UZS) требует второго одобрения другим врачом-экспертом; повтор тем же врачом — 409. Очередь ГП видят `operator` (только чтение) и `doctor_expert`.
- PDF гарантийного письма в прототипе собирается в браузере тем же генератором, что и документы HR (`src/features/hr/pdf.ts`); настоящий PDF с подписью формирует бэкенд. Вложения ГП только скачиваются, в страницу не встраиваются.
- Карточка клиники для сотрудников: номер договора в моке выводится из id клиники; вкладки ГП и реестров показываются только ролям с этими правами.
- Seed клиник использует отдельный поток ГСЧ (`mulberry32(SEED ^ 0x0c11e1c5)`), чтобы не сдвинуть остальной seed. Снимок мока в `sessionStorage` без новых таблиц отбрасывается и пересоздаётся.
- В seed добавлено одно ГП клиники в режиме `api` (не демо-клиники): e2e проверяет, что чужое ГП отдаёт 404.
- Прайс-лист новых клиник, созданных администратором МИГ, копируется из прайса первой клиники — в прототипе нет экрана редактирования прайса.
- `ClinicAdapter` (`src/shared/integration/adapter.ts`) — только интерфейс для исходящей интеграции МИГ → МИС; реализации (HTTP к API клиники, iCal, ручной режим) пишет бэкенд.

## Полисы и состав (docs/POLICY_SPEC.md)

- Право на оформление полиса — существующее `policies.write` (только андеррайтер); новые действия `policy_changes.read` (оператор, андеррайтер, бухгалтер, HR своей компании), `policy_changes.request` (HR своей компании), `policy_changes.decide` (только андеррайтер: решение меняет премию).
- Кнопка «Оформить полис» есть у клиента без действующего полиса и у клиента в статусе «истёк»; продление действующего полиса — отдельный процесс, не в этом ТЗ (мок отвечает 409).
- Полис с датой начала позже чем через 30 дней оформляется в статусе `draft`, иначе `active`.
- Члены семьи, как и раньше в модели, — число у сотрудника (`familyMembersCount`), а не отдельные застрахованные; в CSV это колонка `familyMembers` (0–10).
- Тарифы программ и лимиты вынесены в `src/shared/domain/programs.ts` и `policies.ts`, чтобы их видел и мастер оформления, и мок; у полисов seed тарифа нет — берётся премия / число застрахованных.
- Пропорциональный пересчёт считает дни включительно с обеих сторон, округление до 1 000 UZS; доплата или возврат фиксируется в заявке на момент её создания.
- Заявка HR на прикрепление до решения не создаёт застрахованного: в списке HR она видна отдельной строкой со статусом `pending`, отклонённые показываются 30 дней. Отказ по исключению показывается у сотрудника 30 дней.
- Повторная заявка на того же человека, пока первая ждёт решения, — 409; дата прикрепления или исключения вне срока полиса — 422.
- Допсоглашение создаётся одно на полис на каждый пакет решений и попадает в документы клиента (видны сотрудникам и HR); PDF допсоглашения в прототипе не формируется.
- HR, приглашённый при оформлении, получает демо-пароль и код MFA, как остальные демо-пользователи; если у компании уже есть HR, новый не создаётся.
- Существующие HR-тесты обновлены под новое поведение (тексты «Заявка отправлена в МИГ», «Отправлено заявок»), логика проверок в них не ослаблена.
- Seed заявок — отдельный поток ГСЧ (`mulberry32(SEED ^ 0x9011c7)`), чтобы не сдвинуть остальные данные; снимок мока без таблицы `policyChanges` отбрасывается.

## Ассистанс (docs/ASSISTANCE_SPEC.md)

- Каркас интеграции обобщён до партнёра: у `IntegrationClient` и `WebhookEndpoint` появилось поле `partnerType` (`clinic` по умолчанию), а колонка `clinicId` хранит id партнёра — клиники или ассистанса. Так бэкенду не нужна вторая таблица ключей; переименование в `partnerId` — при переходе на API.
- Ключ партнёра работает только с методами своего типа: клиничные методы закрыты для ключей ассистанса и наоборот (403 `wrong_partner`), области доступа при создании ключа тоже проверяются по типу.
- Экраны «Интеграция» клиники переиспользуются в портале ассистанса через контекст партнёра (`PartnerProvider`): базовый путь, области доступа, события, методы песочницы и разделы документации берутся из него.
- Смена ассистанса — только с сегодняшнего дня или позже (для черновика полиса — с его начала): задним числом менять плательщика по уже оказанным услугам нельзя.
- Доступ к карточке застрахованного: текущий ассистанс — полный, прежний — только чтение 12 месяцев после окончания закрепления; поиск ищет только среди закреплённых сегодня.
- В seed 34 клиента с полисами распределены пропорционально 15/12/8/5 из ТЗ: 13 / 10 / 6 и 5 без ассистанса. Клиент, сменивший ассистанс, перешёл от второго к первому (так старый видит его дела только на чтение).
- Вознаграждение PEPM считается по застрахованным ассистанса в периоде счёта; «за обращение» — по обращениям, созданным в периоде; «процент от выплат» — от суммы строк счёта.
- Счёт на возмещение формируется из строк, **оплаченных клиникам** в периоде (по дате оплаты). Счёт, отправленный через API, сразу уходит в МИГ; в портале — сначала черновик.
- Статус счёта после проверки: есть строки на проверке или оспоренные — «На проверке», иначе «Принят» или «Принят частично». Оспаривание возвращает счёт на проверку. Кто закрыл проверку, тот «принял» счёт (правило четырёх глаз с оплатой).
- Строки принятого счёта становятся убытками МИГ с источником `assistance` и добавляются к убыточности клиента. К оплате — принятые строки плюс вознаграждение целиком.
- Лимит: `used` — убытки плюс строки, принятые ассистансом и ещё не ставшие убытками; `reserved` — одобренные неиспользованные ГП. Это производные значения, поэтому резерв и списание меняются одной операцией без отдельного счётчика.
- Реестр клиники делится на подреестры по плательщику строки (ассистанс полиса на дату услуги). Статус реестра у клиники — общий; у каждого плательщика — свой статус подреестра. Реестр «Оплачен», когда оплачены все принятые строки всех плательщиков.
- Прайс пары «клиника + ассистанс» хранится только для договоров с отдельными ценами; без него действует прайс МИГ.
- Заявки на запись клиентов с ассистансом не попадают в очередь куратора МИГ; ассистанс отвечает на них, только когда клиника не ответила в срок.
- Чат приложения: сообщения клиентов с ассистансом видят его операторы (`/assist/chat`); автоматический ответ дежурного оператора в демо оставлен для всех.
- Доступ к чатам в портале ассистанса — у `asst_operator` (как `assist.appointments.manage`): в матрице ТЗ отдельного действия для чата нет.
- Список и карточка ассистансов в портале МИГ видны всем ролям сотрудников; менять договор может только администратор, вкладка «Аудит» — у тех, у кого есть `audit.read`.
- KPI считаются на лету: среднее время ответа по записям застрахованных ассистанса, доля ГП, решённых за 24 часа, доля «согласен» в контрольной выборке, жалобы за 30 дней на 1000 застрахованных, убыточность портфеля.
- Контрольная выборка 5% формируется при открытии очереди врача-эксперта за текущий месяц (детерминированный хеш), повторно одно и то же решение в выборку не попадает. Несогласие отправляет ассистансу вебхук `qa.disagreement`.
- Симулятор системы ассистанса показывается у ассистанса в режиме `api` или `hybrid`: демо-аккаунты принадлежат гибридному «[Ассистанс 1]», поэтому симулятор доступен им.
- Для e2e-сценария двух плательщиков демо-эндпоинт `/__demo/mis-card?who=mig` выдаёт код карты клиента без ассистанса (только в демо-режиме).
- Оператор второго ассистанса есть в seed для проверки изоляции, но не добавлен в «Войти как…» (меню выбирает аккаунт по роли).
- Seed ассистансов — отдельный поток ГСЧ (`mulberry32(SEED ^ 0xa55157)`); снимок мока без таблицы `rebills` отбрасывается.
- Существующие клиничные e2e-сценарии 1, 3, 6 и 10 обновлены под §9: демо-пациент обслуживается ассистансом, поэтому ГП решает его врач (или эскалирует в МИГ), а реестр проверяет и оплачивает ассистанс. Проверки в сценариях не ослаблены.

- ГП по звонку: оператор ассистанса запрашивает письмо из карточки застрахованного или обращения; направление открывает визит в выбранной клинике на 24 часа (клиника видит пациента и письмо, как после своей проверки). Запросить можно только услугу, для которой прайс требует ГП.
- `updatedSince` в `GET /roster` учитывает последнее изменение человека (прикрепление или исключение): у застрахованного появилось серверное поле `updatedAt`.
- SLA в очередях ассистанса: у записи — срок ответа клиники (после него заявка эскалируется ассистансу), у подреестра — 5 дней на проверку с даты отправки реестра.
- Куратор МИГ видит все обращения ассистанса во вкладке «Обращения» карточки и может закрыть только жалобу (решение с пометкой «Куратор МИГ», действие `complaint_resolved` в аудите); остальные обращения ведёт ассистанс.
- Обращение, из которого запрошено ГП, получает ссылку на убыток, когда строка реестра по этому письму становится убытком в принятом счёте ассистанса.
- Администратор МИГ добавляет ассистанс в разделе «Ассистансы» (компания, договор и первый `asst_admin`, как у клиник); остальных пользователей приглашает администратор ассистанса.
- Демо-эндпоинты `/api/__demo/*` подключаются динамическим импортом только при `VITE_DEMO_MODE=true` (раньше статический импорт оставлял их код в сборке с моками без демо-режима). Тест сборки без флага проверяет и вариант с моками.

## Параметры ДМС
- Бизнес-параметры собраны в `src/shared/config/dmsParameters.ts`: значение, единица, описание, допустимый диапазон, группа. Текущие значения хранит сервер (мок: `db.dmsParams`, хранятся только изменённые), код мока читает их через `dmsParam()`, экраны — через `useDmsParam()` или получают готовые значения из API.
- Проценты хранятся долей (0,05 = 5%), в редакторе вводятся в процентах.
- Экран `/staff/admin/parameters` «Параметры ДМС» видят все роли МИГ; предлагает изменение только `admin`, применяет второй человек с ролью `admin` или `underwriter` (правило четырёх глаз: автор не подтверждает своё). Отклонить может любой из них, автор может отозвать своё предложение.
- В аудите три действия: `dms_param_proposed`, `dms_param_changed` (кто подтвердил; объект «Параметр: было → стало»; в причине — кто предложил и основание), `dms_param_rejected`. Время — время записи.
- Пометка «демо-значение» стоит у параметра, пока его ни разу не меняли через подтверждённое изменение.
- Устаревшее предложение (значение успело измениться) не применяется: 409, нужно создать новое. По одному параметру одновременно может быть только одно предложение.
- Полномочия ассистанса по ГП: индивидуальное значение в договоре необязательно; если его нет — действует параметр. В seed индивидуальное значение есть только у второго ассистанса (12 000 000), остальные работают по параметру. Так же срок ответа клиники: индивидуальный норматив у клиники необязателен, по умолчанию — параметр.
- «Лимит на исходе» — одно правило для приложения, клиники, HR и МИГ: остаток не больше доли `limitLowShare` (раньше были два порога: 80% использовано и меньше 20% остатка).
- В параметры вошли также срок действия ГП по умолчанию и порог высокой убыточности (80%): они тоже зашиты в нескольких местах. Не вошли технические значения (TTL токенов и кодов, лимиты API-ключей, размеры файлов, расписание повторов вебхуков) и нормативы ассистанса из договора (SLA обращений по типам, 12 месяцев доступа прежнего ассистанса) — их меняют отдельной задачей при необходимости.
- Порталы клиник, ассистансов, HR и приложение получают через `GET /api/params/values` только параметры с `audience: 'all'` (пороги лимита и убыточности, срок ответа клиники, срок действия ГП, лимиты проверок по ПИНФЛ); полномочия, пороги подписей и сроки проверки счетов видят только сотрудники МИГ.
- Тест `tests/no-hardcoded-params.test.ts` ищет в `src/` (кроме тестов и реестра) старые константы и значения: 10 000 000 / 20 000 000, 0,05, пороги 0,8/0,2/80 рядом с лимитом или убыточностью, `?? 120`, 30-дневные сроки по умолчанию, тексты про блокировку «на N минут».

## Жизненный цикл
- Новые роли `sales_manager`, `legal`, `claims_officer`; демо-аккаунты по ТЗ плюс «Руководитель андеррайтинга» (скидка до 25%, подписант по доверенности) и «Руководитель урегулирования убытков» (решения до 50 000 000) — чтобы показать согласование выше полномочий. «Войти как…» перечисляет аккаунты, а не роли.
- `staff.authority.manage`: по таблице §14 — только `admin`; второй человек — другой администратор (демо `admin2@demo.mig.uz`), автор и сотрудник, чьи полномочия меняются, не подтверждают.
- Для экранов добавлены права чтения `contracts.read` (менеджер, андеррайтер, юрист, куратор, бухгалтер, HR своей компании) и `invoices.read` (менеджер, андеррайтер, бухгалтер, HR своей компании) — в таблице §14 их нет.
- HR нового клиента создаётся при отправке КП по сделке (email контакта из лида, демо-пароль), чтобы клиент мог принять КП в кабинете.
- Начало страхования по умолчанию — первое число месяца через месяц (`defaultStartDate`), если в сделке не указана желаемая дата.
- Договор создаётся из принятого КП: параметры и премии — из утверждённой котировки, `activationRule` по умолчанию `after_first_payment`, оплата единовременно (меняется в редакторе). Изменять можно только черновик; у отправленного — «Новая версия» сбрасывает подписи.
- Согласование юриста: «Отправить на согласование» переводит договор к юристу, если изменён хотя бы один пункт, иначе сразу в «Согласован». Если премии отличаются от котировки, сначала их утверждает андеррайтер.
- ЭДО: отправка через оператора записывает подпись МИГ способом «ЭДО»; подпись клиента приходит событием через 3 секунды (ленивая проверка часов мока при запросе, экран опрашивает каждые 1,5 с).
- Бумага и скан включают `paperOriginal.required`; скан загружает сотрудник МИГ (за любую сторону) или HR (за клиента), засчитывает его `contracts.verify_scan`.
- Счета формируются после подписания обеих сторон по графику платежей; договор вступает в силу ленивой проверкой при запросе (дата начала наступила и, для `after_first_payment`, первый взнос оплачен полностью). Выписка 1С сопоставляется по правилам раздела «Платежи и повтор чека».
- Изменения состава от HR по-прежнему подтверждает андеррайтер (POLICY_SPEC); для полиса по договору подтверждённое изменение становится заявкой на изменение и копится до доп. соглашения. Старые «доп. соглашения к полису» для таких полисов не создаются.
- При `from_endorsement_signed` новый сотрудник появляется в полисе после подписания ДС; при `from_hr_request` (по умолчанию) — сразу с даты заявки.
- Возмещения застрахованным: клиент без ассистанса — `claims_officer`; с ассистансом — по `handlesReimbursements` договора ассистанса (по умолчанию `true`). В seed у «[Ассистанс 1]» `false`, поэтому возмещения демо-застрахованного рассматривает МИГ.
- `rebills.review` перешло от куратора к `claims_officer` (§14); куратор сохранил SLA обращений и жалобы ассистансов.
- Решение по убытку: «полномочия» сравниваются с суммой, к которой обязывает решение (при отказе — заявленная сумма). Пункт для отказа и частичного одобрения выбирается из разделов 4 и 8 шаблона договора; в базе хранится ссылка `contract:4.3`.
- Резерв хранится историей изменений; резерв на дату — последнее значение истории до конца дня (Ташкент). Ручное изменение — только `claims_officer` с причиной.
- Флаги мошенничества пересчитываются при создании убытка; хэш изображения чека — SHA-256 перекодированного файла.
- Мок отдаёт HR договор и ДС без внутренних полей (список подписантов МИГ, котировка, история версий, комментарии юриста, платежи).
- Шаблоны-заглушки: `approved: false`, хэш-тест действует только для утверждённых (КП). `docs/TEMPLATES.md` генерируется из шаблонов (`UPDATE_TEMPLATES_MD=1 npx vitest run src/features/documents`).

## ИИ-проверка покрытия
- Пункты таблицы покрытия ссылаются на новый шаблон-заглушку «Программа страхования» (`program`, приложение 1 к договору) и на пункты договора; в каталог пунктов для решений по убыткам добавлены пункты программы («п. 6.2 программы …»).
- Демо-программа эталонных случаев — «Стандарт»; в ней вакцинация и профчистка зубов исключены, в «Стандарт+» и «Премиум» покрываются. Период ожидания: плановая стоматология — 30 дней в «Базовой» и «Стандарт», роды — 280 дней.
- Несколько кодов в одном запросе: итог — самый строгий вердикт (полис не действует > исключение > лимит исчерпан > нужна проверка > ГП > покрывается), пункты — всех кодов.
- Строки реестров и ГП несут код услуги из прайса: такие проверки идут без провайдера (уверенность 1), ИИ нужен только для свободного текста.
- Порог уверенности (по умолчанию 60%) — часть настроек ИИ, а не «Параметров ДМС»: его меняет администратор ИИ вместе со сценариями.
- Изменения настроек ИИ подтверждает второй администратор (`ai.admin` с правилом «кроме своих»). Исключение — «Отключить ИИ везде»: срабатывает сразу (безопасное направление) и пишется в аудит; обратное включение — только со вторым администратором.
- Мок-провайдер считается внешним: перед ним текст всегда обезличивается; без обезличивания работал бы только `local`.
- Распознавание чека в моке возвращает позиции (аптечный чек — лекарства, витамины и косметика; чек клиники — услуги), их сумма равна сумме чека. В мастере возмещения позиции «не вернём» убираются одной кнопкой, сумма заявки пересчитывается.
- Подсказка ИИ показывается в карточке убытка и ГП (МИГ и ассистанс); для строк реестров и счетов — массовая «Проверить строки» у клиники и «Предпроверка ИИ» у куратора счетов (`claims_officer`), отдельной подсказки на каждую строку нет.
- `ai.feedback` («все, кто видит подсказку в рабочих экранах») — `claims_officer`, `doctor_expert`, `operator`, `asst_doctor` и `asst_operator` (свои).
- В прайсы клиник добавлены две исключённые программой услуги («Чистка лица», «Коронка металлокерамическая»), чтобы «Проверить строки» было что подсветить; seed-реестры их не используют.
- Обезличивание: ФИО (известные имена застрахованного и шаблон «Фамилия Имя Отчество»), ПИНФЛ, телефоны, email, номера полисов, договоров и сертификатов заменяются метками `[ФИО-1]`, `[ПИНФЛ-1]`…; соответствие меток остаётся на сервере.

## Платежи и повтор чека
- Сопоставление выписки 1С: сначала номер счёта в назначении (без учёта регистра, пробелов вокруг дефисов и «№», не как часть более длинного номера), затем ИНН плательщика + точная сумма **остатка** среди неоплаченных счетов договоров. Автоматически — только если подходит ровно один счёт; оплата меньше остатка по номеру счёта засчитывается как частичная.
- В «Ручную разноску» попадают: счёт указан, но ИНН другой (оплата третьим лицом не разносится автоматически даже по номеру); сумма больше остатка указанного счёта; несколько номеров в назначении; несколько счетов с такой суммой; сумма не совпала ни с одним счётом; у плательщика нет неоплаченных счетов; ИНН не найден. Кандидаты пересчитываются при каждом открытии очереди, но сам платёж из очереди автоматически не разносится.
- Разноска одного платежа может идти на несколько счетов; сумма по счёту не больше его остатка, общая — не больше остатка платежа; неразнесённый остаток остаётся в очереди. Если ИНН плательщика не совпадает с ИНН клиента хотя бы одного счёта — комментарий обязателен (минимум 5 символов), он пишется в платёж и в аудит.
- Очередь и разноска — право `payments.record` (бухгалтер), отдельное действие в матрицу прав не добавлялось. Раздел «Ручная разноска» — отдельный пункт навигации бухгалтера. В выписке появился необязательный столбец `payer` (название плательщика).
- Защита от повторного импорта: обязательный столбец `doc_number` (номер платёжного документа); ключ строки — номер документа + дата + сумма + ИНН (`statementLineKey`). Ключи всех загруженных строк хранятся в `statementKeys`, повтор (из прошлой выписки или внутри одного файла) пропускается и считается в «пропущено как повтор»; строка без номера документа — ошибка строки. Строки seed-очереди тоже считаются загруженными.
- В seed две записи в очереди: оплата холдингом за демо-клиента по номеру счёта и платёж неизвестного плательщика без номера.
- Фискальные данные чека (фискальный признак, дата и время, сумма, ИНН точки продажи) мок «распознаёт» из SHA-256 изображения: то же фото даёт тот же чек у любого застрахованного. При подаче убытка сервер распознаёт первое фото заново; из формы клиента фискальные данные не принимаются. Примерно у каждого шестого фото фискальный признак «не читается».
- «Повтор чека»: сравниваются все убытки всех застрахованных, у которых есть чек (фискальные данные, хэш изображения или источник «приложение»); счета клиник по реестрам не сравниваются — у разных пациентов в один день цена приёма совпадает законно. Если фискальный признак есть у обоих чеков — решает только он (разные признаки — разные чеки); иначе сумма чека, дата и ИНН точки продажи (без фискальных данных — заявленная сумма, дата услуги и название). Совпадение хэша изображения — дополнительный признак: само ставит флаг и упоминается в сообщении рядом с фискальным совпадением. В сообщении — номер другого обращения и «другого застрахованного», без ПДн.
- ИНН точки продажи в моке — стабильное число из названия аптеки или клиники; в seed фискальные данные есть у всех убытков из приложения, одна пара демонстрирует повтор чека у двух разных застрахованных.

## Навигация и рабочий стол по ролям
- Сворачиваемая боковая панель — у порталов МИГ и ассистанса (у них было боковое меню). У клиники и HR навигация верхняя по SPEC §7.2, её не меняли.
- Ширина панели: 248 px развёрнута, 64 px свёрнута. Состояние хранится в `mig.ui.navCollapsed` как `{ staff, assist }`: ключ тот же, формат изменился, старое значение `true/false` читается как «по умолчанию» (развёрнуто).
- На узком экране панель — диалог Radix (Esc, клик по подложке, ловушка фокуса), открывается бургером в верхней панели. Пока она открыта, остальная страница скрыта от вспомогательных технологий.
- Блок пользователя переехал из шапки ассистанса и из аватара внизу рейла МИГ в нижнюю часть панели. В развёрнутом виде «Выйти» — отдельная кнопка, в свёрнутом — меню аватара «Профиль и выход».
- Счётчики в меню МИГ — количество задач очереди роли по разделам (`QUEUE_NAV` в `nav.ts`), у «Рабочего стола» — вся очередь. У ассистанса — счётчики его обзора (обращения, ГП, строки реестров, счета на проверке).
- Группы МИГ: «Работа» (рабочий стол, записи, изменения состава, изменения лимитов, контроль качества), «Продажи и андеррайтинг» (сделки, клиенты, договоры, доп. соглашения, полисы), «Урегулирование» (убытки, ГП, резервы), «Партнёры» (клиники, реестры клиник, ассистансы), «Финансы» (счета и оплаты, ручная разноска, счета ассистансов), «Отчёты», «Администрирование» (аудит, пользователи, параметры ДМС, ИИ). Реестры клиник отнесены к «Партнёрам». Группы ассистанса: «Работа», «Справочники», «Финансы», «Администрирование».
- Очередь рабочего стола собирается по роли, а потом каждый элемент проходит проверку прав по типу (`QUEUE_TYPE_META` в `src/shared/domain/queue.ts`: тип → права, любого из которых достаточно). Вкладки очереди — типы, которые пришли в ответе, с количеством; старые сгруппированные вкладки («Записи» вместе с «Клиника не ответила», «ГП» вместе с эскалациями) разделены.
- Ошибка «у андеррайтера в очереди Убыток»: экран показывал вкладки «Записи», «Убытки», «Продления» всем ролям без проверки прав. Теперь вкладки берутся из ответа сервера, а сервер отдаёт только разрешённые типы.
- У андеррайтера в очереди остались изменения состава полиса (`policy_changes.decide` — его работа по POLICY_SPEC), хотя в списке задачи их нет. У юриста третий тип — сканы подписей на проверке (`contracts.verify_scan`), чтобы в очереди было не меньше трёх видов работы.
- Продление в очереди андеррайтера — только без живого КП, окно — параметр `renewalLeadDays` (60 дней). Клиент с готовым КП из очереди уходит, а не меняет статус.
- Новые параметры ДМС: `leadIdleDays` (7 дней без событий по лиду) и `kpNoAnswerDays` (5 дней без ответа на КП), группа «КП».
- Очередь показывает только свои сделки менеджера (`ownerId`), запросы на лимиты и изменения параметров, полномочий и ИИ — только чужие (правило четырёх глаз).
- «Ошибки интеграций» у администратора — недоставленные вебхуки клиник, одна строка на клинику. Других журналов ошибок интеграций в моке нет.
- KPI каждой роли считаются из её же очереди (плюс денежные суммы бухгалтера и воронка менеджера), чтобы цифры совпадали с тем, что человек видит ниже.
- При переключении вкладки очередь не показывает строки предыдущей вкладки, пока грузится новая (раньше `keepPreviousData` позволял нажать «Подтвердить» в строке другой вкладки).
- Seed дополнен, чтобы у каждой роли было не меньше трёх типов работы: лид без активности 12 дней, черновик котировки андеррайтера по второму лиду (клиент остаётся лидом), ДС-3 у юриста с изменением «прочее» (заодно утверждение сумм андеррайтером), предложения второго администратора: параметр «лимит на исходе» 20% → 25% и полномочия андеррайтера.
- Tailwind CSS обновлён с 3.4 до 4. Причина: `npm audit --audit-level=high` начал падать на `braces` ≤ 3.0.3 (GHSA-vfj7-8cjw-p6xm, DoS на вложенных шаблонах). Исправленной версии `braces` нет, а приходит он только через Tailwind 3 (`chokidar`, `micromatch`, `fast-glob`). Tailwind 4 этих пакетов не тянет. Затронуто только сборочное окружение, в браузер `braces` не попадал.
- Миграция сделана официальным `@tailwindcss/upgrade`: конфиг перенесён из `tailwind.config.ts` в `@theme` в `src/styles/index.css`, PostCSS-плагин заменён на `@tailwindcss/postcss` (новая зависимость сборки), классы переименованы по v4 (`shadow-sm`→`shadow-xs`, `rounded`→`rounded-sm`, `outline-none`→`outline-hidden`, `z-[45]`→`z-45` и т. п.).
- Правки инструмента в строках, которые не являются классами (CSS шаблонов документов и КП, узбекский перевод, названия тестов), откатаны: утверждённый шаблон КП не изменился.
- Токены радиусов и шрифта заголовков подключены через `@theme inline reference`: у них те же имена, что в `tokens.css`, и обычный `@theme` дал бы на `:root` самоссылку `--radius-btn: var(--radius-btn)`, которая ломала бы скругления и шрифт в порталах (модалки, меню, подсказки).
- Сохранено поведение v3: цвет рамки по умолчанию gray-200 (совместимый блок от инструмента) и курсор-указатель у кнопок.

## Боковая панель в стиле Claude и «Войти как…»
- Одна панель (`AppSidebar` + `SidebarProvider` + `SidebarToggle`) во всех четырёх порталах. У клиники и HR верхняя навигация заменена панелью, их шапка контента — кнопка панели и название клиники или компании. Меню пользователя переехало в панель; «Профиль» открывает окно с именем, ролью и порталом (отдельной страницы профиля в прототипе нет).
- Скрытая панель имеет ширину 0 и атрибут `inert` (её ссылки не получают фокус). Предпросмотр — отдельный слой поверх контента. Шапка контента — свой контекст наложения, поэтому кнопка контента не может оказаться над слоем предпросмотра. Вместо этого в предпросмотре кнопка «Закрепить панель» стоит ровно на её месте: тот же клик закрепляет панель.
- Ctrl+B на узком экране открывает и закрывает выезжающую панель. В выезжающей панели у кнопок нет подсказок: иначе первое Esc закрыло бы подсказку, а не панель.
- Ширина выезжающей панели на узком экране — сохранённая ширина, но не больше 288 px и 85% экрана.
- Настройки панели хранятся в `mig.ui.nav` как `{ staff|assist|clinic|hr: { collapsed, width } }`. Старый ключ `mig.ui.navCollapsed` больше не читается: панель просто откроется развёрнутой.
- Цвета панели заданы токенами `--sb-*` в `tokens.css` на `:root` — они одинаковы в темах `staff` и `client` (по ТЗ панель от темы не зависит). Шрифт панели — Golos Text в обоих режимах.
- Тонкие полосы прокрутки (пересмотрено ниже): сначала были через `::-webkit-scrollbar`, теперь через стандартные свойства.
- Строка «Убыточность» в очереди андеррайтера ведёт на новую страницу `/staff/clients/:id/loss`. Данные для неё отдаёт отдельный эндпоинт `GET /api/clients/:id/loss-stats`: премия, убыточность, число и сумма обращений, по категориям и по 12 месяцам (по дате услуги, без отказанных). Схема ответа строгая (`.strict()`): лишнее поле со списком или именем не пройдёт проверку на клиенте.
- В карточке клиента строка истории «Новый убыток У-…» показывается только ролям с `claims.read`: номер — это уже отдельный убыток. Вкладку «Застрахованные» в карточке клиента андеррайтер видит по матрице (`insured.read`), её не трогали.
- «Войти как…» — поповер с поиском, а не выпадающее меню: в меню Radix поле ввода конфликтует с поиском по первой букве. Пункты по-прежнему `role="menuitem"` в группах «МИГ», «Ассистанс», «Клиника», «HR компании», «Застрахованный». Строка — «Роль — email», у застрахованного — телефон. Стрелки переходят между пунктами, Enter в поиске выбирает первый найденный.

## Предпросмотр панели и стандартные полосы прокрутки
- Предпросмотр открывается после 200 мс непрерывного наведения на кнопку панели: быстрый проход мышью по углу ничего не открывает. Закрытие — по-прежнему через 300 мс после ухода.
- После скрытия или показа панели (клик, Ctrl+B) наведение на кнопку не открывает предпросмотр, пока указатель не уйдёт с неё. Кнопка может сама подъехать под неподвижный курсор, пока контент сдвигается (150 мс), поэтому «ушёл» считается так: `mouseleave` кнопки или движение указателя не над кнопкой — после того как раскладка устоялась (250 мс); через 250 мс пауза снимается сама, если последняя позиция указателя (`elementFromPoint`) не над кнопкой; движение указателя на кнопку после движения в другом месте — тоже новое наведение. Так быстрый жест «Ctrl+B и сразу к кнопке» работает, а кнопка, приехавшая под курсор, панель не открывает.
- Полосы прокрутки: на всех элементах `scrollbar-width: thin` и `scrollbar-color: var(--scroll-thumb) transparent`. Chrome/Edge 121+ и Firefox рисуют их сами, на Windows Chrome оставляет стрелки по краям. При этих свойствах Chromium игнорирует `::-webkit-scrollbar`, поэтому стили `::-webkit-scrollbar` (6 px, ползунок с наведением) оставлены только как запасной вариант для Safari внутри `@supports not (scrollbar-color: auto)`. Цвет ползунка при наведении стандартными свойствами не задаётся — в Chrome и Firefox он один.

## Языки интерфейса: ru, uz-Latn, en
- Интерфейс всех порталов и приложения — на трёх языках (раньше по CLAUDE.md портал и HR-кабинет были только на русском). Русский по умолчанию.
- Ключи плоские (`раздел.экран.элемент`), по одному файлу на раздел и язык. Тип `Translation<typeof Ru>` делает полноту проверкой `tsc`; тест в `src/i18n/i18n.test.ts` дополнительно проверяет плейсхолдеры, отсутствие кириллицы в uz/en и пересечения ключей между разделами.
- Русский текст при переносе в словари сохранён без изменений (на нём держатся тесты). Исключение — места, где раньше было неправильное склонение: там теперь `tp()`.
- В подписях вида «Сумма, UZS» русский текст сохранён как был; в uz — «soʻm», в en — «UZS».
- Смена языка перемонтирует дерево от корня (`I18nProvider` с `key`). Поэтому `t()` можно вызывать прямо в рендере и в модульных функциях без хука. Черновик формы на экране при смене языка сбрасывается: язык не меняют посреди формы.
- Константы на уровне модуля не вызывают `t()` при загрузке: справочники через `defineLabels` (геттеры), навигация — через геттеры.
- Сообщения zod — ключи, упакованные с параметрами (`v.tooLong|{"max":200}`). Те же схемы на мок-сервере дают ошибки полей тоже ключами; `Field` переводит их через `tm()`. Строка, которая не является ключом, показывается как есть (данные).
- `ApiError` теперь `{ code, key, params?, fields? }` без поля `message`. Тексты рабочего стола (KPI, статусы и детали очереди, «Требует внимания»), очереди ассистанса, статистики HR и напоминаний по сделке сервер отдаёт упакованными ключами. Аудит, чат, история клиента и события — это данные, они остаются как есть.
- API интеграции клиник (для МИС) остаётся русским: ответы там читают машины и разработчики, а не пользователь интерфейса.
- Демо-строки не попадают в сборку без `VITE_DEMO_MODE`: демо-модуль сам регистрирует свой словарь (`registerMessages`). Тест сборки без демо по-прежнему зелёный.
- Валюта: «сум» (ru), «soʻm» (uz-Latn), «UZS» (en). Документы (КП, договор, ДС, сертификат, счета-заглушки PDF) сохраняют свой формат `UZS` через `formatMoneyDoc`/`formatDateDoc` независимо от языка интерфейса.
- Относительные сроки — `Intl.RelativeTimeFormat` (style `short`): «через 16 дн.», «вчера», «завтра». Раньше было «через 16 дн» и «−1 дн».
- В части сборок Chromium Intl объявляет узбекский поддерживаемым, но форматирует корневыми данными («2026-01-15», «yesterday», «156,000»). Это определяется на лету: тогда даты и числа в узбекском интерфейсе идут по русским шаблонам (dd.mm.yyyy, группировка пробелом — так принято в Узбекистане), а относительные сроки берутся из словаря (`fmt.rel.*`).
- Знаки ʻ и ʼ: в Golos, Rubik и JetBrains Mono нет ʻ (U+02BB). Глиф из Nunito оказался слишком широким, поэтому `scripts/build-uz-marks.py` собирает из Golos шрифты по ~600 байт на начертание (ʻ — глиф левой кавычки Golos, ʼ — собственный U+02BC). Они лежат в `public/fonts`: не `data:`-URI, чтобы проходить CSP `font-src 'self'`. Подключение — через `FontFace` с `unicode-range: U+02BB-02BC`, первым в каждом стеке. Лицензия OFL лежит рядом.
- Пояснение ИИ к покрытию приходит на языке модели: она поддерживает `ru` и `uz`, для `en` используется `ru`. Английские подсказки-примеры в приложении могут не распознаваться мок-сопоставлением услуг.
- Справочник медицинских услуг (`coverage/catalog.ts`) — данные, не переводится. Образцы строк CSV-шаблонов и выписки 1С — тоже данные (оставлены с `eslint-disable` и причиной). Номера документов только ASCII, а подписи форм собственности лежат в `src/shared/config/legalForms.ts` на трёх языках.
- Ключи сервера тянут за собой подписи в параметрах (специальность, категория, сумма), они вычисляются на сервере на языке в момент запроса. Поэтому при смене языка все запросы инвалидируются и перезапрашиваются.
- Перевод на узбекский и английский сделан без носителя; все термины помечены «требует проверки МИГ». Для правок — `docs/i18n-review.csv` и `npm run i18n:import`.
- Видимый переключатель языка — `LanguageButton` в верхней панели всех порталов (справа, после поиска; у клиники и HR, где поиска нет, — у правого края) и в шапке главной приложения вместо сегментного RU·UZ·EN. Кнопка показывает код языка, список — полные названия на своём языке. Переключатели в меню пользователя, на экранах входа и в профиле приложения остались.
- gitleaks: словари не исключаются целиком. Одна ложная находка (`generic-api-key` на строке с «password» в `src/i18n/dict/en/v.ts`, коммит `b1a91e9`) погашена отпечатком в `.gitleaksignore`. Любой новый ключ в словарях по-прежнему ловится.
- Шаблоны номеров документов живут в «Параметры ДМС» → «Нумерация документов» (демо-значения) и меняются тем же потоком «четырёх глаз»: ключ `numbering.<вид>`, значение изменения `number | string`, те же права, аудит и очередь подтверждения; все генераторы номеров мок-сервера берут шаблон в силе (`packages/domain/src/services/params.ts`: `ParamsView.numbering()`, `nextDocNumber()`, `maxDocSeq()`).
- Смена шаблона не перенумеровывает выданные документы; максимальный порядковый номер читается по шаблону в силе, затем по демо-шаблону, затем по последним цифрам номера.
- Номер документа на возврат премии: `VZ-{REF}-{N:6}`, где REF — номер допсоглашения, N — порядковый номер документа на возврат.
- API клиник принимает номера полиса и ГП в любом шаблоне МИГ: латиница, цифры, «-» и «/», до 60 символов (`DOC_NUMBER_RE`); номер полиса сравнивается без учёта регистра.

## Закреплённая шапка таблиц
- Как в GitHub и Notion: на странице портала ровно одна вертикальная прокрутка — область содержимого под верхней панелью (`<ContentScroll>`, `data-content-scroll`, `src/shared/ui/content-scroll.tsx`). Каркас портала (`.portal-shell`) занимает ровно высоту окна за вычетом демо-баннера и сам не прокручивается; документ тоже не прокручивается. Первая версия (обёртка таблицы со своим `overflow: auto` и `max-height`) отменена: вложенная прокрутка внутри прокручиваемой страницы сначала крутила таблицу, а у её конца — страницу, и шапка уезжала.
- Обёртка таблицы (`<TableScroll>`, `.table-scroll`) не прокручивается ни по одной оси: нет `overflow` и `max-height`. Ячейки шапки (`thead th`, `data-sticky-head`) — `position: sticky; top: 0` относительно области содержимого, то есть ровно под верхней панелью (и баннером); заголовок страницы, вкладки и фильтры уходят вверх, шапка доезжает до панели и стоит там до конца таблицы, в том числе в самом нижнем положении страницы.
- Горизонтальная прокрутка широких таблиц: **прокручивается вся область содержимого** (`overflow: auto` у неё самой, по обеим осям), а не обёртка. Почему не `overflow-x: clip` с выбором столбцов: clip прячет столбцы без возможности до них добраться, и на узком экране (телефон) таблица стала бы недоступной без ручной настройки столбцов; прокрутка области содержимого сохраняет закрепление (контейнер sticky один и тот же) и оставляет все столбцы доступными. Карточка с таблицей и каждая колонка на пути к ней растут вместе с таблицей (`min-width: min-content` для `.rounded-card` и `.min-w-0`, содержащих таблицу; колонки сеток рядом с таблицами — `minmax(min-content, 1fr)` вместо `minmax(0, 1fr)`), поэтому широкая таблица отодвигает соседние блоки, а не наезжает на них; e2e проверяет это на всех разделах меню шести ролей. Минус: при горизонтальной прокрутке вбок уезжает и заголовок страницы — для редких широких таблиц это приемлемо.
- Строка итогов (`tfoot`, `data-sticky-foot`) и панель пагинации `DataTable` (`.table-pager`: «46 клиентов · … 1–25 из 46») закреплены внизу видимой области, пока таблица на экране: пагинация — `bottom: 0`, итоги — над ней (`bottom: var(--pager-h)`, высоту панели меряет `ResizeObserver`).
- Исключение — таблицы в модалках и карточках со своей прокруткой: там тот же CSS закрепляет шапку внутри этого контейнера (sticky берёт ближайший прокручиваемый предок).
- Тень под шапкой появляется, когда шапка закреплена: `<TableScroll>` слушает прокрутку ближайшего прокручиваемого предка и ставит `data-scrolled`, пока верх таблицы выше верха этого контейнера. В начальном положении тени нет.
- Фон ячеек шапки непрозрачный (`--color-surface`); нижняя линия — `inset box-shadow`: обычная граница у sticky-ячеек с `border-collapse` пропадает. `z-index` шапки, итогов и пагинации — 2: выше строк, ниже верхней панели (30), выезжающей боковой панели (40), меню, подсказок и модалок (50).
- Переход на другую страницу открывает её с начала: область содержимого прокручивается наверх при смене пути (`ScrollRestoration` работает только с окном).
- Печать: `@media print` снимает закрепление и ограничение высоты каркаса и области содержимого, страница печатается целиком.
- У `DataTable` появилась строка итогов (`totals` по ключам столбцов → `<tfoot>`, закреплена внизу): используется в реестре клиники (количество и сумма). Строки ДС уже имели `<tfoot>`.
- Сортировка добавлена в таблицы, где её не было, но она нужна для работы с длинным списком: обращения ассистанса (номер, дата создания — на сервере) и строки реестра клиники (дата услуги, сумма — на странице, реестр загружается целиком).

## Боковая карточка (split view)
- Где есть: списки МИГ «Клиенты» (`/staff/clients`), «Убытки» (`/staff/claims`) и «Сделки» (`/staff/deals` — и таблица, и доска; `?panel=id`). Остальные списки во всех порталах открывают страницу (полисы, договоры, обращения и ГП ассистанса, реестры клиники) или модальное окно (очередь ГП МИГ, ГП клиники, записи); «Клиники» и «Чат» ассистанса — мастер-деталь, где правая часть — основное содержимое страницы, а не карточка строки. Их не трогали.
- Карточка убытка: номер, статус, категория, SLA; застрахованный, клиент, где оказана услуга, дата, заявлено/одобрено, резерв (если роль видит резервы), создан, 5 последних смен статуса; внизу «Открыть карточку» и «Карточка застрахованного» (роли `INSURED_CARD_ROLES`). Решения по убытку (переходы, урегулирование) остаются на полной странице — в карточке только просмотр.
- Карточка сделки: клиент, форма, этап, «продление», номер; напоминания, тип, менеджер, андеррайтер, численность, текущий страховщик, премия, желаемое начало, 5 последних событий; внизу «Открыть карточку» и «Карточка клиента» (роли раздела «Клиенты»).
- Доска сделок: обычный щелчок по плитке открывает карточку рядом (плитка выделена рамкой), Enter на плитке, щелчок с модификатором или средней кнопкой — переход по ссылке на полную карточку, как раньше; Esc и «Назад» закрывают. ↑/↓ на доске не переключают карточку: у доски нет линейного порядка строк (колонки по этапам).
- Щелчок по строке убытков и сделок больше не уводит на страницу: полная карточка — Enter на строке или «Открыть карточку»; e2e lifecycle и flows обновлены соответственно.
- Раскладка: [боковая панель] [область содержимого — единственная прокрутка] [карточка]. Место для карточки даёт каркас портала: `<ContentScroll>` рендерит `<DetailPanelHost>` — строку из области содержимого и слота (`data-detail-slot`, `display: contents`); страница пишет `<DetailPanel>` где угодно, карточка порталом попадает в слот. Она сестра области содержимого, не потомок: закреплённая шапка, итоги и пагинация таблицы её не перекрывают и не могут, область содержимого сужается на ширину карточки. Слот в `ContentScroll`, поэтому все четыре каркаса (МИГ, ассистанс, клиника, HR) получили его без правок.
- Карточка (`src/shared/ui/detail-panel.tsx`) — от нижнего края верхней панели до низа окна, со своей вертикальной прокруткой (`overscroll-contain`); шапка (название, форма, статус, ИНН, «Закрыть») закреплена сверху, кнопки действий («Открыть карточку», «Подготовить КП», «Письмо HR») — снизу.
- Ширина: тянется за левый край, 360–640 px, двойной щелчок — 420; на разделителе (`role="separator"`, `aria-valuenow/min/max`) ← шире, → уже на 16 px, Home/End — пределы (край левый, поэтому стрелка «наружу» расширяет). Одна ширина на все списки и порталы: `mig.ui.detail` через `storage.ts` (UI-настройка, как ширина боковой панели); при чтении значение зажимается, мусор отбрасывается.
- Клавиатура: щелчок по строке переключает карточку сразу; ↑/↓ в таблице двигают фокус и, пока карточка открыта, переключают её (`DataTable.onRowMove`); Enter открывает полную карточку клиента; Esc закрывает карточку, если его не обработали раньше (меню или диалог внутри карточки — Radix ставит `defaultPrevented`).
- Выбранная строка подсвечена (`aria-selected`) и при переключении стрелками или открытии по ссылке прокручивается в видимую часть области содержимого с учётом закреплённой шапки, итогов и пагинации. Отступы `DataTable` меряет сам (`reveal()`): Chrome не учитывает `scroll-margin` у строки, которая уже внутри области прокрутки, но под закреплённой пагинацией. `scroll-margin` у строк (`index.css`) оставлен для прокрутки браузером при фокусе с Tab.
- Узкий экран (< 1280 px): карточка открывается поверх таблицы справа как модальный диалог Radix (светлая подложка `bg-black/10`, Esc, щелчок по подложке, «Закрыть», ловушка фокуса), без перетаскивания ширины. Прокрутка таблицы под ней заблокирована дважды: Radix гасит колесо вне диалога, а область содержимого получает `overflow: hidden` (`data-locked`). Диалог порталится в слот каркаса, а не в `body`, чтобы остаться внутри `data-theme` портала.
- Слои: прикреплённая карточка не пересекается с таблицей (z-index 10 только для разделителя у края); диалог на узком экране — 40, как выезжающая боковая панель: выше шапки таблицы (2) и верхней панели (30), ниже меню, модалок (50) и подсказок (60), которые Radix рендерит в `body`.
- История: `?panel=id` сохранён (`useDetailPanelParam`). Открытие карточки добавляет запись в историю (Назад закрывает её), переключение на другую строку заменяет запись (одно «Назад» закрывает карточку, сколько строк ни пролистано), закрытие возвращается на запись списка (`navigate(-1)`, если карточку открыли из списка — отмечено в `history.state`) или убирает параметр на месте, если страницу открыли прямой ссылкой. id в параметре — только UUID, иначе карточка не открывается.
- Печать: карточка не печатается (`print:hidden`), печатается таблица целиком.
- Старый `SidePanel` (`src/shared/ui/side-panel.tsx`, `sticky` внутри области содержимого — уезжал с прокруткой и оказывался под шапкой таблицы) удалён: его использовал только список клиентов.

## Кнопка «+ Создать»
- Один общий компонент (`src/features/shell/CreateMenu.tsx`) и один конфиг (`createItems.ts`): пункт виден, если `can(роль, право)` выполняется в портале роли; первый подходящий вариант задаёт точку входа (`?create=…`, страница снимает параметр после открытия диалога). В URL только ключевое слово, без данных.
- Автоматические пункты (Полис, Доп. соглашение, КП и договор) показываются неактивными с пояснением (текст, `aria-describedby`, `title`) только ролям, у которых есть права на соответствующий процесс, и только если роль может создать что-то ещё. Роль без доступных пунктов кнопку не видит.
- «Клиент» для продаж — лид (`leads.manage`), для андеррайтера — клиент (`clients.write`). «Сделка» открывает ту же форму лида: сделка начинается с лида. «Убыток» (оператор) открывает палитру команд в режиме выбора застрахованного — отдельного списка застрахованных нет. «Обращение» начинается с поиска застрахованного в ассистансе, «Гарантийное письмо» — с проверки пациента в клинике.
- Кнопка «+ Новый клиент» в верхней панели МИГ объединена с «+ Создать»; кнопки на самих страницах остались.
- Для пункта «Пользователь» у администратора МИГ добавлено приглашение сотрудника (ФИО, рабочий email, роль) — `POST /api/admin/users` под `users.manage`; пароль не возвращается, действие пишется в аудит.
- Горячая клавиша — физическая клавиша C (`code: KeyC`, работает и в русской раскладке как «С»); игнорируется с модификаторами, при автоповторе, в полях ввода и при открытом диалоге или меню.

## Перенос действующего портфеля
- Права: `migration.manage` (администратор) и `migration.approve` (администратор, кроме автора пакета); мок проверяет их на каждом эндпоинте.
- Строки с ошибками: шаг с ошибками подтверждается только явной галочкой «Исключить строки с ошибками (N)»; такие строки не записываются никогда. Отдельный «исправленный» демо-файл не нужен.
- Шаг открывается, когда все предыдущие подтверждены или пропущены; перезагрузка или пропуск шага сбрасывает следующие. Ссылки в строках разрешаются на безошибочные строки предыдущих файлов того же пакета или на записи, уже существующие в системе.
- Проверка — это только разбор и отчёт: строки хранятся в пакете, в рабочие таблицы ничего не попадает до применения вторым администратором. При отправке и при применении весь пакет проверяется заново; если данные успели измениться (например, тот же клиент загружен другим пакетом), пакет возвращается в черновик с ответом 409.
- Перенесённый договор: сразу «действует», новый номер по шаблону, старый — `externalNumber`; к нему создаются сделка в стадии «действует», полис, документы клиента и новые сертификаты (старый номер — `externalCertificateNumber`). График платежей строится по периодичности; счета не создаются автоматически — неоплаченные счета приходят отдельным файлом.
- Премии при переносе: в файле договоров общая премия `premium` плюс премии по типу `premium_employee` и `premium_family`; в файле застрахованных — необязательная индивидуальная премия `premium` (годовая премия строки: сотрудник вместе с членами семьи под его сертификатом). Деления премии поровну больше нет.
- Колонки премий по типу называются `premium_employee` и `premium_family` (snake_case, как в постановке пользователя), хотя остальные колонки шаблонов в camelCase.
- Премия застрахованного по приоритету: индивидуальная → по типу (`premium_employee` + `premium_family` × `familyMembers`) → ошибка строки «Нет премии». Отдельной колонки «сотрудник / член семьи» не добавляли: в модели системы застрахованный — сотрудник, а члены семьи — число `familyMembers` у его сертификата (`familyMembersCount`, тариф полиса `employee`/`family`); отдельные строки членов семьи считали бы их дважды. (Заменено разделом «Члены семьи как застрахованные»: строка на человека.)
- Строка договора без `premium_employee`/`premium_family` валидна (на шаге договоров ещё не известно, у всех ли застрахованных будет своя премия); ошибка «Нет премии» ставится на каждую строку застрахованного такого договора без своей премии. Если задана только `premium_employee`, строка с членами семьи без своей премии — тоже ошибка.
- Премия хранится у перенесённого застрахованного (`migratedPremium {amount, source}`) и используется вместо тарифа договора при расчёте годовой премии человека (`annualOf` в ДС на исключение, `premiumDelta` заявки HR на исключение).
- Тариф перенесённого договора для последующих изменений состава: `premium_employee`/`premium_family` из файла, а если их нет — базовый тариф программы (`defaultTariff`).
- Сверка премий по договорам: сумма премий застрахованных (строки к записи) против общей премии договора, допуск ±1 сум (округления старой системы). Расхождение — предупреждение на шаге застрахованных (на первой строке договора, колонка `premium`) и выделенная строка в блоке «Премии по договорам» рядом со сверкой; общая строка «Сумма премий» осталась. До применения — по проверке файлов, после — по премиям в системе, у откаченного пакета — как было при применении.
- Если у существующего клиента нет действующего полиса, текущим становится перенесённый; прежние значения сохраняются для отката.
- Использованные до переноса лимиты хранятся у застрахованного (`migratedUsed`) и прибавляются в расчёте лимитов: остаток в приложении = лимит программы − использовано до переноса − убытки после.
- Перенесённые убытки — только открытые статусы, источник «оператор»; если резерв отличается от заявленной суммы, это запись истории резерва «на дату переноса».
- Метка переноса — поле `migration {batchId, at, byName}` у клиента, договора, застрахованного, убытка и счёта; в карточках — плашка «Перенесено из старой системы».
- Откат блокирует любое новое действие после применения: изменяющее событие аудита по перенесённой записи или новая связанная запись (убыток, платёж, ДС, заявка на изменение, запись к врачу, ГП, визит, счёт, договор, сделка, КП, застрахованный, заявка на лимит, обращение, сообщение чата, файл), а также согласие застрахованного в приложении. События только чтения (вход, раскрытие ПДн, выгрузка) не блокируют.
- Сверка живая: после применения она сравнивает итоги файлов с текущими данными, поэтому последующие правки видны как расхождения. Исключённые строки с ошибками тоже показываются как выделенные расхождения.
- В CSV застрахованных есть необязательная колонка `phone` (нужна для входа в приложение); без неё — предупреждение. ПИНФЛ, не согласованный с датой рождения, — предупреждение.
- Файлы пакета (в них ПДн) удаляются после применения, хранится только отчёт.
- `MOCK_DB_VERSION` поднят до 3 (таблица `migrationBatches`), затем до 4 (`migratedPremium` у застрахованного, `contractPremiums` у пакета).
- Поиск по старому номеру: строка поиска в списке договоров (`GET /api/contracts?q=` ищет новый номер, старый номер и клиента), группа «Договоры» в палитре команд; поиск убытков находит и старый номер убытка.
- Демо-файлы генерируются детерминированно (`src/demo/migrationSamples.ts`), доступны на экране только в демо-режиме и совпадают с e2e-фикстурами (проверяется тестом).

## Регистрация убытка специалистом по убыткам
- Право `claims.create` выдано роли claims_officer. В «+ Создать» пункт «Убыток» для неё открывает форму на `/staff/claims?create=claim` с поиском застрахованного внутри формы; оператор по-прежнему идёт через палитру → карточку застрахованного. Вариант выбирается по `claims.create` + `claims.reserves` (поле `alsoPerm` в конфиге меню), то есть остаётся привязан к матрице прав. В карточке застрахованного — кнопка «+ Убыток» с предзаполненным застрахованным.
- Форма: застрахованный, дата события, категория, сумма, источник (`Claim.intakeChannel`: письмо HR, звонок, email, прочее), вложения. Источник обязателен при регистрации сотрудником МИГ и пуст у убытков из приложения, клиник и ассистанса.
- Резерв выставляется сразу: начальная точка существующей истории резерва — заявленная сумма («Регистрация: заявленная сумма»), без дублирующей записи; в аудит пишутся `claim_created` и `claim_reserve_changed`.
- Такие убытки имеют `source: 'operator'` и `handledBy: 'mig'`, поэтому всегда попадают в очередь «Новые» специалиста по убыткам.
- Вложения — по правилам гарантийных писем (PDF/JPEG/PNG по сигнатуре, до 10 МБ, до 10 файлов, изображения перекодируются), застрахованному не видны. `POST /api/claims` принимает multipart (поля + `files`), как `/me/claims`.

## Члены семьи как застрахованные
- Член семьи — отдельная запись `Insured` с `relation` (`employee` | `spouse` | `child` | `parent` | `other`) и `principalId` (id сотрудника; у сотрудника пусто). Поле `familyMembersCount` удалено; в API у сотрудника — вычисляемый список `family` (имя, кем приходится, статус), у члена семьи — `principalName`.
- Дата рождения — существующее поле `birthDate` строки БД (в API — `birthDateMasked`); отдельного `dateOfBirth` не заводили, чтобы поле было одно.
- `CensusRelation` = `InsuredRelation`: анонимная выгрузка для котировки принимает и `parent`, `other`; котировка по-прежнему считает премию по возрастным группам каждого человека.
- `limitMode`, `maxChildAge`, `studentMaxAge` — общие параметры ДМС (группа «Члены семьи»), не по программам: программы в системе несут только лимиты. Единица «лет» добавлена к единицам параметров.
- `limitMode = family_shared`: один лимит программы на семью по категории в пределах полиса; расход (убытки, принятые строки реестров ассистанса, перенесённые лимиты, резервы ГП) любого члена семьи уменьшает общий остаток; каждый член семьи видит тот же остаток.
- Ребёнок «в приложении родителя» — `relation = child` и возраст меньше `maxChildAge` (`studentMaxAge` при `isStudent`); день рождения, на который исполняется предельный возраст, — первый день задачи. 29 февраля в невисокосный год — 28 февраля.
- Задача «Предельный возраст» (`age_limit`) — в очереди андеррайтера (он решает заявки на изменение состава и ведёт клиентов), видна по праву `policy_changes.decide`; ведёт в карточку застрахованного; исчезает, когда по ребёнку есть заявка на исключение или он исключён. Автоматического исключения нет.
- Доступ в приложении (`src/shared/domain/family.ts`, используется моком): сотрудник видит ребёнка до предельного возраста полностью; взрослого (супруг, родитель, другой, ребёнок старше предела) — только факт страхования, полис, сертификат и QR; лимиты, убытки и записи — после согласия взрослого. Взрослый член семьи видит только себя (не сотрудника и не детей). Все остальные люди — 404.
- Дизайн API приложения: те же `/api/me/...` с необязательным `?personId=` (UUID человека семьи); без него — сам вошедший. Убыток и запись по id открываются, если доступ к их человеку — `full`. Чат и согласие на обработку ПДн — только свои.
- Согласие взрослого — запись `familyConsents` (кто, кому, когда дано, когда отозвано), в аудите `family_consent_granted` / `family_consent_revoked`; отозванные остаются в истории.
- Карта для возмещений: у члена семьи пустое `payoutCard` означает карту сотрудника; взрослый задаёт свою и может вернуться к карте сотрудника (`card: null`), у сотрудника карта обязательна. Смена карты в аудите без номера.
- Взрослый член семьи входит по своему телефону (`+998 90 000 00 02` у демо-супруги); у ребёнка телефона нет, он не приглашается в приложение и не считается в «Не в приложении» у HR.
- Добавление HR: `POST /api/hr/family` — та же заявка на изменение состава, что для сотрудника (`PolicyChange` с `relation`, `principalId`), должность у члена семьи пустая. Заявка из приложения: только сотрудник, с подтверждением согласия члена семьи; HR одобряет (создаётся та же заявка на изменение, начало — указанное или завтра) или отклоняет с причиной. Решение HR в аудите.
- Премия включаемого в течение срока — по условиям договора (`Contract.params.pricingBasis`, `src/shared/domain/pricing.ts`): `flat_by_type` (по умолчанию) — `premium_employee` сотруднику, `premium_family` члену семьи; `age_banded` — ставка возрастной группы человека на дату включения из таблицы договора `ageBandRates`. Сумма = годовая премия × оставшиеся дни / дни срока. Годовая премия и правило сохраняются в `payload.annual` / `payload.rule` заявки на изменение; строка ДС показывает правило («по типу: premium_family …» / «по возрастной группе 0–17: …», ru/uz/en). Заменяет прежнее «семейный тариф × коэффициент возрастной группы».
- Таблица ставок по возрастным группам не заполняется вручную: котировка выводит её из своего тарифа (базовая ставка × коэффициент группы × (1 − скидка за группу) × (1 + корректировки), округление до 1000) — те же множители, что у премий котировки; андеррайтер только выбирает основу расчёта в калькуляторе. Договор из КП копирует основу и таблицу из котировки (таблицу — всегда, чтобы основу можно было переключить в черновике). Группы — с 0 лет, без пропусков и пересечений, последняя открытая.
- `age_banded` без таблицы — ошибка: договор нельзя сохранить (422, поле `params.pricingBasis`), отправить юристу и подписать; решение по заявке на изменение и заявка HR по такому договору — 422 до каких-либо изменений. Исключение по `age_banded` возвращает по ставке группы на дату включения (или начала договора).
- Перенос портфеля: в файле договоров колонки `pricing_basis` (пусто = `flat_by_type`) и `age_bands` («0-17:900000; 18-29:1200000; …; 60+:2900000»), для `age_banded` таблица обязательна (ошибка строки). Премия застрахованного без индивидуальной по `age_banded`-договору — ставка группы на дату включения. Демо-файлы — `flat_by_type`; `age_banded` в сиде — договор сделки 3 (у юриста). В документе договора — п. 5.4 и Приложение 4 «Ставки по возрастным группам». `MOCK_DB_VERSION` = 6.
- Первичный полис (`/clients/:id/policies`) по-прежнему считается по типу: тариф сотрудника × сотрудники + семейный тариф × члены семьи (средние тарифы котировки); добавление в течение срока — по `pricingBasis` договора.
- Список полиса и приложение 2 договора — строка на человека: колонки `relation` (пусто = сотрудник) и `principal_pinfl` (ПИНФЛ сотрудника того же файла), `student` = 1 для студента; телефон и должность члену семьи можно не указывать. В документе договора столбец «Кем приходится» вместо «Членов семьи».
- Исключение сотрудника через HR создаёт заявки на исключение и его действующих членов семьи с той же даты (или с даты их включения, если она позже).
- Перенос портфеля: строка на человека, `relation` и `principal_pinfl`; сотрудник члена семьи — строка того же файла без ошибок или уже перенесённый застрахованный, обязательно по тому же договору. Премия по типу: `premium_employee` сотруднику, `premium_family` члену семьи; индивидуальная `premium` — у каждого человека. Ребёнок без телефона — без предупреждения.
- Демо-файлы переноса: у 200 сотрудников 204 члена семьи (супруг со своим телефоном +99878…, дети без телефона), суммы премий по договорам те же, что раньше; лимиты и убытки — по сотрудникам.
- Сид: члены семьи создаются отдельным потоком RNG после сотрудников; случайные убытки и записи сида по-прежнему распределяются между сотрудниками, чтобы остальной сид не сдвинулся; розыгрыш прежнего «размера семьи» оставлен в том же месте последовательности. `MOCK_DB_VERSION` = 5.
- В списках МИГ (клиент, полис) член семьи показывается вместо должности как «кем приходится · сотрудник»; в карточке застрахованного — список семьи со ссылками или сотрудник; в ассистансе — кем приходится. Выгрузка HR — строка на человека с колонками «Кем приходится» и «Сотрудник».
- Новые права: `family.self_service` (застрахованный, только своё) и `family.requests.decide` (HR своей компании); добавление HR — по `hr.employees.manage`.

### Члены семьи: экраны HR и приложения
- В кабинете HR отдельные маршруты: `/hr/family` (список), `/hr/family/new` (добавление, сотрудник передаётся UUID в URL, имя — в состоянии навигации), `/hr/family/requests` (заявки из приложения со счётчиком в навигации). Список сотрудников остаётся списком сотрудников; семья сотрудника открывается диалогом из меню строки.
- HR видит дату рождения члена семьи только годом (`birthDateMasked`), медицинских данных в ответе `/api/hr/family` нет (проверяется e2e).
- `Insured.ageLimit {age, reachedOn}` приходит с сервера, чтобы карточка застрахованного объясняла задачу «Предельный возраст» без полной даты рождения.
- В форме добавления поле телефона есть только у взрослых (для их собственного входа в приложение), флаг «студент» — только у ребёнка. «Член семьи» в «+ Создать» — отдельный пункт для HR.
- Выбранный в приложении человек хранится только в состоянии React внутри макета приложения (не в URL и не в хранилище) и сбрасывается при перезагрузке и смене пользователя.
- «Мой сертификат» в профиле всегда показывает вошедшего человека; сертификат с главной — выбранного в переключателе.
- `MeProfile` получил `principalName`/`principalFirstName`, `FamilyProfile` — `payoutCardOwn`: приложению нужно имя сотрудника и факт своей карты у члена семьи, но не сама карта.
- Мутации карты для выплат и заявки на члена семьи используют `gcTime: 0`, чтобы полный номер карты и ПИНФЛ не оставались в кэше TanStack.
- Сотрудник показывается взрослому члену семьи как «Держатель полиса — сотрудник»: «Страхователь» по словарю — это компания-клиент.
- Демо «Войти как…» при смене застрахованного без согласия ведёт сразу на `/app/consent` — так нет гонки двух переадресаций.

## Справка

- Якоря заголовков записаны в самом руководстве как `{#anchor}` в конце строки `##`/`###` (синтаксис pandoc/kramdown): переводчикам проще сохранить, парсер надёжно отделяет от текста.
- Аудитория — HTML-комментарии `<!-- audience: … -->` трёх видов: строка после заголовка (раздел), отдельная строка (блок до `<!-- /audience -->` или следующего заголовка), комментарий в конце пункта списка или строки таблицы (только она; GitHub такую ячейку не показывает). Уровни пересекаются: вложенная пометка только сужает.
- Словарь аудиторий: `all`, `staff`, `staff:<StaffRole>`, `hr`, `insured`, `clinic`, `clinic:admin|registrar`, `assist`, `assist:operator|doctor|billing|admin`, `demo` (только демо-сборка). Неизвестный токен — ошибка разметки, тест её ловит; раздел без пометки видят только сотрудники МИГ.
- Разметка по ролям сверх минимальной из ТЗ: HR видит весь раздел 6 (подписание, оплата, вступление в силу, выпуск полиса), кроме пункта о праве подписи за МИГ; застрахованный — «Члены семьи» (7) и строку 17 «Лимит исчерпан»; клиника — «Покрывается ли?» (8); сотрудники МИГ видят все подразделы 14 (чтобы помогать HR, клиникам и ассистансам).
- Раздел 10 для ассистанса — без «Контроль качества» и «Где МИГ видит ассистансы» (внутренние метрики МИГ). В 15 «Интеграции» клиника видит часть про свои ключи и вебхуки, ассистанс — весь подраздел, вводный абзац 15 — только МИГ.
- В разделе 18 «внутренние подробности» — раскрытие ПДн по причине и медкарта (`staff assist`), убыточность для андеррайтера (`staff`), секреты ключей API (`staff clinic assist`); в 19 у каждой строки статусов своя аудитория.
- Раздел 20 (`demo`) вырезается из руководства при сборке без `VITE_DEMO_MODE` Vite-плагином `mig-help-guide` (`vite.config.ts`, `src/shared/help/demoStrip.ts`): в такой сборке нет ни демо-аккаунтов, ни описания «Войти как…» (тест no-demo-build). Во время работы мок дополнительно проверяет флаг.
- Руководство импортирует только мок-сервер (`import.meta.glob(..., { query: '?raw' })` в `src/mocks/help-content.ts`); клиент получает уже отфильтрованный по роли markdown через `/api/help*`, как и все остальные данные. Сборка без моков руководство не содержит — его отдаст бэкенд.
- Перевод раздела берётся, только если его якорь и последовательность пометок совпадают с русскими; аудитория заголовков всегда берётся из русского файла, так что перевод не может расширить доступ. Иначе русский текст с `fallback: true`.
- Поиск — своя реализация без зависимостей (BM25 по лёгким основам слов после `normalizeSearch`, префиксы, опечатки по расстоянию Дамерау—Левенштейна, синонимы из словаря и короткий список `EXTRA_SYNONYMS`): minisearch не понадобился. Индекс строится на сервере (мок) из уже отфильтрованного по роли контента: скрытое найти нельзя.
- Единицы поиска — подразделы, вводные тексты статей и отдельные строки таблиц «Что делать, если…», «Справочник статусов» и словаря (строка словаря — термин, в выдаче отдельной группой «Термины»).
- «Задать вопрос» — новый сценарий ИИ `help` (help.answer) в общих настройках: выключатель сценария и «Отключить ИИ везде» дают ответ `status: 'disabled'`, поиск работает. Провайдер mock — извлекающий: короткий ответ, шаги, предупреждения — это предложения, пункты и ячейки руководства; источники обязательны; нет ответа, если лучший фрагмент покрывает меньше 60% слов вопроса (для двух слов — оба или одно в заголовке).
- В ответах определения словаря поднимаются только для «что такое…», цепочки статусов — для вопросов о статусах, строки «Что делать, если…» — когда ситуация в заголовке совпадает с вопросом; шаги берутся из нумерованного списка лучшего подраздела.
- Вопрос обезличивается `redactForAi` до поиска (метки ФИО, ПИНФЛ, телефонов и номеров выбрасываются из запроса) и хранится только в обезличенном виде с ролью и языком (`db.help.questions`, до 2000). Оценку «Полезно / Не полезно» ставит только автор вопроса (иначе 404); список для администратора — `GET /api/ai/admin/help-questions` (право `ai.admin`).
- Метрики сценария `help` на /staff/admin/ai: вызовы — вопросы, «согласие» — доля «Полезно», «нужен специалист» — доля вопросов без ответа.
- Кнопки «Открыть раздел» — по карте названий экранов `SCREENS` (`src/features/help/routeMap.ts`): только экраны портала роли и только доступные ей маршруты (доступ — по матрицам разделов `STAFF_SECTIONS`/`ASSIST_SECTIONS` и правам маршрутов роутера).
- Контекстная справка: `ROUTE_HELP` сопоставляет каждый шаблон маршрута роутера якорю; для неизвестного вложенного пути берётся ближайший родитель. `/staff/clients` → статья «Новый клиент» (`new-client`).
- Эталонный набор `src/features/help/eval/golden.json`: 40 вопросов по всем порталам с допустимыми якорями (любой из списка в первых трёх источниках), порог 85%, плюс вопросы, на которые у роли не должно быть ответа (HR о мошенничестве).
- Ключи запросов TanStack для справки включают роль: контент разный для ролей и не должен показываться другой роли из кэша.
- Экран справки у каждого портала свой: `/staff/help`, `/hr/help`, `/clinic/help`, `/assist/help`, `/app/help` и `…/help/:anchor` (якорь статьи или подраздела) с `#подраздел`; в URL только латинские якоря руководства. «Скопировать ссылку» копирует `…/help/<статья>#<подраздел>`.
- «Справка» — отдельный пункт внизу боковой панели (проп `footer` у `AppSidebar`, над меню пользователя) во всех порталах с панелью; у HR он заменил группу «Поддержка → Помощь». «?» («Справка по этому экрану») — в верхней панели рядом с выбором языка, открывает `…/help/<якорь из ROUTE_HELP>`. В приложении — пункт «Помощь» в профиле.
- Старая страница HR «Помощь» стала общим экраном справки; карточка менеджера МИГ и короткий FAQ кабинета остались под статьёй, «Написать нам» у HR — письмо менеджеру клиента.
- Канал «нет ответа»: сотрудники МИГ — «Написать куратору», клиника и ассистанс — «Написать нам» (оба `mailto:` на адрес из `src/shared/config/support.ts`; демо — публичный адрес МИГ, настоящие адреса кураторов и поддержки партнёров даст МИГ), застрахованный — чат приложения `/app/chat`. Тема письма фиксированная, текст вопроса в URL не попадает (может содержать ПДн).
- Ссылки внутри текста справки — обычные `<a href>` из HelpMarkdown; экран перехватывает клик и переходит через роутер без перезагрузки.
- Оглавление показывает подразделы только текущей статьи; на узком экране и всегда в приложении (колонка телефона) оно за кнопкой «Содержание справки».
- Термины словаря подчёркиваются пунктиром по одному разу на статью (в самом словаре — нет); определение — во всплывающей подсказке Radix по наведению и по фокусу с клавиатуры (термин в порядке Tab).
- «Открыть раздел «…»» — под каждым подразделом (и вводным текстом), где упомянут экран, и под ответом на вопрос; доступ проверяется ещё раз через `canOpenRoute`. Текст кнопки — подпись пункта навигации в текущем языке (`labelKey`; экранам приложения и «Документам» клиники добавлены ключи).
- Поиск в справке — ARIA-combobox со списком: группы «Термины» (до 4) и «Статьи» (до 8), совпадение — `<mark>` из частей сниппета сервера, ↑/↓, Enter, Esc; термин ведёт в статью словаря. В Ctrl+K портала МИГ — группа «Справка» (до 2 терминов и 5 статей) из того же серверного поиска.
- «Задать вопрос» выключен (поле и кнопка недоступны, пояснение), если `GET /api/ai/status` говорит, что сценарий `help` выключен или ИИ отключён везде; ответ `status: 'disabled'` даёт то же. Поиск при этом работает.
- Вкладки /staff/admin/ai: «Настройки и метрики» (как было) и «Справка» (вопросы без ответа и «Не полезно»); вкладка в URL `?tab=help`.
- «Скачать PDF» — версия для печати поверх экрана (портал в `body`, роль dialog) и сразу `window.print()`; пока она открыта, у `<html>` класс `help-printing`, и стили печати скрывают всё остальное. Титульный лист (название, роль, дата, язык, версия), оглавление со ссылками `#hp-<якорь>` (префикс, чтобы не совпасть с якорями статьи на экране), каждая статья с новой страницы, `tr { break-inside: avoid }`, заголовки таблиц повторяются, кнопок нет. Отдельный маршрут печати не нужен: содержимое «Вся справка» — `GET /api/help` для роли, «Текущая статья» — уже загруженная статья.

- «Открыть раздел» в переведённых руководствах находит экраны по их подписям в интерфейсе: uz-Latn — «…», en — “…” (подпись берётся из словаря по `labelKey` экрана), русские — по названиям из `SCREENS`.
- Строки `help.guide.<якорь>` в `docs/i18n-review.csv` — названия статей руководства для ориентира проверяющего: экспорт берёт их из `docs/help/USER_GUIDE.<locale>.md`, импорт их пропускает (правятся в markdown).

## Боковые колонки (одно правило для всех порталов)

- Общая раскладка «основная область + боковая колонка» — `<SideColumn>` (`src/shared/ui/side-column.tsx`). На экране от 1280 px колонка порталом попадает в слот `DetailPanelHost` (`[левая колонка][область прокрутки][правая колонка][карточка деталей]`): она соседка области прокрутки, не двигается при прокрутке и занимает высоту от низа верхней панели до низа окна. Уже 1280 px колонка выводится там, где её поставила страница (после основного содержимого), и прокручивается вместе со страницей. Карточки деталей уже 1280 px, как и раньше, открываются поверх.
- Колонка и карточка деталей — одна прокручиваемая область (`<ColumnFrame>`, `sticky-sections.tsx`): общий заголовок `sticky top-0`, кнопки `sticky bottom-0`, высота заголовка измеряется в CSS-переменную `--column-head-h`. Заголовок раздела (`<SideSection>` или `<Card>` внутри колонки) — `position: sticky; top: var(--column-head-h)` внутри своего раздела, поэтому следующий выталкивает предыдущий. Фон непрозрачный; закреплённый заголовок получает `data-stuck` (один capture-слушатель прокрутки на портал) и лёгкую нижнюю границу.
- Длинные полные карточки (убыток, застрахованный, договор, ДС, сделка, котировка) включают закрепление заголовков разделов и в основной области (`StickySectionsCtx`); шапка таблицы в таком разделе закрепляется под заголовком раздела (`--section-head-h`), ↑/↓ таблицы это учитывают.
- Колонки не печатаются (`print:hidden`), как и карточка деталей; документы печатаются своими кнопками.
- В «Активности» карточки клиента теперь есть журнал работы с клиентом (`ClientRow.log`); у демо-клиента Toshkent Agrologistika — 40 событий (версия мок-БД 7).

## Справка: одно поле для поиска и вопроса

- Поиск и «Задать вопрос» объединены в `HelpFinder` (`src/features/help/HelpFinder.tsx`): одно поле «Найдите термин или задайте вопрос», результаты поиска показываются под ним (теперь в потоке страницы, а не всплывающим списком, чтобы карточка ответа стояла над ними), первой строкой — «Спросить: «…»». Старые `HelpAsk`/`HelpSearch` удалены; карточка ответа (`HelpAnswer.tsx`) не изменилась.
- «Похоже на вопрос» (`isQuestion`, `src/shared/help/question.ts`): заканчивается на «?», начинается с вопросительного слова любого из трёх языков **и за ним есть ещё слово** (одно «как» — человек ещё печатает), или длиннее пяти слов. Тогда ответ запускается сам через 600 мс после паузы в печати; повторно тот же текст не спрашивается. Показывается только ответ на последний вопрос.
- Enter без выбранной строки — спросить (и для короткого запроса, если ИИ включён). Строка «Спросить» видна при любом непустом вводе; меньше 3 символов — сообщение о длине, как раньше.
- Ctrl+K: «Спросить в справке: «…»» (от 3 символов) открывает `/staff/help`, вопрос передаётся в состоянии маршрутизатора, а не в URL (в вопросе могут быть ПДн); после ответа запись истории его забывает.
- Сценарий справки выключен (или «Отключить ИИ везде») — строки «Спросить» нет ни в поле, ни в Ctrl+K, автоответа нет, поиск работает.
- В руководстве — подраздел «Справка» `{#using-help}` в разделе 2 (на трёх языках); «?» на экране справки любого портала ведёт на него.

## Только корпоративные клиенты и минимальная численность

- Четыре параметра группы «Клиенты» (первая в «Параметрах ДМС», все демо-значения): `minGroupSize` = 10, `minGroupCountsFamily` = нет, `allowedLegalForms` = все, кроме ЯТТ (ИП), с пометкой «требует решения МИГ», `belowMinDuringTerm` = «уведомить»; правила считает одна чистая функция `groupRulesOf` (`src/shared/domain/minGroup.ts`), её используют экраны и мок-сервер (`groupRules()`).
- `allowedLegalForms` хранится числом — битовой маской по порядку `LEGAL_FORMS` (параметры ДМС числовые, четыре глаза и аудит не меняются); в редакторе — флажки, нужна хотя бы одна форма.
- Лид и клиент недопустимой формы не сохраняются: сервер отвечает 422 с ошибкой поля `legalForm`, экран показывает то же объяснение под полем и не даёт отправить. Численность ниже минимума у лида — только предупреждение.
- Котировка ниже минимума никогда не утверждается «в пределах полномочий» (`quoteAuthorityProblem` получает группу данных для оценки): только согласование сотрудником с новым полномочием `allowBelowMinGroup` (демо: underwriter-head@) и с обязательным комментарием (сервер: 403 без полномочия, 422 без комментария); исключение хранится в котировке (`belowMinException`: кто, когда, почему).
- Договор перед подписанием (любым способом, включая ЭДО) проверяется по строкам приложения 2 (без него — по численности в параметрах договора): ниже минимума без утверждённого исключения в котировке — 409 и красная плашка в договоре. Перенесённые действующие договоры не проверяются.
- Исключение HR, после которого группа (активные без исключений на рассмотрении) падает ниже минимума: экран предупреждает до подтверждения; при «уведомить» заявка уходит и сервер ставит задачу `below_min_group` андеррайтеру и менеджеру (одна открытая на клиента и роль, ссылка на карточку клиента); при «запретить» — 409. Автоматического расторжения нет.
- Сид: клиенты формы ИП заменены на MChJ (длина пула не менялась, чтобы не сдвинуть остальной сид), кроме одного лида ИП для демонстрации запрета; добавлены лид на 6 сотрудников с черновиком котировки и котировка на 8 с утверждённым исключением; MOCK_DB_VERSION 9.
- Вход в приложение: подсказка «Для сотрудников компаний — клиентов МИГ и членов их семей»; неизвестный номер и неверный код дают один и тот же ответ сервера и один текст с советом обратиться к HR, и только после ввода кода (чтобы перебором нельзя было узнать, кто застрахован); у каждого номера свой счётчик попыток.
- Перенос портфеля: договор ниже `minGroupSize` или с клиентом недопустимой формы загружается (он действует) с предупреждением в отчёте пакета, а не ошибкой; предупреждения не меняют записываемые строки и подтверждённые шаги.
- Перенос портфеля: минимум считается по корректным строкам застрахованных этого договора в пакете; без файла застрахованных проверки и пометки нет. Пометки живут в `MigrationMark.warnings` / `MigrationMark.group`; клиент, созданный пакетом, получает свою пометку формы и пометки своих договоров, уже существующий клиент — нет.
- Перенос портфеля: предупреждение о форме называет договор и форму, но не клиента — имя ИП является именем человека, а в отчётах нет ПДн.
- Справка: Enter не переспрашивает вопрос, который уже задан автоматически после паузы (один ответ, одна запись в «Вопросах без ответа»); схема ответа `/params/values` знает все ключи параметров — это проверяет юнит-тест.

## Запросы между сотрудниками: полный цикл

- Запрос («Попросить {роль}») уходит ответственному за объект: менеджеру сделки (иначе менеджеру клиента), андеррайтеру последней котировки сделки (иначе андеррайтеру сделки) — только активному сотруднику этой роли; без ответственного — всем сотрудникам роли, первый «Взять в работу» становится исполнителем, у остальных строка пропадает (сервер отвечает 404).
- Статусы запроса: ожидает (`open`) → в работе (`in_progress`) → выполнено (`done`) / отклонено (`rejected`); «Отклонить» и ручное «Отметить выполненным» у сотрудника МИГ — с обязательным комментарием (у HR комментарий к «Выполнено» необязателен); автоматическое закрытие по действию (`completeTasks`) работает и для взятых запросов.
- Один открытый запрос одного вида (действие + кому) по одному объекту: повтор — 409, на объекте вместо кнопки плашка с исполнителем, датой и статусом; после закрытия кнопка возвращается.
- Срок ответа — два параметра группы «КП» (будни по Ташкенту, время суток сохраняется): «Срок ответа на внутренний запрос» (`requestResponseWorkdays`, демо 2 рабочих дня) — между сотрудниками МИГ; «Срок ответа клиента на запрос МИГ» (`clientResponseWorkdays`, демо 5 рабочих дней) — для запросов к HR (вместо прежних 7 календарных дней).
- «Завтра срок» и «Просрочен» отправляются исполнителю (или всей роли / HR клиента) и автору по одному разу; проверка сроков идёт при чтении уведомлений и запросов (в моке нет фонового планировщика). «Напомнить» — только автору и только после срока.
- Уведомления: исполнителю — сразу при создании («{Автор} просит: {что} — {объект}»), автору — при взятии, выполнении, отклонении (с комментарием исполнителя во второй строке); клик открывает объект и отмечает одно уведомление прочитанным, «Отметить всё прочитанным» — все; закрытие списка больше не отмечает прочитанными. Параметр-сообщение (`what`) переводится внутри `tm`.
- Колокольчик есть во всех порталах: МИГ, HR, клиника, ассистанс и приложение застрахованного (в приложении — над содержимым страницы).
- История запроса (`history`) и каждое изменение статуса пишутся в «События» сделки (договор — через свою сделку) и в «Активность» клиента; «Мои запросы» — вкладка рабочего стола (не тип очереди), видна тем, кто может отправлять запросы.

## Заявка на члена семьи на виду

- Вход в заявку с главной приложения: последний элемент переключателя профилей «+ Добавить» (только у сотрудника, показывается и без членов семьи) открывает форму сразу (`/app/family?add=1` — в адресе нет ПДн), плюс плитка «Моя семья» среди действий главной (у всех: взрослый член семьи видит там страхователя и подсказку вместо кнопки).
- «Моя семья»: у каждого члена семьи статус «В полисе» / «Исключён(а) из полиса»; кнопка «Добавить члена семьи»; назад — на главную.
- HR одобрил или отклонил заявку — сотруднику уведомление в колокольчике (ссылка на «Мою семью», причина отказа во второй строке).
- В приложении один колокольчик — в шапке главной (вместо прежней заглушки «Уведомлений нет»); полоса с колокольчиком над всеми экранами приложения убрана.
- Аудит заглушек: результаты и решения — в `docs/STUBS_AUDIT.md`; «Выйти на всех устройствах» завершает все сеансы человека (`POST /auth/logout?all=1`); убыток члена семьи в приложении показывает лимиты этого человека (`MyClaim.personId`); фраза «Демо-значение.» убрана из описаний параметров — её показывает чип, который исчезает после подтверждения МИГ.
- Бэкенд, шаг 1 (BACKEND_SPEC §13.1): npm workspaces — фронтенд в `apps/web`, общий код в `packages/{i18n,contracts,domain,seed}`; пакеты подключаются по имени прямо из исходников TypeScript (`exports: "./*": "./src/*.ts"`), без сборки и без project references.
- Добавлен четвёртый пакет `@mig/i18n` (словари и `t()`/`msg()` без React): от строк интерфейса зависят и правила `domain`, и схемы `contracts`, и seed, а сервер будет отдавать те же упакованные сообщения. Язык хранится через подключаемое хранилище (`configureLocaleStore`), в браузере его подключает `apps/web/src/i18n`, `<html lang>` тоже ставит фронтенд.
- Граница `contracts` / `domain`: типы и схемы ответов и запросов (включая `forms.ts` и схемы API интеграции) — в `contracts`; правила, параметры ДМС, права, форматирование, шаблоны документов и схемы строк переноса портфеля — в `domain`. Во время выполнения `contracts` зависит от `domain` (перечисления и проверки параметров), а `domain` от `contracts` — только типами.
- Seed (`@mig/seed`) не знает про мок-сервер: схема строк БД — `packages/seed/src/db.ts`, а то, что seed берёт у сервера (сделать базу текущей, превратить счёт ассистанса в убытки), передаётся хуками `SeedHooks`; мок подключает их в `apps/web/src/mocks/seed-db.ts`.
- Скачивание CSV (`downloadText`) осталось во фронтенде; экранирование CSV и имена файлов выгрузок — в `@mig/domain/lib/csv`.
- Пакеты проверяются отдельным `tsc` без DOM (`packages/tsconfig.json`) и не могут импортировать фронтенд (ESLint `no-restricted-imports`); юнит-тесты — одна команда `vitest run` с проектами `web` (jsdom) и `packages` (node).
- Демо-сайт на Cloudflare не перенастраивается: корневой `npm run build` собирает `apps/web` и копирует сборку в корневой `dist/`, куда смотрят `wrangler.jsonc` и настройки Pages.
- Мок отвечает только по адресу API (`location.origin` + `VITE_API_BASE_URL`, в тестах — абсолютный адрес): прежний шаблон `*/api/*` в `npm run dev` перехватывал модули Vite с `/api/` в пути (`/src/shared/api/queries/params.ts`) и отдавал им 404, из-за чего не загружался демо-модуль. Сборки и e2e это не задевало — там модули склеены.
- CI: e2e вынесены в отдельную задачу `e2e` с двумя шардами Playwright, которые идут параллельно (`--shard=1/2`, `2/2`, лимит 45 минут); задача `check` — typecheck, lint, юнит-тесты, сборка и `npm audit`. Одна общая задача шла 27–29 минут при лимите 30 и уже отменялась по времени.

## Бэкенд, шаг 2: сервисы вместо мок-ядер

- Логика всех эндпоинтов — асинхронные сервисы `packages/domain/src/services/*` (`(ctx, input) → результат`, ошибка — `DomainError`); они работают только через репозитории `ctx.repos` (`packages/domain/src/store/repo.ts`), поэтому тот же код пойдёт на Postgres. Реализация в памяти — `memoryRepos` (`store/memory.ts`): чтение отдаёт копии строк, изменение сохраняется только через `insert`/`update`/`put`/`updateWhere`/`remove`/`removeWhere`; порядок хранения тот же, что у массивов мока: `insert(row, { at: 'start' })` вместо `unshift` (новые сверху), списки без `orderBy` приходят в порядке хранения.
- Мок (`apps/web/src/mocks`) — MSW-адаптер сервисов и БД в памяти: обработчик разбирает запрос (сессия, параметры пути, JSON или multipart в простые значения) и вызывает сервис; задержка, имитация сбоев и сохранение в `sessionStorage` остались только в моке. Старые синхронные ядра мока (`*-core.ts`, `views.ts`, `params.ts` и переходные мосты) удалены.
- Тело запроса проверяет сам сервис (`validate(schema, body)` той же zod-схемой, что и форма): адаптер не знает схем, и API на FastAPI получит ту же проверку.
- Порядок ошибок одинаковый во всех эндпоинтах: сессия (401) → параметры пути (404 для не-UUID) → разбор тела (400/413) → права и проверки сервиса (403/404/409/422).
- Партнёрский API клиник и ассистансов — один каркас (`services/integrationKit.ts`: токены, области, IP, лимит запросов, идемпотентность, problem+json, журнал, выдача токена) и одна MSW-обвязка (`mocks/integration-http.ts`); время в журнале вызовов считается от прихода запроса (до имитации задержки), журнал сохраняется после каждого вызова, в том числе GET.
- Seed самостоятельный: `createSeed(opts)` больше не принимает хуки и не делает базу текущей во время заполнения; убытки из принятых счетов ассистанса seed строит сам (`packages/seed/src/seed-rebill-claims.ts`) по шаблону номеров из `dmsParams.values` создаваемой базы. Данные seed не изменились (побайтное сравнение до и после). Заменяет запись о `SeedHooks`.
- Номер убытка, заведённого сотрудником или застрахованным, — наибольший существующий номер + 1, но не меньше 9001 (`FILED_CLAIM_SEQ_FLOOR`), вместо счётчика в памяти мока, который сбрасывался при перезагрузке; убытки из реестров, счетов ассистансов и переноса портфеля — наибольший + 1 без нижней границы. Одна функция `nextClaimNumber` в `services/clinic.ts`.
- Тест сравнения старых ядер с сервисами (`services-parity.test.ts`) удалён вместе со старыми ядрами: сравнивать больше не с чем. Сценарии записи, где проверялось не только совпадение, остались регрессионными тестами сервисов (`apps/web/src/mocks/services-writes.test.ts`).

## Бэкенд, шаг 3: схема БД, RLS, pgTAP, CI

- Схема БД описана один раз в TypeScript (`packages/domain/src/store/schema.ts`) с типом `ColumnsOf<Row>`: каждое поле типа строки обязано иметь колонку, вид колонки и её обнуляемость проверяет компилятор, `enumOf<T>()` требует перечислить ровно все значения объединения; SQL-миграции, seed.sql, pgTAP-тесты и `docs/backend/RLS.md` генерируются из него и коммитятся (тест сверяет).
- Добавлена dev-зависимость `supabase` (Supabase CLI v2): локальная база (`supabase db start/reset`) и pgTAP (`supabase test db`) в CI без отдельной установки CLI.
- Локальная база — Postgres 15 (`major_version = 15` в `supabase/config.toml`), как в образе self-hosted стека; работает и на 17.
- Таблица журнала — `audit_log` (как в BACKEND_SPEC §9), остальные таблицы — snake_case имени коллекции, колонки — snake_case поля; зарезервированные слова (`from`, `to`) в SQL в кавычках.
- Служебные колонки начинаются с подчёркивания: `_pos`, `_created_at`, `_updated_at`, `_created_by` (у многих строк уже есть доменные `createdAt`/`updatedAt` со своим смыслом); `_created_at/_updated_at` ведёт триггер `app.stamp()`, `_created_by` — `app.uid()`.
- Порядок хранения — `_pos bigint` из последовательности `app.pos_seq`: добавленные в конец строки получают `nextval`, вставленные «в начало» — `-nextval` (всё более отрицательные); списки по умолчанию сортируются по `_pos`. У таблиц без ключа — синтетический `_id uuid`.
- Внешние ключи только там, где seed согласован (проверено загрузкой), и все `DEFERRABLE INITIALLY DEFERRED`: в одной транзакции строки приходят в любом порядке (клиент ↔ полис, договор ↔ полис). Ссылки на пользователей (`*_by_id`, `actor_id`, `user_id`) без FK: пользователи живут в нескольких таблицах и в Supabase Auth.
- Пароли (`password` строк пользователей) и байты файлов не хранятся в таблицах (поле `virtual`): учётные данные — в Supabase Auth, файлы — в Storage.
- ПИНФЛ и телефон: `*_enc bytea`, `*_key_ver smallint`, `*_hmac bytea` (поиск), `*_mask text` (маска для списков, её пишет API при шифровании — без неё нельзя строить списки в БД, не расшифровывая); номер карты выплат — только `payout_card_mask` и `payout_card_token`. Свободные тексты с медданными (`chat.text`, описание и решение обращения ассистанса, заключение врача по убытку), данные новых людей в заявках, приложение 2 и файлы переноса — `*_enc` без HMAC.
- Маскирование: шифротексты ПИНФЛ/телефона, токены карт, `secret_hash` ключей партнёров и секрет подписи вебхуков закрыты от `authenticated` привилегиями на колонки; списки застрахованных — представление `insured_masked` (`security_invoker`); полное значение — только `app.reveal(table, id, field, reason)` (SECURITY DEFINER: право `insured.reveal_pii`/`assist.insured.reveal_pii` или сам человек, строка видна по RLS, запись `reveal_pii` в аудит). Дата рождения и email не шифруются (их нет в требованиях §5, их считают сервисы), маски строит API или представление.
- seed.sql пишет ПДн открытым текстом в `*_enc` с `key_ver = 0` и HMAC на фиксированном dev-ключе — только для локальной разработки и CI; API шага 4 считает версию 0 «не зашифровано (dev)».
- RLS: каждая операция таблицы — набор «группа ролей → предикат строки», допуск группы определяется матрицей (`app.can_any(действия)`, правило роли не `false`); все политики начинаются с `app.active()` (пользователь, роль и `aal2` для сотрудников МИГ, клиник и ассистансов). Функции `app.*()` в политиках обёрнуты в `(select …)`, чтобы считаться один раз на запрос.
- Записи, которые сервисы делают как побочный эффект чужой роли (активация договора после подписи HR или оплаты, уведомления клиникам и вебхуки, флаги ИИ, контрольные выборки, массовое применение и откат переноса портфеля), RLS пользователю не открывает: API выполняет их через `systemDb` после проверки прав в сервисе. Аутентификационные таблицы (сессии, коды, блокировки, счётчики, токены партнёров, идемпотентность) — только сервисная роль.
- Клиника видит застрахованного только при действующем визите (`visits.expires_at > now()`), поэтому проверку пациента по QR/номеру полиса до открытия визита выполняет API (сервисная роль) — так же, как в моке.
- Журнал аудита: только добавление (нет привилегий INSERT/UPDATE/DELETE ни у одной роли и триггер, запрещающий UPDATE/DELETE/TRUNCATE даже владельцу); запись только через `app.audit()` — для пользователя автор берётся из claims; цепочка `sha256(hex(prev_hash) | каноническая запись)` в порядке `chain_seq` под advisory-lock; `app.verify_audit_chain()` и ежедневная проверка pg_cron с уведомлением всем администраторам (`srv.auditChainBroken`, ключ словаря добавит шаг 4).
- Фоновые задачи — `packages/domain/src/services/jobs.ts`; pg_cron вызывает SQL-функции для задач без доменной логики (очистка истёкших сессий/кодов/счётчиков/токенов, проверка цепочки аудита), остальные кладёт в `app.job_queue`, их выполняет API шага 4. Регистрация в pg_cron пропускается, если расширения нет.
- Seed детерминирован полностью: id убытков из принятых счетов ассистанса выводятся из id строки реестра, а не `randomId()`.
- pgTAP-тесты матрицы проверяют точное число видимых строк (а не «больше нуля») и запись на своей/чужой строке; каждая попытка выполняется как пользователь seed (`set local role authenticated` + `request.jwt.claims`) и откатывается.

## Бэкенд, шаг 4 (часть 1): таблица маршрутов, API на Fastify, репозитории Postgres, RLS на запрос

- Одна таблица маршрутов для мока и сервера — `packages/domain/src/http/routes.ts` (метод, путь, вид входа `session|none|partner|demo`, вид тела `json|form|text|none`, вызов сервиса, вид ответа `json|201|raw`); порядок и поведение — как у прежних MSW-обработчиков, которые были спецификацией.
- MSW-обработчики теперь генерируются из таблицы (`apps/web/src/mocks/handlers/index.ts`); в вебе остались только ручки мока: задержка, имитация 500, сохранение состояния, «распознавание» чека 1 с, `/api/__demo/reset` и `/api/__demo/failures`; файлы обработчиков по областям удалены.
- Тело запроса в обоих адаптерах читает один код (`http/request.ts`) из Fetch `Request`: Fastify отдаёт сырые байты, адаптер собирает из них `Request`; multipart разбирает `Response.formData()` Node 20 — поэтому `@fastify/multipart` не нужен, а `@fastify/cookie` появится в части 2 вместе с BFF-cookie.
- Демо-маршрут `/__demo/mis-card` — в `http/demoRoutes.ts` (вид входа `demo`): веб подключает его только в демо-сборке, API — только вне production; сброс данных и имитация сбоев остаются только в моке.
- Новая зависимость `fastify` (apps/api): HTTP-сервер по BACKEND_SPEC §2.
- Новая зависимость `pg` (apps/api): драйвер Postgres; `@types/pg` — его типы (dev).
- `esbuild` объявлен devDependency `apps/api` (уже был в дереве через vite): сборка сервера в один `dist/server.js`; dev — `esbuild --watch` + `node --watch`, без `tsx`.
- SQL строится в `packages/domain/src/store/postgres.ts`, драйвер — только в API за интерфейсом `SqlSession` (`query` и `privileged`); пакет не зависит от `pg`.
- DSL Where/Query → параметризованный SQL: текст сравнивается и сортируется `COLLATE "C"` (как сравнение строк в JS), `contains` — `ILIKE` с экранированием `\ % _`, «нет значения» последним в обе стороны, при равенстве — `_pos`; не-UUID в условии по uuid-колонке — «нет совпадений», а не ошибка БД.
- Строки из БД — как в памяти: `ts` через `to_char(… at time zone app.tz())` в `YYYY-MM-DDTHH:mm:ss+05:00`, `date` — текст `YYYY-MM-DD`, `bigint`/`epoch` — числа, NULL — отсутствующее свойство (для `T | null` — `null`); поле `x?: T | null` в БД не отличить от `null`, поэтому `createClient` теперь пишет `assistanceId: null` явно.
- Журнал аудита пишется только через `app.audit()`; чтобы новые записи шли «в начало» (списки без сортировки, `audit.first()`), у функции добавлен последний параметр `p_pos` (миграция `…0500_audit.sql` перегенерирована), API передаёт `-nextval('app.pos_seq')`.
- RLS молча пропускает чужие строки в UPDATE/DELETE: репозиторий сравнивает число видимых строк с изменёнными и при расхождении бросает `RlsDenied` (ответ 500) — несоответствие сервиса и политик видно сразу, а не теряется.
- Репозиторий сам выполняет привилегированно (той же транзакцией, `set local role service_role`) три вида операций, заложенных в RLS шага 3: любые операции с таблицами без политик (`sessions`, `challenges`, `grants`, `lockouts`, `check_locks`, `access_tokens`, `idempotency`, `login_failures`, `check_attempts`, `api_calls`), вставки в таблицы, куда не вставляет ни одна роль (`webhook_deliveries`, `api_logs`, `clinic_events`, `sms_outbox`, `qa_samples`; `ai_rebill_flags` с политиками записи для проверяющего счета — уже под RLS), и чтение секретных колонок строк, которые RLS уже показал человеку (`insured.pinfl/phone`, `family_requests.pinfl`, `integration_clients.secret_hash`, `webhooks.signing_secret`): их расшифровывает API, а маскируют на выходе сервисы, как в моке.
- ПДн — через интерфейс `PiiCrypto` (`store/pii.ts`): шифротекст + версия ключа, HMAC для поиска по равенству (`where { pinfl }` → `pinfl_hmac`), маска рядом; сейчас только dev-реализация как в `seed.sql` (открытый текст, `key_ver = 0`, HMAC на dev-ключе), часть 2 подставит AES-256-GCM; номер карты превращается в маску при записи.
- Транзакция на запрос (`apps/api/src/db.ts`, READ COMMITTED): начинается под `service_role` (поиск сессии, вход), затем `set_config('request.jwt.claims', …, true)` + `set local role authenticated` с claims человека (`sub`, `aal`, `app_metadata.role` и `company_id/clinic_id/assistance_id/insured_id` из серверной записи пользователя).
- `aal = aal2` после входа по коду: в части 1 одноразовый код и есть второй фактор (как в моке); часть 2 берёт `aal` из Supabase Auth (TOTP).
- `DomainError` фиксирует транзакцию (как мок, где счётчики попыток и блокировки остаются после 401/429), любая другая ошибка — откат и 500 `errors.internal`.
- Временные сессии части 1: таблица `sessions` и `Authorization: Bearer <sessionId>`, как в моке; пароль демо-аккаунтов проверяется только при заданном `DEMO_PASSWORD` (виртуальное поле `password` читается как это значение; только dev/ci), код — `000000`; с `APP_ENV=production` сервер не запускается до части 2.
- Партнёрский API (`partner`) выполняется системными репозиториями: партнёр — не человек RLS, доступ ограничивают ключ и сервисы (scope, clinicId); OAuth-партнёры — этап 2.
- Справка на сервере: тот же движок поиска и ответов из `apps/web/src/shared/help` (чистый TS, по алиасу `@/`, ESLint разрешает API только его), руководство читается с диска (`HELP_DIR` или `docs/help`); ссылки «открыть экран» в ответах пока пустые — карта экранов живёт в вебе вместе с иконками навигации.
- ИИ-провайдер API — тот же детерминированный мок без задержки (настоящая модель — этап 2); картинка засеянного чека — пустой PNG, байты загруженных файлов не хранятся (Storage — часть 2).
- 403 против 404 под RLS: где мок отвечал 403 роли без права на существующую строку, а RLS спрятал бы строку (404), право роли проверяется до поиска (`readerRole` в договорах, ДС и сертификатах); `GET /files/:id` решает 403/404 по виду скрытого файла (`app.fact_file_kind`: есть ли и вложение ли ГП) и никогда не отдаёт скрытый файл.
- `systemDb` (`apps/api/src/systemDb.ts`) — сервисная роль вне запроса человека (задачи, обслуживание, фикстуры тестов); ESLint запрещает импорт `systemDb` из пакетов и из `apps/api/src` (кроме самого модуля, `jobs/` и тестов).
- Узкая привилегированная возможность сервисов — `ctx.system` через `systemRepos(ctx, причина)` / `asSystem(ctx, причина)` (`services/kernel.ts`); в моке это те же репозитории. Полный перечень мест и решений — `docs/PRIVILEGED_AUDIT.md` (раздел «Сокращение привилегированного доступа» ниже).
- Тест соответствия мок ↔ postgres (`apps/api/src/conformance.test.ts`): все GET-маршруты таблицы для каждого демо-аккаунта и сценарии записи всех порталов на обеих сторонах из одного seed, с замороженным `Date` и одинаковыми случайными числами (`crypto.randomUUID`/`getRandomValues` из одного генератора на каждый запрос) — ответы сравниваются целиком.
- Тесты API загружают seed под своё «сегодня» (усечение таблиц владельцем с временно выключенным запретом TRUNCATE журнала аудита), файлы идут последовательно (одна общая БД), а в конце прогона возвращается канонический seed (как после `supabase db reset`).
- CI: задача `api` (`supabase db start` → `db reset` → `api:build` → `api:test` с `DATABASE_URL`); в общей задаче `check` эти тесты пропускаются без базы.

## Бэкенд, шаг 4 (часть 2): Supabase Auth, BFF-сессии, CSRF, шифрование ПДн, файлы, фоновые задачи

- Новых зависимостей нет: Supabase Auth (GoTrue) и Storage — через их REST по `fetch`, проверка JWT (ES256/RS256 по JWKS, HS256 по `SUPABASE_JWT_SECRET`), AES-256-GCM, HMAC и TOTP (RFC 6238, тестовый режим) — `node:crypto`, PNG засеянных чеков — свой кодер на `node:zlib`, cookie — свой разбор одного имени (`@fastify/cookie`, обещанный в части 1, не понадобился), метаданные изображений — побайтно (без `sharp`).
- API — единственный клиент Supabase Auth: пароль проверяет GoTrue (`grant_type=password`, aal1), второй шаг — TOTP-фактор (challenge + verify в момент ввода кода → aal2). TOTP обязателен для сотрудников МИГ, HR, клиник и ассистансов; RLS по-прежнему требует aal2 только у МИГ, клиник и ассистансов, HR сессия без aal2 не создаётся в API.
- Тестовый режим MFA (development, ci, staging): демо-фактор с секретом из id учётной записи и опубликованного dev-ключа (`packages/domain/src/auth/devMfa.ts`); `000000` API превращает в текущий код этого фактора и проверяет его в GoTrue. Фактор с заданным секретом GoTrue через API создать не даёт, поэтому seed и тестовый режим пишут его в `auth.mfa_factors` напрямую. В production тестового режима нет.
- Первый вход без подтверждённого фактора: API подключает TOTP-фактор (незавершённые удаляет) и возвращает в ответе `login` поле `totpEnrollment: { uri, secret }`; подтверждение — тем же `POST /auth/otp`. Экран с QR — шаг 5.
- Вход по телефону: GoTrue `/otp` с `create_user: false`, ответ одинаков для известных и неизвестных номеров (ошибка GoTrue не раскрывается); демо-телефоны получают `000000` через `[auth.sms.test_otp]`. Supabase CLI выключает вход по телефону без включённого SMS-провайдера даже при hook, поэтому в `supabase/config.toml` включена заглушка Twilio, которая никогда не вызывается (при включённом hook GoTrue отдаёт SMS только ему).
- SMS: Auth Hook «Send SMS» → `POST /api/hooks/send-sms` (подпись Standard Webhooks, проверка срока 5 минут) → адаптер `SmsSender`; этап 1 — адаптер `log`: код пишет только вне production, телефон маскирует. Dev-секрет hook опубликован в `config.toml` и `env.ts`, production его не принимает.
- BFF-сессия — строка `app_sessions`, продолжающая строку `public.sessions` (FK `on delete cascade`): сервисы мока и дальше завершают сессии через `repos.sessions` (выход, деактивация пользователя), BFF-строка уходит вместе с ней. В таблице HMAC значения cookie (`SESSION_SECRET`), токены Supabase зашифрованы ключом ПДн.
- Обновлённые сервером токены сохраняются отдельным соединением вне транзакции запроса: Supabase ротирует refresh-токен, и откат запроса (500) не должен его потерять.
- Шаги входа — своя таблица `app_auth_challenges` (а не `challenges` мока): там токены aal1 и телефон (зашифрованы), попытки и ключ блокировки. Счётчики и блокировки — те же функции сервисов: `services/auth.ts` экспортирует `checkLock`, `recordFailure`, `findAccount`, `passwordFailed`, `recordSignIn`, `resendSchema`.
- Claims транзакции — из проверенного access-токена (`sub`, `aal`, ключи `app_metadata`); пользователь — по-прежнему из серверной записи. Если `app_metadata` токена разошлись с записью (сменили роль или привязку), API в том же запросе синхронизирует пользователя Supabase и обновляет токен; не сошлось — сессия завершается.
- Custom Access Token Hook (`public.custom_access_token_hook`, plpgsql) оставляет в `app_metadata` только `role` и привязки (и `provider(s)` Supabase), `user_metadata` в токене пустой.
- Роли в Supabase Auth следуют таблицам через триггеры (`staff`, `hr_users`, `clinic_users`, `assist_users`, `insured`) → очередь `app.identity_sync` → воркер API (outbox): сервисы не меняются и мок ничего не знает про Auth. Загрузка seed очередь не наполняет (`set_config('mig.seeding', 'on', true)`), её пользователей создаёт сам seed.
- Приглашения: в production учётная запись создаётся неподтверждённой и приглашается `inviteUserByEmail` (письмо уходит через SMTP контейнера auth), в development/ci с `DEMO_PASSWORD` — демо-пароль и демо-фактор (в локальном стеке нет SMTP). Поле `password` строк — виртуальное, на сервере `invitePassword` случайный.
- Ответы `/auth/*` прежние, плюс cookie; `sessionId` в ответе и `Authorization: Bearer <сессия>` — только при `AUTH_BEARER_COMPAT=1` в development/ci до шага 5, в staging и production запрещено.
- Cookie `__Host-mig_session` — сессионная (без Max-Age): срок жизни задаёт сервер (тайм-аут неактивности), выход и 401 по истёкшей сессии её стирают. Фолбэк `mig_session` без `Secure` — только `APP_ENV=development` и `INSECURE_DEV_COOKIE=1`.
- CSRF: `X-Requested-With: mig-web` обязателен на всех не-GET маршрутах таблицы, включая `/auth/login` (подмена входа); исключение — партнёрский API `/integration/v1/*` (свои bearer-токены, без cookie) и подписанный hook.
- Тест соответствия мок ↔ postgres входит через фикстуру мока (`apps/api/src/test/demoAuth.ts`: демо-пароль, демо-код, bearer-идентификаторы `sessions`), потому что вход через Supabase тратит другие случайные числа; `server.ts` её никогда не собирает, виртуальный пароль `demoPassword` в репозиториях есть только у неё. Вход Supabase и BFF проверяет `auth.test.ts`.
- ПДн: AES-256-GCM в `packages/domain/src/store/piiAes.ts` (Node-only модуль пакета: его используют API и генератор seed, браузер — нет), формат `IV ‖ шифротекст ‖ тег`, версия ключа рядом. `devPiiCrypto` (версия 0) удалён.
- `supabase/seed.sql` зашифрован опубликованным dev-ключом версии 1 с IV, выведенным из значения (файл стабилен), HMAC считается в JS — открытых ПДн в файле больше нет. API без `PII_KEYS` (development, ci, staging) читает его этим ключом; версия 0 читается только вне production.
- Production не запускается без `PII_KEYS`, `PII_HMAC_KEY`, `SESSION_SECRET`, `SMS_HOOK_SECRET`, с опубликованными dev-значениями (сравнение ключей в постоянном времени), с `DEMO_PASSWORD`, `AUTH_BEARER_COMPAT`, `INSECURE_DEV_COOKIE`. Staging может работать на dev-ключах: у него данные seed.
- Ротация ключей ПДн: новые значения — текущей версией (`PII_KEY_CURRENT`), старые читаются своим ключом; массовое перешифрование старых строк — отдельная задача, пока не сделана.
- Файлы: имя объекта Storage — id строки `files` (UUID v4 сервиса, лишних случайных чисел нет — тест соответствия не сбивается); бакет — по виду строки; `bucket`, `object_name`, `sha256`, `size_bytes` — колонки новой миграции, а не поля `FileRow` (домен не менялся); байты читаются только в `files.get`, объект пишется до строки.
- Удалённая строка `files` оставляет объект (запрос ещё может откатиться); такой объект никто не отдаёт, уборка сирот — позже.
- Метаданные изображений удаляются побайтно в доменном коде (`lib/imageMeta.ts`, одинаково в моке и на сервере): JPEG — APP1…APP13, APP15 и COM (APP0 и APP14 остаются), PNG — только чанки отрисовки, WebP — EXIF/XMP и их флаги VP8X. Пиксели не перекодируются (без библиотек): ориентацию Exif уже применил браузер при своём перекодировании.
- Скачивание: `GET /api/files/:id` по-прежнему отдаёт байты через API (контракт фронтенда); подписанная ссылка на 60 секунд — маршруты только сервера `GET /api/files/:id/link` (те же права) и `GET /api/files/signed?token=` (токен Storage, срок проверяет Storage; сам Storage наружу не открыт по BACKEND_SPEC §2.1).
- Засеянные чеки (у seed строки текста, не фото) сервер рисует PNG-«чеком» из полос по словам вместо пустой картинки; в Storage их нет.
- Бакеты создаёт миграция (если схема Storage уже есть) и API при старте (`ensureBuckets`): Storage может создать свою схему после миграций.
- Воркер — в процессе API (`WORKER=inline`) или `dist/worker.js`; задания берутся `for update skip locked`. «Напоминания SLA», «напоминания продаж», «продление» и «предельный возраст детей» в моке считаются при открытии экранов — воркер выполняет те же функции и пишет счётчики, новых уведомлений не добавляет (иначе сервер разойдётся с моком); `task-deadlines` и `contract-lifecycle` пишут то же, что мок.
- `app.job_cleanup_expired()` переопределена второй миграцией: дополнительно BFF-сессии без активности дольше 31 минуты, истёкшие шаги входа и выполненные задания старше 7 дней.
- Справка: карта экранов (`ROUTE_HELP`, `SCREENS`, роли разделов) перенесена в `packages/domain/src/help/routeMap.ts`; веб реэкспортирует её, навигация берёт оттуда роли разделов, ответы справки API несут те же ссылки «Открыть раздел».
- Лимиты Supabase Auth по IP в локальном/CI `config.toml` подняты (все запросы приходят с IP API); в рабочем развёртывании API передаёт IP клиента в `X-Mig-Client-Ip`, Supabase Auth считает по нему (`GOTRUE_RATE_LIMIT_HEADER`).
- В словари добавлены `errors.csrf`, `srv.auth.smsCode` (текст SMS) и обещанный шагом 3 `srv.auditChainBroken`.
- Тесты API берут `SUPABASE_URL` и сервисный ключ из окружения или из `npx supabase status` (локальный стек); загрузка seed в тестах удаляет созданных тестами пользователей Supabase Auth. Сборка API — три точки входа esbuild: `server.js`, `worker.js`, `provision-demo.js` (пользователи демо-аккаунтов для staging, production отказывается).

## Бэкенд, шаг 5: фронтенд на cookie-сессии в обоих режимах, e2e против бэкенда

- Сессия — только HttpOnly-cookie API: `client.ts` шлёт каждый запрос с `credentials: 'include'` и `X-Requested-With: mig-web` (на всех, не только изменяющих: проще и безвредно), без `Authorization`. `session.ts` хранит только открытые данные вошедшего (`{ user }`: роль, имя, область) — в памяти и `sessionStorage`; идентификатора сессии в браузерном коде нет. 401 старого запроса после повторного входа отсекается счётчиком входов (`sessionEpoch`), а не сравнением идентификаторов.
- Контракт: `SessionResponse` = `{ user }` (без `sessionId`), `ChallengeResponse.totpEnrollment?` (`{ uri, secret }`). Сервисы входа возвращают внутренний `SignedIn` (`sessionId` + `user`); маршрут таблицы с `session: 'start'` — адаптер кладёт идентификатор в cookie и отвечает `{ user }`; `session: 'end'` (выход) — cookie стирается. Так оба адаптера и фикстура соответствия ведут себя одинаково.
- Мок хранит «cookie» на своей стороне (`persist.ts`: `mockCookie`, в `sessionStorage` вкладки рядом с остальным состоянием мок-сервера), а не через ответ: MSW записал бы мокнутый `Set-Cookie` в `document.cookie` и в своё хранилище в `localStorage` — оба доступны коду страницы, а `localStorage` для сессий запрещён (правило 3). В тестах мока на Node (`createMockServer()`) — настоящий `Set-Cookie: mig_session=…; HttpOnly` и заголовок `Cookie`, чтобы тест держал несколько сессий; компонентные тесты берут хранилище мока (`createMockServer({ cookieJar: true })` в `test/utils.tsx`). MSW на Node сам эмулирует cookie-банку и дописывает сохранённые cookie к запросу — мок читает первый `mig_session`, а тестовый помощник `test-session.ts` всегда шлёт свой (пустой без сессии).
- CSRF в моке — тем же правилом, что в API (`packages/domain/src/http/csrf.ts`: `needsCsrf`, `readCookie`): изменяющий маршрут таблицы и демо-ручки без `X-Requested-With: mig-web` — 403 `errors.csrf`; 401 мок cookie не стирает.
- API стирает cookie в ответе 401, только если сам только что завершил сессию (тайм-аут, отозванный токен, учётная запись исчезла — `sessionEnded()`), а не для неизвестной сессии: ответ на запрос, отправленный до нового входа («Войти как…»), иначе стёр бы cookie новой сессии.
- `AUTH_BEARER_COMPAT` удалён: `Authorization: Bearer` принимается только партнёрским API; с этой переменной API не запускается ни в одном окружении (тест). Фикстура соответствия `test/demoAuth.ts` тоже перешла на cookie `mig_session`, `memoryClient` проверяет CSRF и ставит cookie как MSW.
- «Войти как…» — маршрут `POST /__demo/login-as` `{ login }` в демо-маршрутах таблицы: мок входит сервисами (демо-пароль и код), API — настоящим входом в Supabase Auth за один запрос (пароль демо-аккаунтов, демо-код тестового режима MFA, фиксированный код демо-телефонов) с BFF-cookie; только аккаунты из `DEMO_LOGIN_AS` (`packages/seed/src/credentials.ts`), текущая сессия на сервере завершается.
- Экран подключения TOTP — блок на экране кода (`features/auth/TotpEnrollment.tsx`): QR из otpauth-URI (`qrcode`), ключ для ручного ввода, тот же ввод кода. Секрет — только в памяти модуля до ввода кода: не в состоянии роутера (история браузера), не в URL и не в хранилищах; после перезагрузки вход начинается заново (API удаляет незавершённый фактор). В тестовом режиме MFA шаг не показывается: у демо-аккаунтов фактор есть в seed, новые получают демо-фактор.
- Серверные демо-ручки (`apps/api/src/demo.ts`, только development/ci/staging, в production — 404, тест): `reset` `{ xss? }`, `failures`, `clock`; без сессии, с CSRF, как ручки мока. Сброс сохраняет вошедших (как мок), строит seed для «сейчас» сервера.
- Сброс быстрый: таблицы очищаются `delete` при `session_replication_role = replica` (без триггеров и проверок FK; ~0,1 с против ~1 с `truncate` ста таблиц; где роль не может — `truncate`), seed для следующего сброса строится заранее (если его «сейчас» отличается от текущего не больше чем на 2 минуты), пользователи Supabase Auth переписываются, только если их отпечаток (логины, баны, роли, пароли, факторы) изменился с прошлой загрузки. Итог ~0,6 с на тест (было ~3 с). `delete` под ролью replica не каскадирует: таблицы API (`app_sessions` и др.) перечислены явно; мёртвые строки убирает autovacuum (если его держит забытая «idle in transaction» сессия, сброс замедляется в разы — так было найдено зависание пула ниже).
- Тестовые часы: смещение «сейчас» сервисов (`ctx.now()` API, тайм-ауты BFF, шаги входа, воркер); Supabase Auth и сроки токенов — по реальному времени. SQL-функции с `now()`/`current_date` (видимость пациента клиникой по открытому визиту, закрепление ассистанса на дату) смещение не видят: спецификации e2e, двигающие время, их не затрагивают; если понадобится — `app.now()` из настройки транзакции.
- e2e против бэкенда: `E2E_BACKEND=1` в `playwright.config.ts` запускает API (`APP_ENV=ci`, `LOG_LEVEL=warn` — в выводе только сбои) и сборку с `VITE_USE_MOCKS=false VITE_DEMO_MODE=true` за `vite preview` с прокси `/api` (`API_PROXY` в `vite.config.ts`) — один origin, cookie `__Host-mig_session` первой стороны (Chromium принимает `Secure` на localhost). Фикстура `e2e/test.ts` (все спецификации импортируют `test` из неё) перед каждым тестом возвращает часы, выключает сбои и сбрасывает базу с `xss: true`; `fastForward()` двигает часы страницы и сервера. Тесты делят одну базу, поэтому в бэкенд-прогоне один воркер, а CI делит набор на 8 шардов со своим стеком Supabase; итоговая задача `e2e-backend` — одна обязательная проверка.
- `e2e/helpers.ts` `api()` ходит из страницы с cookie и CSRF-заголовком (в обоих режимах), сессию из `sessionStorage` больше не читает.
- Ошибки, найденные прогоном e2e против бэкенда (исправлены в коде, тесты не ослаблялись):
  - взаимоблокировки Postgres между параллельными запросами одной сессии и выходом: активность сессии писалась в транзакции запроса (`app_sessions`, затем `sessions`), а выход удаляет `sessions` → `app_sessions` каскадом; теперь активность (и смена роли) пишется одним коротким запросом вне транзакции, исчезнувшая строка — 401, а не 500;
  - исчерпание пула соединений: запросы, держащие все 10 соединений транзакциями, ждали одиннадцатое для записи вне транзакции (активность, токены, синхронизация учётной записи) — у этих записей теперь свой пул на 4 соединения (`assemble.ts`);
  - сравнение настроек ИИ через `JSON.stringify` зависело от порядка ключей (`jsonb` хранит свой) — «Отключить ИИ везде» становился предложением на второе подтверждение; сравнения JSON в сервисах — `sameJson`/`canonicalJson` (`lib/json.ts`; также проверка «устаревших» настроек, пересчёт счёта ассистанса, изменённые параметры договора);
  - откат пакета переноса: поле, которого у клиента не было, в сохранённом JSON отсутствует, а не `undefined`, — `activePolicyId` не возвращался, внешний ключ `clients.active_policy_id` падал при фиксации; поля восстанавливаются по списку, клиенты пакета отпускают его полисы до их удаления;
  - места, где сервис читал строки, скрытые RLS от роли (в моке видно всё), — новые места `ctx.system` с причиной: контекст проверки покрытия ИИ (полис, программа, лимиты; клиника его не читает), расчёт лимитов `limitsFor` (заявки, ГП, строки реестров семьи — застрахованному, HR и ассистансу видны только суммы), пациент и период полиса в строках реестра клиники (после закрытия визита клиника пациента не видит), ГП, которое ассистанс запрашивает в клинике направления (строка клиники), код карты члена семьи (`card_tokens` по RLS — только свой), сверка, список договоров и блокировки отката пакета переноса;
  - напоминание о сроке запроса уходило дважды: параллельные запросы (колокольчик, «Мои запросы») оба видели флаг `overdueSent`/`dueSoonSent` снятым; теперь флаг «захватывается» условным `updateWhere` (Postgres перепроверяет условие после фиксации соседа), напоминание шлёт только захвативший;
  - HR не мог загрузить приложение 2 к черновику договора по запросу МИГ («Запросить у HR»): черновик скрыт от HR политикой RLS; после проверок сервиса (своя компания, открытая задача) запись делает система (`ctx.system`);

В тестовом режиме `000000` недемо-телефона заменяется кодом, который получил hook «Send SMS» (`TestPhoneCodes`, только вне production), — e2e входит новым застрахованным; API e2e слушает 8787 на всех интерфейсах, чтобы hook из Docker до него доходил.

Seed считает месяцы через `monthStartTz` (`lib/time.ts`) и дни через `isoDay`, тесты мока — «сегодня» по Ташкенту.
- Ни одна спецификация не исключена из бэкенд-прогона. Две спецификации стали устойчивее к медленному API, без ослабления проверок: split-view меряет карточку, когда она перестала двигаться (анимация въезда), тест тайм-аута неактивности ждёт окончания загрузки страницы перед сдвигом часов.

## Сокращение привилегированного доступа (RLS)

- Обход RLS из обработчиков запросов сведён к перечню `docs/PRIVILEGED_AUDIT.md`: 63 вызова `systemRepos`/`asSystem` в домене → 15, все в разрешённых модулях (`services/system/`, перенос портфеля, демо-маршрут); 49 мест работают от имени пользователя, ещё в одном системным осталось только сохранение пересчёта.
- Где роль законно видит данные на экране, доступ выражен политикой RLS в `schema.ts` (генерируются `npm run db:gen` вместе с тестами pgTAP), а не системными репозиториями: так правило видно в `docs/backend/RLS.md` и проверяется матрицей pgTAP.
- Где роль должна узнать факт о чужих строках (число, сумму, код, занят ли слот, существует ли файл) или оставить след в чужой ленте, используется узкая функция `app.fact_*`: SECURITY DEFINER, `search_path = ''`, сама проверяет `app.active()` и право или область, возвращает только значение; в репозиториях — `Repos.facts` с двойником на TypeScript для мока и системного контекста, совпадение двойников проверяет тест соответствия.
- Функции фактов возвращают минимальные строки в порядке хранения, а выбор, сортировку и арифметику оставляют сервису; где важны только итоги (лимиты, KPI, счётчики стола ассистанса, отчёт), суммы считает SQL, а округление и доли — сервис, так что ответ мока и API совпадают до знака.
- Записи в чужую ленту или журнал: INSERT-политика с условием, привязывающим строку к тому, с чем человек вправе работать (`deal_events` для HR — сделка своей компании через `app.client_of_deal`), а где нужна ещё и обрезка или обновление чужой строки — узкая функция (`app.fact_push_clinic_event`, `app.fact_append_client_log`, `app.fact_advance_deal` — только вперёд по воронке).
- Ленивые «часы» (истечение ГП, статус счёта, ЭДО и вступление договора, пересчёт счёта ассистанса, ежемесячная выборка контроля качества) остаются системными как задачи при чтении и живут в `services/system/clocks.ts`; истечение писем пула лимитов делает сама `app.fact_limit_sums`.
- Последствия действия одной роли в строках других (подпись — счета и вступление в силу, закрытие запросов к другим ролям, сделка продления) остаются системными в `services/system/consequences.ts`: узкая функция повторила бы машину состояний договора, а очередь изменила бы ответ запроса.
- Исходящие вебхуки остаются системными (`services/system/outbox.ts`): подпись требует секрета партнёра, недоступного людям.
- Область ассистанса домена (назначение на дату события, 12 месяцев только чтения бывшему) перенесена в RLS (`app.assist_access`, `app.assist_scope`, «сегодня» — по Ташкенту): раньше бывший ассистанс в Postgres не видел человека и полис, а карточка падала.
- Генератор политик допускает для группы ролей несколько областей с разными действиями-воротами (`staff: [ALL, always(…)]`): так сотрудникам МИГ без доступа к таблице открыты только строки, которые показывает карточка партнёра (случаи, требующие внимания; счета ассистанса, кроме черновиков).
- Занятость слота клиники проверяется по всем записям (`app.fact_taken_slots`, только время): под RLS застрахованный видел только свои записи и мог записаться на занятое время.
- ESLint (`no-restricted-syntax`) запрещает `systemRepos(`, `asSystem(`, `.privileged(`, `.system(` и `privileged: true` в `packages/domain/src` и `apps/api/src`, кроме списка `PRIVILEGED_ALLOWLIST` в `eslint.config.js`; новое место требует строки в этом списке и в `docs/PRIVILEGED_AUDIT.md`.
- Партнёрский API остаётся на системных репозиториях до отдельной роли ключа в матрице прав (этап 2, вместе с OAuth-партнёрами).
- Свободные слоты клиники и проверка при записи читают записи клиники через `systemRepos` (все записи, кто бы их ни сделал): под RLS застрахованный и сотрудник видят только часть записей, и чужая запись не занимала слот — можно было записаться дважды на одно время. Портал клиники видит все записи своей клиники и читает как раньше.
- Тестовый код TOTP `000000`, демо-факторы, «Войти как…» и `000000` для SMS-кода — только при `ALLOW_TEST_TOTP=true` (по умолчанию выключено, в том числе в development/ci/staging); при `APP_ENV=production` или `NODE_ENV=production` API с флагом не стартует. В docker-compose `NODE_ENV` по умолчанию `production`, staging с демо-входом задаёт `NODE_ENV=staging`. Демо-маршруты (`/__demo/*`) по-прежнему включаются `APP_ENV` ≠ production.
- Объекты Storage удаляются вместе со строкой файла: триггер на `public.files` (удаление, каскад, откат переноса, замена объекта) ставит объект в очередь `app.storage_gc`, фоновый обработчик API удаляет его на каждом проходе (`apps/api/src/files/gc.ts`); раз в сутки — сборщик «осиротевших» объектов (старше суток, без строки), итог пишется в журнал (`storage gc: orphan sweep`). Объект, на который снова указывает строка, не удаляется. Демо-сброс идёт без триггеров: его объекты подбирает суточный сборщик.
- Серверное перекодирование изображений — `sharp` 0.35 (libvips, новая зависимость `@mig/api`): без библиотеки на сервере изображение не декодировать и не нарисовать заново, а в браузере canvas уже есть. JPEG и WebP → JPEG 85, PNG → PNG, длинная сторона до 2 000 px, ориентация камеры применяется, метаданные и хвостовые байты не сохраняются, «бомбы» отсекаются лимитом 50 Мп; файл, который не декодируется, — 422. В мок-режиме кодека нет: метаданные только вырезаются (`cleanFile` в `services/uploads.ts`). `sharp` вынесен из бандла API (нативный модуль).
- Общее состояние реплик API — в Postgres: демо-переключатели ci/staging (`app.demo_state`: имитация сбоев и смещение тестовых часов, читаются в начале каждого запроса) и коды SMS тестового режима (`app.test_phone_codes`, пять минут, один раз). Состояние входа (шаг TOTP/SMS) и сессии уже были в Postgres (`app_auth_challenges`, `app_sessions`). В памяти процесса остаются только кэши без влияния на ответы (справка, ключи JWT).
- e2e против бэкенда в CI идут с двумя репликами API (`E2E_API_REPLICAS=2`) за круговым балансировщиком `scripts/e2e-api-lb.mjs` (только для тестов; в развёртывании — Caddy и `API_REPLICAS`).
