# ТЗ: жизненный цикл договора ДМС и урегулирование убытков

Версия 1.0 · 02.10.2026. Дополняет `docs/SPEC.md`, `KP_SPEC.md`, `CLINIC_SPEC.md`, `ASSISTANCE_SPEC.md`. Правила из `CLAUDE.md` действуют полностью. Все числовые правила и пороги — в экране «Параметры ДМС» с пометкой «демо-значение».

## 1. Цель

Сейчас клиент в системе просто существует с активным полисом. Нужно провести его по всему пути:

```
Лид → Данные для оценки → Котировка → КП → Договор → Подписание → Оплата → Полис и сертификаты
     → Сопровождение (доп. соглашения) → Продление или расторжение
```

Плюс выделить урегулирование убытков в отдельную роль и разделить продажи и андеррайтинг.

## 2. Новые роли и полномочия

| Роль | Кто | Что делает |
|---|---|---|
| `sales_manager` | менеджер по продажам (аккаунт-менеджер) | лиды, сделки, сбор данных, отправка КП и договоров, контроль подписания и оплаты, формирование доп. соглашений |
| `legal` | юрист МИГ | согласование договоров и доп. соглашений с изменёнными пунктами |
| `claims_officer` | специалист по урегулированию убытков | решения по убыткам, проверка строк счетов ассистансов, резервы, признаки мошенничества, апелляции |

Изменения существующих ролей:
- `underwriter` больше не ведёт продажу. Он считает и утверждает котировки, утверждает финансовые условия договора и доп. соглашений.
- `operator` (куратор ДМС) оставляет за собой сервис и KPI ассистансов, а **проверка строк счетов ассистансов переходит к `claims_officer`**. Правило четырёх глаз сохраняется: принял `claims_officer`, оплатил `accountant`.
- `doctor_expert` даёт медицинское заключение, а решение по убытку выносит `claims_officer`.

**Полномочия на уровне сотрудника.** В профиле `StaffUser` появляются:

```ts
authority: {
  quoteDiscountMaxPct?: number;    // максимальная скидка от тарифа без согласования
  quotePremiumMax?: Money;         // максимальная годовая премия котировки без согласования
  claimDecisionMax?: Money;        // максимальная сумма решения по убытку без согласования
};
signatory?: { canSign: true; basis: string };   // «Доверенность № … от …»
```

- Если действие выходит за полномочия сотрудника, оно уходит на согласование сотруднику той же роли с бо́льшими полномочиями.
- Полномочия и признак подписанта меняет `admin`, изменение подтверждает второй пользователь (как в «Параметрах ДМС»), всё пишется в аудит.

## 3. Сделка

```ts
export type DealStage =
  | 'lead' | 'census' | 'quote' | 'kp_sent' | 'kp_accepted'
  | 'contract_draft' | 'contract_review' | 'contract_sent' | 'signing'
  | 'awaiting_payment' | 'active' | 'lost';

export interface Deal {
  id: UUID;
  number: string;                  // 'СД-2026-000045'
  clientId: UUID;
  type: 'new' | 'renewal';
  stage: DealStage;
  ownerId: UUID;                   // sales_manager
  underwriterId?: UUID;
  expectedStart?: ISODate;
  lostReason?: string;
  previousPolicyId?: UUID;         // для продления
  createdAt: ISODateTime;
  updatedAt: ISODateTime;
}
```

- `ClientStatus` дополни значением `'lead'`. Новый клиент создаётся как лид: название, ИНН, реквизиты (банк, р/с, МФО, руководитель, основание полномочий), контакт, ориентировочная численность, текущий страховщик.
- Продление из КП (KP_SPEC) теперь создаёт сделку типа `renewal`.
- **Экран `/staff/deals`** — воронка: доска по этапам (как вариант C из прототипа дизайна) и переключатель «Таблица». Фильтры по менеджеру и типу. В колонках — число сделок и сумма премий.
- **Экран `/staff/deals/:id`** — карточка сделки. Вверху шаги этапов, текущий выделен, пройденные отмечены. Ниже панель текущего этапа с действиями, документы сделки и лента событий. С любого этапа можно отметить «Сделка проиграна» с причиной.

## 4. Данные для оценки

- `/staff/deals/:id/census`: загрузка CSV со столбцами пол, год рождения, тип (`employee`, `spouse`, `child`). Шаблон скачивается там же.
- Имена, ПИНФЛ и телефоны на этом этапе **не принимаются**. Если в файле есть такие столбцы, они отбрасываются с предупреждением.
- После загрузки показываются: распределение по возрастным группам (график), доли мужчин и женщин, число сотрудников и членов семей, средний возраст.

```ts
export interface Census {
  id: UUID;
  dealId: UUID;
  rows: { gender: 'm' | 'f'; birthYear: number; relation: 'employee' | 'spouse' | 'child' }[];
  uploadedAt: ISODateTime;
}
```

## 5. Котировка

- `/staff/quotes/:id` — калькулятор андеррайтера:
  - программа;
  - таблица возрастных групп с базовыми ставками и коэффициентами (демо-тариф из «Параметров ДМС»: базовая ставка по программе, коэффициенты по группам 0–17, 18–29, 30–39, 40–49, 50–59, 60+, скидка за размер группы);
  - ручные надбавки и скидки с обязательным комментарием;
  - итог: премия за сотрудника, за члена семьи, общая.
- Если скидка или премия выше полномочий андеррайтера, котировка уходит на согласование (`pending_approval`) пользователю с бо́льшими полномочиями.
- **КП можно отправить только по утверждённой котировке.** Параметры КП берутся из котировки.

```ts
export interface Quote {

  adjustments: { label: string; pct: number; comment: string }[];
  premiumEmployee: Money;
  premiumFamily: Money;
  total: Money;
  discountFromTariffPct: number;
  status: 'draft' | 'pending_approval' | 'approved' | 'rejected';
  approvals: { byId: UUID; byName: string; at: ISODateTime; comment?: string }[];
  createdById: UUID;
}
```

## 6. КП: дополнения

- Статусы КП дополни значениями `accepted` и `declined`.
- В кабинете HR у отправленного КП появляются кнопки «Принять» и «Отклонить» (с причиной). Менеджер тоже может отметить решение клиента вручную, например, если клиент ответил письмом.
- Когда КП принято, сделка переходит на этап `kp_accepted`, и появляется кнопка «Подготовить договор».

## 7. Договор

### 7.1 Шаблоны-заглушки
Текстов МИГ пока нет. Сделай **шаблоны-заглушки** так, чтобы потом заменить только текст:

- `src/features/documents/templates/contract.ts` — договор ДМС;
- `endorsement.ts` — дополнительное соглашение;
- `certificate.ts` — сертификат застрахованного;
- `claimDecisionLetter.ts` — письмо застрахованному о решении по убытку.

Требования к заглушкам:
- Структура реального документа: разделы и пункты с **идентификаторами** (`1.1`, `4.3`…) и правдоподобными, но явно условными заголовками.
- Текст пунктов — короткая заглушка «[Текст пункта 4.3 будет предоставлен МИГ]».
- Подставляемые поля в формате `{{client.name}}`, `{{contract.number}}`, `{{premium.total}}`.
- На каждой странице водяной знак «ШАБЛОН-ЗАГЛУШКА».
- Флаг `approved: false`. Тест хэша (как в KP_SPEC) применяется только к шаблонам с `approved: true`.
- Отдельный файл `docs/TEMPLATES.md`: список всех шаблонов, разделов, пунктов и полей с описанием, откуда берётся значение. Когда МИГ даст тексты, их можно будет просто вставить.

Рендер, экранирование, показ в изолированном iframe и печать в PDF — **ровно как у КП** (KP_SPEC §3 и §6). Используй общий модуль `src/features/documents/`, и КП тоже переведи на него.

### 7.2 Состав договора
- Основной текст: стороны и реквизиты из карточки клиента, подписанты, срок, порядок вступления в силу, премия.
- Приложение 1 — программа страхования (из программы котировки).
- Приложение 2 — список застрахованных, загружается HR или менеджером в формате HR-импорта.
- Приложение 3 — график платежей: единовременно, поквартально или помесячно, с датами и суммами.
- Ссылка на правила страхования.
- Параметр `activationRule`: `on_start_date` (с даты начала) или `after_first_payment` (с даты начала, но не раньше оплаты первого взноса).

### 7.3 Изменение пунктов
- В редакторе договора у каждого пункта есть кнопка «Изменить формулировку». Изменённый пункт подсвечивается, а рядом показывается исходный текст.
- Если изменён хотя бы один пункт, договор **обязательно проходит согласование юриста** (`legal`): одобрить или вернуть с комментарием. Без изменений этап юриста пропускается.
- Финансовые условия (премия, график, скидки) утверждает андеррайтер, если они отличаются от утверждённой котировки.

### 7.4 Экран `/staff/contracts/:id`
- Слева форма параметров и список пунктов с возможностью правки.
- Справа предпросмотр всех страниц.
- Сверху статус, версия и действия:
  - «Отправить на согласование»;
  - «Отправить клиенту»;
  - «Скачать PDF»;
  - «Новая версия» (у отправленного договора).
- История версий с указанием, что изменилось.


## 8. Подписание — все способы

Подписание отслеживается **отдельно для каждой стороны** (МИГ и клиент). Способы можно комбинировать: например, клиент подписал сканом сейчас, а оригинал пришлёт позже.

```ts
export type SignMethod = 'eimzo' | 'edo' | 'paper' | 'scan';

export interface SideSignature {
  method: SignMethod;
  signedAt: ISODateTime;
  signerName: string;
  certificate?: { serial: string; owner: string; validTo: ISODate };  // для eimzo/edo
  edoProvider?: string;                     // для edo
  scanFileId?: UUID;                        // для scan
  scanVerifiedById?: UUID;                  // кто из МИГ проверил скан
}

export interface Signing {
  mig?: SideSignature;
  client?: SideSignature;
  paperOriginal: {
    required: boolean;
    migCopySentAt?: ISODate;
    clientOriginalReceivedAt?: ISODate;
    receivedById?: UUID;
  };
}
```

1. **ЭЦП (E-IMZO).**
   - Подписант МИГ подписывает в портале, HR клиента — в своём кабинете.
   - В прототипе — имитация: модалка «Выберите ключ ЭЦП» с демо-сертификатом, ввод пароля ключа (любой), в документ записываются данные сертификата. Настоящий E-IMZO работает через локальное приложение на компьютере пользователя и подключается с бэкендом. Опиши это в README.
2. **ЭДО** (Didox и аналоги).
   - Кнопка «Отправить через ЭДО» и выбор оператора из списка.
   - В прототипе через 3 секунды приходит имитация события «подписано клиентом в ЭДО».
3. **Бумага.**
   - «Распечатать два экземпляра» (PDF), затем «Подписано МИГ» и «Отправлено клиенту» с датой.
   - «Оригинал клиента получен» отмечает тот, кто получил: дата, сотрудник.
4. **Скан.**
   - Загрузка скана подписанного документа (PDF, JPEG, PNG до 20 МБ, проверка как в SPEC §9.4) со стороны МИГ или в кабинете HR.
   - Сотрудник МИГ проверяет скан («Скан проверен») — только после этого подпись засчитывается.

Правила:
- Договор считается подписанным, когда засчитаны подписи **обеих сторон** любым способом.
- Если хоть одна сторона подписала бумагой или сканом, автоматически включается `paperOriginal.required`.
- Если оригинал не получен через 30 дней (параметр), в очереди менеджера появляется напоминание. Работу договора это не блокирует.
- Подписать за МИГ может только сотрудник с `signatory.canSign`.

Эти же правила и способы действуют для доп. соглашений и расторжения.

## 9. Оплата и вступление в силу

- После подписания счета формируются автоматически по графику платежей и видны бухгалтеру МИГ и HR клиента.
- Оплату отмечает бухгалтер вручную или через «Загрузить выписку из 1С» (CSV-заглушка: дата, сумма, ИНН плательщика, назначение). Частичная оплата допустима.
- Договор становится `active` по `activationRule`. Сделка переходит в `active`, клиент — в статус `active`.
- Просроченный взнос: напоминание менеджеру и бухгалтеру. Блокировка обслуживания при просрочке — параметр (по умолчанию выключено).

## 10. Выпуск полиса и сертификатов

Когда договор вступает в силу:
1. Создаётся `Policy` (существующий тип) со ссылкой на договор и ассистансом, выбранным в сделке.
2. Из приложения 2 создаются записи `Insured`. Каждому присваивается **номер сертификата** (`СЕРТ-2026-000123-0001`) и формируется сертификат по шаблону-заглушке.
3. Застрахованные получают SMS-приглашения (имитация). Ассистанс получает событие `insured.added` по каждому.
4. HR видит полис, список застрахованных и может скачать сертификаты: по одному или все сразу для печати.
5. В приложении: «Профиль» → «Мой сертификат» (просмотр и скачивание). На карточке для клиники появляется номер сертификата.

```ts
// Policy дополни: contractId: UUID
```

## 11. Сопровождение: дополнительные соглашения

- Изменения, которые делает HR (включение и исключение сотрудников) и МИГ (смена программы, прочие условия), сначала копятся как **заявки на изменение** со своими датами.
- Периодичность доп. соглашения — параметр: `monthly` (одно ДС по итогам месяца) или `per_change` (на каждое изменение).
- Расчёт премии за оставшийся срок:
  - включение: `годовая премия × оставшиеся дни / дни срока договора`;
  - исключение — правило возврата (параметр): `pro_rata`, `pro_rata_minus_claims` (возврат за вычетом выплат по этому застрахованному, не меньше нуля) или `none`. Демо-значение `pro_rata_minus_claims`;
  - смена программы: разница премий за оставшийся срок.
- Начало покрытия нового сотрудника — параметр: `from_hr_request` (с даты заявки HR, по умолчанию, чтобы человек не остался без защиты) или `from_endorsement_signed`.
- Исключённый застрахованный теряет покрытие с даты исключения. Приложение показывает ему «Полис завершён», ассистанс получает `insured.excluded`.
- Документ ДС — по шаблону-заглушке. Согласование юриста нужно только при изменённых пунктах. Подписание — §8. После подписания формируется счёт на доплату или документ на возврат.
- Экраны:
  - `/staff/endorsements` — заявки на изменение и ДС;
  - `/staff/endorsements/:id` — расчёт по каждой строке с формулой, предпросмотр, подписание;
  - в кабинете HR раздел «Изменения и доп. соглашения»: статусы заявок, ДС на подпись, суммы.

```ts
export interface ChangeRequest {
  id: UUID;
  contractId: UUID;
  type: 'add_insured' | 'exclude_insured' | 'change_program' | 'other';
  effectiveDate: ISODate;
  insuredId?: UUID;
  payload: Record<string, unknown>;
  requestedBy: { id: UUID; role: Role };
  status: 'pending' | 'included' | 'cancelled';
  endorsementId?: UUID;
}

export interface Endorsement {
  id: UUID;
  number: string;                  // 'ДС-3 к ДМС-Д-2026-000123'
  contractId: UUID;
  changeRequestIds: UUID[];
  lines: { changeRequestId: UUID; description: string; days: number; amount: Money; formula: string }[];
  total: Money;                    // >0 доплата, <0 возврат
  clauseOverrides: Contract['clauseOverrides'];
  status: 'draft' | 'legal_review' | 'approved' | 'sent' | 'signing' | 'signed';
  signing: Signing;
}
```

## 12. Расторжение и окончание

- **Досрочное расторжение по соглашению сторон.** ДС типа «расторжение» с датой и возвратом по правилу из §11. После подписания полис закрывается, застрахованные деактивируются, ассистанс получает события.
- **Окончание срока.** За 60 дней (параметр) создаётся сделка на продление. В день окончания полис переходит в `expired`, если продление не оформлено.

## 13. Урегулирование убытков (`claims_officer`)

**Рабочее место `/staff/claims`:**
- Вкладки:
  - «Новые»;
  - «На рассмотрении»;
  - «Ждут заключения врача»;
  - «Выше моих полномочий»;
  - «Апелляции» (застрахованный или клиника оспаривает решение, в том числе решение ассистанса);
  - «Строки счетов ассистансов».
- Колонки: номер, застрахованный, клиент, источник, сумма, резерв, срок, флаги мошенничества.

**Карточка убытка, панель решения:**
- «Запросить заключение врача» → `doctor_expert` даёт медицинское заключение (текст и рекомендация), но не решение.
- Решение: одобрить полностью, одобрить частично (сумма) или отказать. Для отказа и частичного одобрения **обязательна ссылка на пункт** из каталога пунктов шаблонов (§7.1) и текст причины.
- Если сумма больше `claimDecisionMax` сотрудника, решение уходит на согласование.
- После решения формируется письмо застрахованному по шаблону-заглушке. В приложении на экране статуса показывается причина простым языком и кнопка «Оспорить».

**Кто обрабатывает возмещения застрахованным** (чеки из приложения):
- для клиентов без ассистанса — `claims_officer`;
- для клиентов с ассистансом — по параметру договора с ассистансом `handlesReimbursements` (по умолчанию `true`: ассистанс рассматривает, выплачивает и перевыставляет МИГ). При `false` возмещения идут `claims_officer`.

**Резервы:**
- У каждого открытого убытка есть резерв заявленного убытка: при создании — заявленная сумма или сумма одобренного ГП; меняется при решении; обнуляется при оплате, отказе или закрытии. История изменений с автором.
- Отчёт `/staff/reports/reserves`: резерв заявленных, но неурегулированных убытков на выбранную дату, в разрезе клиентов, ассистансов и категорий, с выгрузкой CSV. Резерв произошедших, но незаявленных убытков (IBNR) — актуарная задача, она вне прототипа, отметь это в README.

**Признаки мошенничества** (флаги, не автоматический отказ):
- повтор чека (та же сумма, дата и аптека или клиника, либо совпадение хэша изображения);
- больше N обращений в месяц (параметр);
- дата услуги до начала покрытия или после исключения;
- обращения в последние дни перед исключением;
- сумма чека заметно выше прайса.

Флаги видны в списке и в карточке с объяснением. Снять флаг можно только с комментарием.

**Журнал убытков** — выгрузка CSV для отчётности, без ПИНФЛ и телефонов.

## 16. Seed

- 2 лида.
- 4 сделки на разных этапах: котировка на согласовании; КП отправлено; договор у юриста с изменённым пунктом; подписание (МИГ подписал ЭЦП, клиент прислал скан, оригинал ещё не получен).
- Один активный договор с двумя ДС (одно подписано, одно на подписании) и накопленными заявками HR на текущий месяц.
- 30 убытков для `claims_officer`:
  - 5 выше полномочий `claims@`;
  - 4 с флагами мошенничества;
  - 2 апелляции;
  - 3 ждут заключения врача.
- Компания демо-HR видит своё КП к продлению (можно принять) и ДС на подпись.

## 17. Тесты

**Юнит:**
- демо-тариф и котировка;
- маршрутизация по полномочиям;
- расчёт за оставшийся срок для всех типов изменений и трёх правил возврата;
- `activationRule`;
- правила подписания (обе стороны, автоматическое включение оригинала, только подписант);
- резервы;
- все флаги мошенничества;
- новые ячейки матрицы.

**E2E:**
1. Полный путь нового клиента. Менеджер создаёт лид и загружает данные. Андеррайтер считает котировку со скидкой выше своих полномочий, руководитель андеррайтинга утверждает. Менеджер отправляет КП, HR принимает. Менеджер готовит договор и меняет пункт, юрист одобряет. Подписант МИГ подписывает ЭЦП, HR — ЭЦП. Бухгалтер отмечает оплату, полис активен, сертификаты сформированы. Застрахованный видит сертификат в приложении.
2. Бумажный путь: печать, «Подписано МИГ», скан клиента, проверка скана, договор подписан, оригинал отмечен как полученный.
3. ЭДО: отправка, событие подписания, договор подписан.
4. HR добавляет сотрудника и исключает другого. В конце месяца формируется ДС с правильными суммами по формулам, подписывается сканом, создаётся счёт. Новый сотрудник видит полис с даты заявки HR.
5. Убыток выше полномочий `claims@` уходит `claims-head@`. Отказ без ссылки на пункт не сохраняется. Застрахованный видит причину и оспаривает её, апелляция появляется во вкладке.
6. Флаг повтора чека: второй такой же чек получает флаг, флаг снимается только с комментарием.
7. Отчёт по резервам на дату совпадает с суммой открытых резервов.
8. Права: менеджер не может утвердить котировку и подписать за МИГ (если не подписант), юрист не видит убытков.
