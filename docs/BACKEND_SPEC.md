# ТЗ: бэкенд, этап 1 — фундамент на self-hosted Supabase

Версия 1.0 · 09.10.2026. Правила из `CLAUDE.md` действуют полностью. Всё, что уже описано в `docs/SPEC.md` и остальных ТЗ как поведение мок-сервера, становится поведением настоящего сервера.

## 1. Цель этапа

Заменить мок-сервер настоящим бэкендом так, чтобы:

- фронтенд работал без изменений экранов, только с `VITE_USE_MOCKS=false`;
- бизнес-логика **не переписывалась**, а переиспользовалась из мока;
- все существующие e2e-тесты проходили против настоящего бэкенда;
- права доступа проверялись дважды: в коде API и в базе через RLS.

**Входит в этап 1:**
- база Postgres;
- авторизация через Supabase Auth;
- хранилище файлов;
- API с тем же контрактом, что у мока;
- RLS и тесты к ним;
- журнал аудита;
- фоновые задачи;
- конфигурация развёртывания и резервного копирования;
- CI.

**Не входит, это этап 2:**
- настоящая отправка SMS — сейчас адаптер с имитацией;
- E-IMZO, ЭДО, 1С, MyID;
- серверная генерация PDF;
- настоящая модель ИИ;
- внешний API для клиник и ассистансов с OAuth;
- антивирусная проверка вложений;
- перенос реальных данных.

## 2. Архитектура

```
Браузер (порталы, приложение)
        │  HTTPS, cookie сессии
        ▼
Caddy (обратный прокси, TLS) ── раздаёт собранный фронтенд и проксирует /api
        │
        ▼
API (Node.js 20, TypeScript, Fastify) ── доменная логика (общая с моком)
        │  запросы к БД от имени пользователя (RLS)
        ▼
Self-hosted Supabase: Postgres 15+, GoTrue (Auth), Storage, pg_cron
```

**Принципы:**
1. **Браузер обращается только к нашему API.** Supabase (PostgREST, Auth, Storage, Studio) наружу не открыт и живёт во внутренней сети Docker. В браузере нет ни anon-ключа, ни service-ключа.
2. **API выполняет запросы к БД от имени пользователя.** Каждый запрос — это транзакция, в которой выставляются `SET LOCAL ROLE authenticated` и `set_config('request.jwt.claims', …, true)` с claims пользователя. Поэтому RLS работает и для запросов API: ошибка в проверке прав в коде не открывает чужие данные.
3. **Сервисная роль** (обход RLS) используется только для миграций, фоновых задач и системных операций (выдача ролей, аудит). Для неё отдельный модуль `systemDb`, импорт которого в обработчики пользовательских запросов запрещён правилом ESLint.
4. **Сессия по модели BFF.** API хранит токены Supabase у себя, а браузер получает только непрозрачную cookie `__Host-mig_session` с флагами `HttpOnly; Secure; SameSite=Strict; Path=/`. Токены в браузере не хранятся вообще.
5. **Все данные — на сервере в Узбекистане.** Фронтенд в рабочей системе раздаётся тем же Caddy с того же сервера.

## 3. Структура репозитория

Перейди на npm workspaces:

```
apps/web/            — текущий фронтенд (переезжает из корня)
apps/api/            — сервер Fastify
packages/domain/     — доменная логика: права, расчёты, проверки, правила (вынести из src/shared и src/mocks)
packages/contracts/  — zod-схемы запросов и ответов, типы (единые для web, api, мока)
packages/seed/       — детерминированный генератор демо-данных (общий для мока и БД)
supabase/            — config.toml, migrations/, seed.sql (генерируется), tests/ (pgTAP)
deploy/              — docker-compose, Caddyfile, скрипты резервного копирования, инструкции
```

- Переезд не должен ломать мок-режим: `npm run dev` с моками работает как раньше, все тесты зелёные.
- CI, Cloudflare-деплой прототипа и скрипты `package.json` обнови под новую структуру. Демо-сайт на Cloudflare продолжает работать с моками.

## 4. Один код — два адаптера

Главное требование этапа: **обработчики не дублируются**.

1. Вынеси логику мок-обработчиков в сервисный слой `packages/domain/services/*`. Это чистые функции вида `(ctx, input) → result | DomainError`, где `ctx` содержит пользователя, время и репозитории.
2. Опиши интерфейсы репозиториев (`ClientRepo`, `PolicyRepo`, `ClaimRepo`, …) и сделай две реализации: `memory` для мока (текущая БД в памяти) и `postgres` для API.
3. **MSW-адаптер** и **Fastify-адаптер** — тонкие: разбирают запрос, вызывают сервис, превращают результат или `DomainError` в HTTP-ответ одного и того же формата.
4. Тест на соответствие: для набора сценариев один и тот же сервис с `memory` и с `postgres` даёт одинаковые ответы.

## 5. База данных

- Схема строится из типов `packages/contracts`: таблицы в `snake_case`, первичные ключи UUID v4, внешние ключи, `NOT NULL` и `CHECK` везде, где тип это подразумевает. Перечисления — Postgres enum или `CHECK`. Деньги хранятся как `bigint` (целые сумы), даты как `date`, моменты времени как `timestamptz`.
- В каждой таблице: `created_at`, `updated_at` (через триггер), `created_by`.
- Миграции — только SQL-файлы в `supabase/migrations/`, по одной на логическое изменение. Ручных изменений в базе нет.
- **Шифрование персональных данных на уровне приложения:**
  - ПИНФЛ и телефон хранятся зашифрованными (AES-256-GCM в API, ключ из секрета окружения, с версией ключа для ротации);
  - для поиска рядом хранится HMAC-хэш (`pinfl_hmac`, `phone_hmac`) с отдельным ключом;
  - маскированное значение строит API, полное отдаётся только через `reveal` с аудитом, как в моке;
  - свободные тексты медкарты (`summary`) тоже шифруются;
  - номера банковских карт **не хранятся никогда**, только маска и токен банка (на этапе 2).
- Индексы для всех фильтров и сортировок списков из ТЗ. Проверь `EXPLAIN` для основных списков на seed-объёмах.

## 6. RLS

- RLS включён на **всех** таблицах схемы `public`. Тест падает, если найдена таблица без RLS.
- Вспомогательные функции в схеме `app` (`SECURITY DEFINER`, `STABLE`, `search_path` зафиксирован): `app.uid()`, `app.role()`, `app.company_id()`, `app.clinic_id()`, `app.assistance_id()`, `app.insured_id()`, `app.aal()`, `app.can(action text)`.
- Политики повторяют матрицу прав (`packages/domain/permissions`). Отдельно реализуются:
  - **«своё»:** HR — своя компания, клиника — через действующий визит, ассистанс — закрепление на дату события, застрахованный — сам и его дети (взрослые члены семьи — только с согласия);
  - **маскирование:** таблицы с ПДн не отдают зашифрованные поля ролям без права, для списков используются представления (`security_invoker`) только с маскированными колонками.
- **Сотрудники МИГ, клиник и ассистансов** получают доступ к данным, только если `app.aal() = 'aal2'`, то есть пройдён второй фактор.
- **Генерация тестов RLS из матрицы.** Скрипт `scripts/gen-rls-tests.mjs` берёт ту же матрицу прав и генерирует pgTAP-тесты: для каждой роли и таблицы проверяет select, insert, update и delete на «своих» и «чужих» строках. Отдельные тесты на изоляцию HR между компаниями, клиник через визит, ассистансов по дате, семьи по согласию. Запуск — `supabase test db`.

## 7. Авторизация

- **Supabase Auth (GoTrue):**
  - сотрудники, HR, клиники, ассистансы — email и пароль, плюс обязательный TOTP-фактор (MFA Supabase);
  - застрахованные — телефон и одноразовый код.
- **SMS** через Auth Hook «Send SMS» → эндпоинт API → адаптер провайдера. На этапе 1 адаптер `log` пишет код в журнал разработки, а в CI код фиксированный. Интерфейс адаптера готов под местного провайдера.
- **Роли и привязки** (`role`, `company_id`, `clinic_id`, `assistance_id`, `insured_id`) хранятся только в `app_metadata`, их выставляет API сервисной ролью. `user_metadata` для прав не используется никогда. **Custom Access Token Hook** переносит их в claims JWT.
- **Приглашения:** администратор создаёт пользователя через API → `inviteUserByEmail` → письмо через SMTP МИГ (настройки SMTP — из окружения).
- **Сессии BFF** (таблица `app_sessions`):
  - в таблице: хэш идентификатора, пользователь, зашифрованный refresh-токен, время создания, последняя активность, уровень AAL, IP, user-agent;
  - access-токен живёт 10 минут и обновляется сервером;
  - тайм-аут неактивности по ролям (15 и 30 минут) проверяет сервер;
  - фоновые запросы с заголовком `X-Background: 1` активность не продлевают;
  - выход завершает сессию на сервере, «Выйти на всех устройствах» завершает все сессии пользователя.
- **CSRF:** cookie `SameSite=Strict`, а все изменяющие запросы обязаны содержать заголовок `X-Requested-With: mig-web`. Без него ответ 403.
- **Ограничения попыток** входа и проверок по ПИНФЛ — по параметрам ДМС, счётчики на сервере (таблица или Redis не нужен: Postgres с TTL-очисткой через pg_cron).
- Фронтенд: `client.ts` переходит на `credentials: 'include'` и заголовок `X-Requested-With` вместо `Authorization`. Мок эмулирует ту же схему, чтобы оба режима работали одинаково.

## 8. Файлы

- Приватные бакеты Supabase Storage: `receipts`, `contract-scans`, `guarantee-attachments`, `documents`, `help-assets`.
- Загрузка только через API: проверка MIME, магических байтов, размера и количества. Изображения повторно перекодируются на сервере (удаление EXIF — второй уровень защиты после клиента).
- Скачивание: API проверяет права и выдаёт подписанную ссылку на 60 секунд. Имена объектов — UUID, без ПДн.
- Хэш SHA-256 каждого файла сохраняется в метаданных (основа для поиска повторов чеков и целостности сканов).

## 9. Журнал аудита

- Таблица `audit_log` только для добавления: для всех ролей `REVOKE UPDATE, DELETE`, запись — только через функцию `app.audit(...)` (`SECURITY DEFINER`).
- **Цепочка хэшей:** каждая запись хранит хэш предыдущей. Функция `app.verify_audit_chain()` и ежедневная проверка через pg_cron с уведомлением администратору при разрыве.
- Все действия, которые мок пишет в аудит, пишутся и здесь, с теми же типами.

## 10. Фоновые задачи

pg_cron вызывает функции БД или эндпоинты API с системным токеном:
- напоминания о сроках запросов, SLA, КП без ответа, лидах без активности;
- создание сделок на продление за N дней;
- вступление договоров в силу и истечение полисов;
- предельный возраст детей;
- очистка истёкших сессий и счётчиков попыток;
- проверка цепочки аудита.

В моке те же задачи должны вызываться тем же сервисным кодом. Расписания вынеси в один файл.

## 11. Развёртывание

- `deploy/docker-compose.yml`:
  - официальный стек self-hosted Supabase (зафиксированные версии образов);
  - `api`;
  - `caddy`.

  Наружу открыт **только Caddy** на 443 (и 80 для перенаправления). Studio, Postgres и Kong доступны только во внутренней сети или через VPN.
- `deploy/Caddyfile`: TLS, раздача `apps/web/dist`, проксирование `/api`, заголовки безопасности из `public/_headers`, лимиты размера запросов.
- **Два окружения:**
  - `staging` обновляется автоматически при вливании в `main`;
  - `production` — только вручную через GitHub Environments с обязательным подтверждением, с автоматической резервной копией перед миграциями.
- **Два описанных способа доставки:** Coolify и GitHub Actions с self-hosted runner (исходящее соединение, без открытых входящих портов). Оба — в `deploy/README.md`, пошагово для администратора МИГ.
- **Резервные копии:**
  - ежедневно `pg_dump` и копия бакетов Storage в отдельное хранилище;
  - хранение 30 дневных и 12 месячных копий;
  - скрипт восстановления на чистый сервер и ежемесячная проверка восстановления на staging (инструкция и скрипт).
- **Секреты** только в переменных окружения сервера: ключи Supabase, JWT secret, ключи шифрования ПДн и HMAC, SMTP, секрет сессий. `deploy/.env.example` без значений. Ротация каждого секрета описана в `deploy/README.md`.

## 12. Тесты и CI

Новые задачи в CI (GitHub Actions на `ubuntu-latest`, там есть Docker):
1. `supabase start` (Supabase CLI) → применение миграций → `supabase test db` (pgTAP, включая сгенерированные RLS-тесты).
2. Интеграционные тесты API (Vitest) против этой базы: сервисы, адаптер Fastify, сессии, CSRF, шифрование, аудит, файлы.
3. **Весь существующий набор e2e против настоящего бэкенда:** сборка фронтенда с `VITE_USE_MOCKS=false`, API и Supabase из CI, seed из `packages/seed`. Отдельная задача `e2e-backend`, обязательная для вливания. Тесты, которые полагаются на демо-функции мока («Имитировать сбои сети», «Войти как…»), получают серверные аналоги только в окружении `staging` и `ci`, а в `production` эти эндпоинты отсутствуют (проверяется тестом).
4. Тест соответствия мок ↔ postgres из §4.

Если в твоей среде нет Docker, ставь PostgreSQL и Supabase CLI другим способом или опирайся на CI. Но перед вливанием всё должно быть зелёным именно в CI.

## 13. Порядок работы

Этот этап большой. Делай его серией PR, каждый — зелёный и влитый, прежде чем начинать следующий:

1. Переход на workspaces и вынос `packages/domain`, `contracts`, `seed`. Мок-режим работает как раньше.
2. Сервисный слой и интерфейсы репозиториев; MSW-адаптер переходит на них. Мок работает как раньше.
3. Миграции схемы, RLS, генерация pgTAP-тестов, CI с Supabase CLI.
4. API на Fastify: репозитории postgres, сессии BFF, CSRF, шифрование ПДн, аудит, файлы, фоновые задачи. Интеграционные тесты.
5. Фронтенд на cookie-сессии в обоих режимах; задача `e2e-backend` в CI зелёная.
6. Развёртывание: docker-compose, Caddy, резервное копирование, `deploy/README.md`, workflow для staging и production.

После каждого PR обновляй README и DECISIONS. В конце этапа пришли отчёт:
- что сделано;
- что упрощено;
- список того, что нужно от администратора МИГ для первого запуска на staging-сервере;
- оценка нагрузки и рекомендуемая конфигурация сервера по результатам прогонов на seed-объёмах.
