# Нагрузка на seed-объёмах и рекомендуемый сервер

Шаг 6 BACKEND_SPEC (§13, отчёт этапа): замеры развёрнутого стека и рекомендация по серверу. Замеры повторяются
`scripts/loadtest.mjs` (без зависимостей: Node `fetch`, замкнутый цикл виртуальных пользователей).

## Как мерили

- **Стек** — `deploy/docker-compose.yml` целиком (как на сервере): Caddy с TLS → API (контейнер, Node 20) → self-hosted
  Supabase (Postgres 15.19, GoTrue, Storage, Kong) в режиме `APP_ENV=staging` (нужны демо-вход «Войти как…» и
  демо-данные), запросы идут через `https://localhost:9443` (Caddy, HTTP/1.1 + TLS), как у браузера.
- **Данные** — демо-seed (тот же, что в CI): 1 547 застрахованных, 626 убытков, 683 файла, 333 записи, 49 клиентов,
  34 полиса, ~1 580 пользователей Supabase Auth, журнал аудита ~500–1 300 записей; база ~31 МБ.
- **Пользователи** — 12 учётных записей по кругу: оператор, андеррайтер, урегулирование, бухгалтер, продажи,
  врач-эксперт, администратор, юрист, HR, регистратура клиники, оператор ассистанса, застрахованный. Каждый
  виртуальный пользователь входит настоящим входом (Supabase Auth, BFF-cookie; не больше 3 сессий на учётную
  запись, на телефон — одна: код SMS раз в минуту) и по кругу открывает рабочий стол, очередь, списки и карточки
  своей роли (id карточек — из списков) и делает записи: раскрытие ПДн с причиной (запись в аудит с цепочкой
  хэшей), сообщение в чат застрахованного, «прочитать уведомления».
- **Режимы**: без пауз между запросами (`--think 0`: насыщение — это не «100 человек», а 100 непрерывных потоков
  запросов) и с паузой ~3 с (0,5–1,5 × 3 с) — ближе к людям, хотя люди делают паузы ещё длиннее.
- **Ресурсы** — `docker stats` каждые ~2 с (CPU в % одного ядра, память — пик).
- **Машина** — честно: 4 vCPU Intel Xeon 2,1 ГГц (общие, облачная ВМ), 15 ГБ RAM. На ней же работали генератор
  нагрузки (Node, ~0,3 ядра) и простаивающий локальный стек Supabase CLI. Числа — нижняя оценка для выделенного
  сервера; разброс между прогонами ±10–15 %.

```
node scripts/loadtest.mjs --base https://staging.dms.mig.uz --users 10,50,100 --duration 60
node scripts/loadtest.mjs --base https://staging.dms.mig.uz --users 100 --think 3000 --duration 90 --no-phones
```

### Что видно

1. **Узкое место — CPU процесса API.** Один контейнер Node упирается в одно ядро (~115–125 % вместе с GC) на ~50
   запросах в секунду; дальше растёт только очередь (p50 0,12 → 2 с). Сервисы считают ответы в JS над строками
   репозиториев (тот же код, что у мока), поэтому API тратит CPU больше, чем Postgres.
2. **API масштабируется горизонтально**: 3 контейнера (`docker compose up -d --scale api=3`, Caddy балансирует сам)
   дали 85 RPS (+60 %) и вдвое меньшую задержку на 10 пользователях; дальше упёрлась вся машина (4 vCPU:
   ~2,1 ядра API + 1,3 Postgres + генератор). На сервере с бо́льшим числом ядер рост продолжится до Postgres.
3. **С паузами ~3 с** 100 пользователей дают 32 RPS при p50 37 мс и p95 0,32 с, машина загружена на ~треть.
4. Самые тяжёлые запросы (p50 на 10 пользователях, 1 контейнер): `GET /hr/employees` 1,7 с, `GET /contracts` 0,9 с,
   `GET /clients` 0,9 с, `GET /policies` 0,67 с, `GET /deals` 0,66 с, кабинет ассистанса (`/assist/overview`,
   `/assist/appointments`, `/assist/insured`). Это те же последовательные запросы «на каждую строку», что были в
   рабочем столе оператора, — следующие кандидаты на пакетное чтение (ниже).
5. Записи дешёвые: `POST /insured/:id/reveal` (аудит с цепочкой хэшей под advisory-lock) p50 87 мс, p95 169 мс на
   10 пользователях; конфликтов блокировок не было.

### Рабочий стол оператора (`GET /api/dashboard`)

Было: для каждого из 1 547 застрахованных отдельный запрос назначений ассистанса и для каждой заявки — запрос
клиники. Стало: назначения и клиники читаются один раз на очередь (`packages/domain/src/services/dashboard.ts`,
`isOverdueRequestOf` в `services/clinic.ts`), ответы прежние (тест соответствия мок ↔ postgres).

| Замер (оператор, 3 запроса подряд, через Caddy, один и тот же стек) | до                       | после              |
| ------------------------------------------------------------------- | ------------------------ | ------------------ |
| `GET /api/dashboard`                                                | 1 619 / 1 301 / 1 074 мс | 279 / 159 / 132 мс |
| то же на локальном API при параллельном e2e-прогоне на машине       | 2 912 / 1 951 / 1 914 мс | 188 / 132 / 126 мс |

Остальные роли не изменились (андеррайтер ~170 мс, продажи ~180 мс, остальные 30–90 мс).

## Оценка пользователей

Человек в портале делает в среднем один запрос в 5–10 с (открытие экрана — 3–6 запросов, затем чтение и ввод
десятки секунд); приложение застрахованного — реже. Это 0,1–0,2 RPS на **одновременно активного** пользователя.

- 4 vCPU (как тестовая машина, 3 контейнера API): 85 RPS на пределе; держать нагрузку ≤ 50 % (p95 < 0,5 с) →
  ~40 RPS → **200–400 одновременно активных** пользователей.
- 8 vCPU (рекомендация ниже, 4–5 контейнеров API): экстраполяция ~2× → **400–800 одновременно активных**; это
  десятки сотрудников МИГ, сотни HR и регистратур, тысячи зарегистрированных застрахованных (из которых
  одновременно активны единицы процентов). Экстраполяция линейная и проверена только до 4 vCPU — её нужно
  подтвердить тем же скриптом на staging-сервере.

**Главная оговорка — объём данных.** Замер — на seed (1,5 тыс. застрахованных). Многие списки сейчас читают таблицу
целиком и фильтруют/сортируют в сервисе (общий код с моком). На реальном портфеле (десятки тысяч застрахованных,
сотни тысяч убытков и записей аудита) время этих запросов растёт линейно с таблицей, и мощность сервера это не
исправит. До переноса реального портфеля нужно перевести тяжёлые списки (п. 4 выше, а также `/insured`, `/claims`,
`/audit`) на фильтрацию, сортировку и пагинацию в SQL и прогнать `loadtest.mjs` на данных реального объёма
(сгенерированных, не настоящих).

## Рекомендуемый сервер

|                | staging                                                                                                    | production                                                                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| CPU            | 4 vCPU                                                                                                     | **8 vCPU** (выделенные, не burstable)                                                                 |
| RAM            | 8 ГБ                                                                                                       | **16 ГБ**                                                                                             |
| Диск           | 80 ГБ SSD                                                                                                  | **200 ГБ NVMe SSD** + отдельное хранилище копий (S3/второй сервер) ≥ 2 × объём данных × срок хранения |
| Контейнеры API | 1 (демо-коды SMS ловит сам процесс API — с несколькими контейнерами вход по телефону на staging ненадёжен) | 4 (`--scale api=4`), воркер — 1                                                                       |

Распределение production (8 vCPU / 16 ГБ): API 4 × (1 ядро, ~350 МБ) ≈ 4 ядра и 1,5 ГБ; Postgres 2–3 ядра и 6–8 ГБ
(`shared_buffers` 4 ГБ, `effective_cache_size` 10 ГБ, `work_mem` 16 МБ, `max_connections` 200 — пулы API по 10
соединений); Supabase Auth, Storage, Kong, PostgREST, Caddy вместе < 1 ядра и ~1 ГБ; остальное — кэш ОС.
`DB_POOL_SIZE` × число контейнеров API должно быть меньше `max_connections` с запасом для Auth, Storage и
резервного копирования.

Диск: база на seed — 31 МБ; на реальном портфеле основное место займут файлы Storage (фото чеков, сканы
договоров — сотни КБ–единицы МБ каждый, 10–100 ГБ в год в зависимости от доли возмещений) и локальные копии
(30 дневных + 12 месячных; файлы Storage в копиях не сжимаются). Начать с 200 ГБ и следить за заполнением
(`deploy/README.md` §11), расширение тома — без простоя у большинства облаков.
