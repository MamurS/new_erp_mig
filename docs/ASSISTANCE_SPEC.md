# ТЗ: ассистанс-компании

Версия 1.0 · 30.09.2026. Дополняет `docs/SPEC.md`, `docs/KP_SPEC.md` и **меняет часть процессов** из `docs/CLINIC_SPEC.md` (§9 ниже). Правила из `CLAUDE.md` действуют полностью.

## 1. Как устроена работа

МИГ сотрудничает с несколькими ассистанс-компаниями. Каждая обслуживает **своих клиентов**: полис клиента закреплён за одним ассистансом. Для своих застрахованных ассистанс:

1. ведёт круглосуточный колл-центр и записывает к врачам;
2. выдаёт гарантийные письма и проводит медэкспертизу в пределах своих полномочий;
3. проверяет реестры клиник;
4. **сам оплачивает клиникам** и раз в месяц выставляет МИГ счёт на возмещение: оплаченные суммы плюс вознаграждение ассистанса.

Роль МИГ меняется с исполнителя на **контролёра**:
- андеррайтинг и назначение ассистанса клиенту;
- решения выше полномочий ассистанса;
- выборочный контроль качества;
- проверка и оплата счетов ассистансов;
- обслуживание клиентов без ассистанса (`assistanceId = null`). Такие клиенты допустимы, и все процессы из прошлых ТЗ для них работают как раньше.

Разные ассистансы работают по-разному: одни в нашем кабинете, другие через свою систему по API, третьи совмещают. Используется тот же механизм интеграции, что для клиник (CLINIC_SPEC §6), обобщённый до «партнёра».

## 2. Роли ассистанса

| Роль | Кто | Что делает |
|---|---|---|
| `asst_operator` | оператор колл-центра | обращения, записи, чат с застрахованными, поиск по своим застрахованным |
| `asst_doctor` | врач-эксперт ассистанса | гарантийные письма в пределах полномочий, медэкспертиза строк реестров, медкарта своих застрахованных |
| `asst_billing` | финансист ассистанса | реестры клиник, оплаты клиникам, счета МИГ |
| `asst_admin` | администратор ассистанса | пользователи, интеграция, настройки |

- Каждый пользователь привязан к `assistanceId`.
- MFA обязателен, тайм-аут неактивности 15 минут.
- Портал `/assist` в визуальном режиме `staff`: колл-центру нужен плотный интерфейс. В верхней панели показаны название ассистанса и пометка «Портал партнёра».

**Изменения ролей МИГ:**
- `operator` в интерфейсе теперь называется **«Куратор ДМС»**, код роли не меняется. Занимается контролем ассистансов, эскалациями, жалобами, проверкой счетов ассистансов и полностью обслуживает клиентов без ассистанса.
- `doctor_expert` (МИГ) решает по гарантийным письмам выше полномочий ассистанса и проводит контрольную выборку.
- `accountant` (МИГ) оплачивает счета ассистансов, а клиникам платит напрямую только по клиентам без ассистанса.
- `underwriter` назначает ассистанс клиенту или полису.
- `admin` (МИГ) заводит ассистанс-компании, их договоры, первого `asst_admin` и может отозвать любые ключи API партнёра.

## 3. Закрепление и изоляция данных

- В `Policy` появляется поле `assistanceId: UUID | null` и история закреплений: `AssistanceAssignment[]` с датами действия.
- Смена ассистанса возможна только с указанной даты. Новые обращения с этой даты идут новому ассистансу, а прежний сохраняет **доступ только на чтение** к делам, которые вёл, ещё 12 месяцев (для оспариваний и сверок).
- Ассистанс видит только застрахованных, чей полис закреплён за ним **на дату события**. Всё остальное возвращает 404. Правило проверяется в каждом обработчике мока через `requireAssistanceScope()`.
- В отличие от клиники, ассистанс **может искать** по своим застрахованным (ФИО, номер полиса, телефон): колл-центру это необходимо. ПИНФЛ маскирован, раскрытие по причине с аудитом, как у сотрудников МИГ.
- `asst_doctor` видит медкарту своих застрахованных по причине, с доступом на 15 минут и записью в аудит, как `doctor_expert` МИГ.
- Ассистанс не видит условия договоров и суммы вознаграждения других ассистансов, андеррайтинговые данные, премии и КП.
- Все действия пользователей ассистанса пишутся в общий аудит МИГ. Администратор МИГ видит их с фильтром по ассистансу.

## 4. Договор с ассистансом

```ts
export type FeeModel = 'pepm' | 'percent_of_claims' | 'per_case';

export interface AssistanceCompany {
  id: UUID;
  name: string;
  phone24x7: string;                 // показывается застрахованным
  integrationMode: 'portal' | 'api' | 'hybrid';
  contract: {
    number: string;
    validFrom: ISODate;
    validTo: ISODate;
    feeModel: FeeModel;
    feeValue: number;                // PEPM: сум за застрахованного в месяц; percent: доля 0..1; per_case: сум за обращение
    guaranteeAuthorityLimit: Money;  // ГП до этой суммы ассистанс одобряет сам
    rebillPaymentDays: number;       // срок оплаты счёта МИГ
  };
  kpi?: AssistanceKpi;               // вычисляемое
}

export interface AssistanceKpi {
  appointmentResponseMinutesAvg: number;
  guaranteesOnTimeShare: number;     // доля ГП, решённых в срок
  qaAgreementShare: number;          // доля решений, подтверждённых контрольной выборкой МИГ
  complaintsPer1000: number;
  lossRatio: number | null;          // по портфелю ассистанса
}
```

Демо-значения из seed, которые МИГ заменит реальными:
- полномочия по ГП — 10 000 000 UZS;
- контрольная выборка — 5%;
- срок проверки счёта МИГ — 10 рабочих дней;
- вознаграждение: «[Ассистанс 1]» по PEPM 15 000 UZS, «[Ассистанс 2]» 7% от выплат, «[Ассистанс 3]» 50 000 UZS за обращение.

## 5. Процессы

### 5.1 Обращения и запись
- В приложении застрахованного на главной появляется карточка **«Ваш ассистанс 24/7»**: название и кнопка «Позвонить» (`tel:`).
- Чат из приложения уходит операторам ассистанса. Для клиентов без ассистанса он уходит куратору МИГ, как раньше.
- Заявки на запись видны ассистансу застрахованного. Клиника по-прежнему подтверждает сама (CLINIC_SPEC §4.3). Если клиника не ответила в срок, заявка эскалируется **ассистансу**, а не МИГ.
- Обращения колл-центра (`AssistanceCase`): тип (`appointment`, `consultation`, `guarantee`, `complaint`, `emergency`), статус, SLA, связь с записью, ГП или убытком. Оператор создаёт обращение из звонка, находя застрахованного поиском.
- Жалобы застрахованных на ассистанс видны и куратору МИГ.

### 5.2 Гарантийные письма
- Запрос ГП от клиники (или от оператора ассистанса по звонку) направляется ассистансу застрахованного.
- Если сумма не больше `guaranteeAuthorityLimit`, решает `asst_doctor`.
- Если больше, `asst_doctor` даёт заключение и отправляет на **эскалацию** в МИГ, где решает `doctor_expert`. Правило двух врачей из CLINIC_SPEC §5 действует на уровне МИГ для писем выше порога.
- **Одобренная сумма ГП резервирует лимит** застрахованного. Приложение и проверка покрытия в клинике сразу показывают актуальное состояние лимита.

### 5.3 Реестры клиник
- Клиника отправляет **один реестр в месяц**, как и раньше. Система сама разносит строки по плательщикам: для каждой строки определяется ассистанс полиса на дату услуги, а если его нет — МИГ. Получаются подреестры.
- Клиника видит по каждой строке, кто плательщик, статус проверки и статус оплаты.
- Ассистанс проверяет свои строки: принять, отклонить с причиной, ответить на оспаривание.
- Принятая строка **списывает лимит**, а резерв ГП, если был, снимается.
- Прайс-лист зависит от пары «клиника + плательщик»: `ClinicContract { clinicId, payer: 'mig' | assistanceId, priceList }`. Проверка цены строки идёт по прайсу своего плательщика.

### 5.4 Оплата клиникам
- `asst_billing` отмечает оплату принятых строк: дата, сумма, номер платёжного поручения. Можно отметить весь подреестр сразу или частями.
- Клиника видит «Оплачено ассистансом {название}» с датой.

### 5.5 Счёт на возмещение МИГ (перевыставление)
- Раз в месяц `asst_billing` формирует `Rebill` из строк, **оплаченных клиникам в этом месяце**, и добавляет вознаграждение по модели договора. Сумма считается автоматически и отображается с формулой расчёта.
- Автоматические проверки МИГ по каждой строке, с флагом и объяснением:
  - строка принята и оплачена клинике;
  - на дату услуги полис действует и закреплён за этим ассистансом;
  - сумма не превышает лимит и одобренную ГП, если та требовалась;
  - строка не встречается в другом счёте (дубль), в том числе у другого ассистанса;
  - цена соответствует прайсу пары «клиника + ассистанс».
- Куратор МИГ проверяет счёт: принять или отклонить строки с причиной. Ассистанс может оспорить отклонение. **Правило четырёх глаз:** счёт принимает куратор, оплачивает бухгалтер, и один человек не может сделать и то и другое.
- Строки принятого счёта становятся убытками МИГ (`Claim`, источник `assistance`) и попадают в убыточность клиента.
- Статусы счёта: `draft` → `submitted` → `in_review` → `partially_accepted` / `accepted` → `paid`.

### 5.6 Контроль качества
- Каждый месяц система случайно отбирает 5% решений ассистанса (ГП и принятые строки реестров) в очередь `doctor_expert` МИГ.
- МИГ ставит оценку «согласен» или «не согласен» с комментарием. Результаты попадают в KPI ассистанса. Решение по уже оплаченному делу выборка не меняет, но расхождения видны в карточке ассистанса.

### 5.7 Список застрахованных
- Когда HR добавляет или исключает сотрудника, изменение сразу видно ассистансу: в кабинете и через вебхук `insured.added` / `insured.excluded`.
- Ассистанс с API получает полный список своих застрахованных методом `GET /roster` (постранично, с `updatedSince`).

## 7. Изменения в портале МИГ

- **`/staff/assistance`** — список ассистансов: число застрахованных, KPI, счета к проверке, нарушения SLA.
- **`/staff/assistance/:id`** — карточка с вкладками:
  - Обзор и KPI;
  - Договор (модель и размер вознаграждения, полномочия);
  - Клиенты;
  - Пользователи;
  - Интеграция;
  - Счета;
  - Контроль качества;
  - Аудит.
- **`/staff/rebills`, `/staff/rebills/:id`** — проверка счетов ассистансов (куратор) и оплата (бухгалтер).
- **`/staff/guarantees`** показывает эскалации от ассистансов и ГП клиентов без ассистанса.
- **`/staff/qa`** — очередь контрольной выборки.
- В карточке клиента и полиса поле **«Ассистанс»** с историей. Андеррайтер меняет его с датой начала. В форме КП ассистанс выбирается при подготовке продления.
- На рабочем столе новые типы в очереди: «Эскалация ГП», «Счёт ассистанса», «SLA ассистанса нарушен», «Жалоба».
- В отчётах: убыточность и выплаты в разрезе ассистансов, стоимость обслуживания (вознаграждение ассистанса на застрахованного).

Кабинет клиники: в ГП показывается «Решение принимает: {ассистанс}», в реестре по каждой строке виден плательщик.

## 8. API интеграции для ассистансов

Используется тот же каркас, что CLINIC_SPEC §6: OAuth client credentials, области доступа, `Idempotency-Key`, `problem+json`, лимиты, журнал, вебхуки с HMAC. Обобщи его до `partnerType: 'clinic' | 'assistance'`: ключи, вебхуки и журналы принадлежат партнёру.

Методы для ассистанса (`/api/integration/v1/assistance/…`):

```
GET  /roster?updatedSince&cursor                → застрахованные ассистанса (ФИО, дата рождения, полис, программа, лимиты с остатками)
GET  /insured/{id}/limits
POST /cases                                     {insuredId, type, description}
PATCH /cases/{id}                               {status, resolution}
GET  /appointments?status
POST /appointments/{id}/confirm|reschedule|decline
GET  /guarantees?status=requested
POST /guarantees/{id}/decide                    {decision: 'approve'|'reject'|'escalate', amount?, validUntil?, reason}
GET  /registries?status
POST /registries/{id}/lines/{lineId}/decide     {decision: 'accept'|'reject', reason?}
POST /registries/{id}/payments                  {lineIds, paidAt, amount, paymentOrderNumber}
POST /rebills                                   {period, lineIds}
GET  /rebills/{id}
POST /rebills/{id}/lines/{lineId}/dispute       {comment}
```

Области доступа: `roster:read`, `cases:write`, `appointments:write`, `guarantees:decide`, `registries:review`, `payments:write`, `rebills:write`.

Вебхуки ассистансу (тонкие, без ПДн): `insured.added`, `insured.excluded`, `policy.assigned`, `policy.unassigned`, `appointment.requested`, `guarantee.requested`, `registry.received`, `rebill.reviewed`, `rebill.paid`, `qa.disagreement`.

Методы добавь в генерацию OpenAPI (CLINIC_SPEC §6.6) отдельным разделом.

**Симулятор системы ассистанса** (только демо-режим) на вкладке «Интеграция» у API-ассистанса выполняет настоящие вызовы API:
- «Синхронизировать список застрахованных»;
- «Решить все ГП в пределах полномочий»;
- «Принять реестр клиники»;
- «Отметить оплату клинике»;
- «Выставить счёт МИГ за месяц».

## 9. Изменения к CLINIC_SPEC

1. В CLINIC_SPEC §5 решения по ГП для застрахованных с ассистансом принимает ассистанс, а МИГ — только по эскалации и по клиентам без ассистанса.
2. В CLINIC_SPEC §4.5 и §5 проверка и оплата реестра идут по подреестрам плательщиков (§5.3). Оператор и бухгалтер МИГ обрабатывают только строки клиентов без ассистанса.
3. В CLINIC_SPEC §4.3 эскалация неотвеченных заявок идёт ассистансу застрахованного.
4. Прайс-лист клиники становится прайсом пары «клиника + плательщик» (§5.3).
5. Матрица прав CLINIC_SPEC §8 дополняется столбцами ролей ассистанса (§10).

## 13. Безопасность — дополнительно

1. Изоляция по ассистансу **на дату события**, а не только по текущему закреплению. Это проверяется тестами со сменой ассистанса у клиента.
2. Доступ бывшего ассистанса к старым делам только на чтение и только 12 месяцев.
3. Суммы вознаграждения и договоры одного ассистанса недоступны другим.
4. Правило четырёх глаз на счетах ассистансов (принял ≠ оплатил).
5. Проверка дублей строк между счетами разных ассистансов и разных месяцев.
6. Лимиты меняются атомарно: резерв ГП и списание по строке в моке выполняются одной операцией. Бэкенд потом повторит это транзакцией в базе.
7. Запиши в README для бэкенда: ассистанс является обработчиком персональных данных по поручению МИГ. Его система, если он подключён по API, тоже должна хранить данные в Узбекистане. Это требование к договору, а не к коду.

## 14. Тесты

**Юнит:**
- все новые ячейки матрицы;
- `requireAssistanceScope()` на дату события;
- разнос строк реестра по плательщикам;
- расчёт вознаграждения по трём моделям;
- все автоматические проверки счёта;
- резерв и списание лимита;
- выборка контроля качества (детерминированная в тестах).

**E2E:**
1. Звонок: оператор ассистанса находит демо-застрахованного, создаёт обращение и запись. Застрахованный видит запись, клиника её подтверждает.
2. ГП в пределах полномочий решает врач ассистанса. ГП выше полномочий эскалируется, врач-эксперт МИГ одобряет, клиника видит решение.
3. Лимит: после одобрения ГП приложение показывает уменьшенный остаток. После принятия строки реестра остаток окончательный, а резерв снят.
4. Реестр клиники со строками двух плательщиков разносится автоматически: ассистанс видит только свои строки, МИГ — только строки клиентов без ассистанса.
5. Счёт: ассистанс оплачивает строки клинике, формирует счёт МИГ, куратор отклоняет строку с флагом, ассистанс оспаривает, куратор принимает, бухгалтер оплачивает. Куратор оплатить не может.
6. Изоляция:
   - оператор «[Ассистанс 2]» не находит застрахованного «[Ассистанс 1]» (пустой поиск, прямой id → 404);
   - после смены ассистанса у клиента новое обращение идёт новому, а старый видит прежние дела только на чтение.
7. Приложение: карточка «Ваш ассистанс 24/7» показывает правильный ассистанс, а чат уходит в его портал.
8. Симулятор API-ассистанса: синхронизация списка застрахованных и выставление счёта через API видны в портале МИГ.
