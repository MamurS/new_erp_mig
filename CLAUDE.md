# MIG ДМС — фронтенд-прототип

## Что это

Полностью кликабельный фронтенд системы ДМС (добровольного медицинского страхования) Mosaic Insurance Group. В нём три части:

- **Портал сотрудников МИГ** (`/staff`) — ERP/CRM: клиенты, полисы, застрахованные, убытки, записи, клиники, отчёты, аудит.
- **Кабинет HR компании-клиента** (`/hr`) — сотрудники, документы, счета, агрегированная статистика.
- **Приложение застрахованного** (`/app`) — мобильный веб: полис, лимиты, запись к врачу, возмещение по фото чека, чат.

Бэкенда пока нет. Все запросы идут в мок-API на MSW с вымышленными данными. Мок ведёт себя как настоящий бэкенд: сам определяет пользователя по сессии, проверяет права, маскирует данные и пишет аудит. Позже мок заменяется на FastAPI + Postgres (Supabase), и экраны при этом не переписываются.

- Полное ТЗ: `docs/SPEC.md`. Это главный документ, выполняй его целиком.
- Принятые по ходу решения: `docs/DECISIONS.md` (создай сам, одна строка на решение).

## Режим работы

- Собери весь проект за один непрерывный проход по чеклисту `docs/SPEC.md` §13. Не останавливайся ради подтверждений и не задавай вопросов.
- Если в ТЗ чего-то нет, выбери самый разумный вариант, запиши его одной строкой в `docs/DECISIONS.md` и продолжай.
- Отмечай пункты чеклиста как `[x]` прямо в `docs/SPEC.md` по мере выполнения. Если сессия прервётся, работа продолжится с первого незакрытого пункта.
- Работа закончена, только когда все проверки из раздела «Проверки» проходят без ошибок. Падающие тесты не отключай и не удаляй, а чини код.
- В конце выведи отчёт по форме из `docs/SPEC.md` §14.

## Архитектура

- Экраны ничего не знают про моки. Данные идут только через `src/shared/api/client.ts` (обёртка над fetch к `/api/...`) и хуки TanStack Query в `src/shared/api/queries/`.
- Моки включаются флагом `VITE_USE_MOCKS=true`: MSW стартует до первого рендера. Вся «серверная» логика живёт в `src/mocks/`: БД в памяти, seed, обработчики, проверка прав, маскирование, аудит.
- Типы в `src/shared/types/` — это контракт API. Бэкенд потом повторит их один в один.
- Права определяются в одном месте: `src/shared/auth/permissions.ts` (матрица из SPEC §4). Её используют и UI (guards, скрытие кнопок), и мок-сервер (403/404).
- Структура по фичам: `src/features/{auth,staff,hr,insured}/`, общее лежит в `src/shared/`.
- Никакой бизнес-логики в компонентах UI. Форматирование и расчёты выноси в `src/shared/lib/`.

## Безопасность — обязательные правила

Нарушение любого пункта считается багом. Подробности в SPEC §9.

1. Никаких секретов в коде и в переменных `VITE_*`: всё с префиксом `VITE_` попадает в браузер. Файлы `.env*` добавлены в `.gitignore`, кроме `.env.example`.
2. Запрещено: `dangerouslySetInnerHTML`, `innerHTML`/`outerHTML`/`insertAdjacentHTML`, `eval`, `new Function`, строковый `setTimeout`, `document.write`, ссылки `javascript:`. Любой URL из данных проходит через `safeUrl()`.
3. Никаких токенов и сессий в `localStorage`. Сессия хранится в памяти и `sessionStorage`, доступ к ним только через `src/shared/auth/session.ts`. В `localStorage` через `src/shared/lib/storage.ts` можно класть только UI-настройки: язык и свёрнутую навигацию.
4. Персональные данные (ПИНФЛ, телефон, email, дата рождения, номер карты) приходят из API уже замаскированными. Полное значение выдаётся только отдельным вызовом `reveal` с указанием причины, показывается 30 секунд, не кладётся в кэш запросов и пишется в аудит.
5. Никаких ПДн и медданных в URL, `document.title`, `console`, текстах ошибок и именах файлов выгрузок. Логирование идёт только через `src/shared/lib/logger.ts`, который вычищает ПДн.
6. ID сущностей — UUID v4. Застрахованный получает свои данные только через `/api/me/...`, а не по id. Чужой id возвращает 404.
7. Проверки прав во фронте нужны только для удобства. Мок-сервер обязан проверять права сам на каждом запросе.
8. У каждой формы есть zod-схема с ограничениями длины, `trim` и нормализацией. Те же схемы мок-сервер применяет к телу запроса.
9. Загрузка файлов: белый список MIME-типов, лимит размера и количества, перекодирование изображений через canvas, чтобы удалить EXIF и геолокацию.
10. Заголовки безопасности и CSP лежат в `public/_headers` (SPEC §9.3). В `index.html` нет inline-скриптов и inline-обработчиков.
11. Демо-баннер, переключатель ролей и подсказки с демо-кодами существуют только при `VITE_DEMO_MODE=true`. В сборке без флага их кода нет вообще (проверяется тестом).
12. При выгрузке CSV ячейки, начинающиеся с `= + - @ Tab CR`, экранируются, чтобы не сработала CSV-инъекция.

## Дизайн

Два визуальных режима (SPEC §7), и новых цветов не придумывай:

- `staff` — плотный и строгий, для сотрудников МИГ.
- `client` — мягкий и дружелюбный, для HR-кабинета и приложения.

Токены задаются CSS-переменными в `src/styles/tokens.css`, режим включается атрибутом `data-theme` на корне раздела.
