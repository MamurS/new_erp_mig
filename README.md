# MIG ДМС — фронтенд-прототип

Кликабельный фронтенд системы добровольного медицинского страхования Mosaic Insurance Group:

- **Портал сотрудников** (`/staff`) — рабочий стол с очередью, клиенты, полисы, застрахованные, убытки, записи к врачу, клиники, запросы на изменение лимитов, отчёты, журнал аудита, пользователи и роли. Командная палитра ⌘K / Ctrl+K.
- **Кабинет HR компании-клиента** (`/hr`) — сотрудники, добавление и импорт из CSV, счета и документы, агрегированная статистика (k ≥ 10), помощь.
- **Приложение застрахованного** (`/app`) — мобильный веб на русском и узбекском: полис и лимиты, QR-карточка, запись к врачу, возмещение по фото чека, чат, профиль.

Бэкенда пока нет: все запросы уходят в мок-API на MSW, который ведёт себя как сервер — определяет пользователя по сессии, проверяет права, маскирует ПДн и пишет аудит. Данные вымышленные.

Полное ТЗ — [`docs/SPEC.md`](docs/SPEC.md), принятые решения — [`docs/DECISIONS.md`](docs/DECISIONS.md).

## Запуск

Нужен Node 20+.

```bash
npm ci
npm run dev        # http://localhost:5173, моки и демо-режим включены
```

Команды:

| Команда | Что делает |
|---|---|
| `npm run dev` | локальный сервер, моки включены |
| `npm run build` | production-сборка в `dist/` |
| `npm run preview` | раздача `dist/` с заголовками безопасности из `public/_headers` |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run lint` | ESLint, 0 предупреждений |
| `npm run test` | Vitest: юнит- и компонентные тесты |
| `npm run test:e2e` | Playwright (Chromium), собирает `dist-e2e` с `VITE_SEED_XSS=true` |
| `npm run check` | всё выше подряд + `npm audit --audit-level=high` |

Переменные окружения (см. `.env.example`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `VITE_USE_MOCKS` | `true` | включает мок-API (MSW стартует до первого рендера) |
| `VITE_DEMO_MODE` | `true` в `dev`, иначе выключен | демо-баннер, «Войти как…», сброс данных, имитация сбоев, подсказки на входе |
| `VITE_API_BASE_URL` | `/api` | адрес API |
| `VITE_SEED_XSS` | — | добавляет в seed XSS-строки (используют e2e) |

В `VITE_*` нельзя класть секреты: они попадают в браузер.

## Как устроено

```
src/
  app/            роутер, корневой layout, 403/404, ErrorBoundary, офлайн-баннер
  features/
    auth/         вход сотрудников и HR, второй фактор
    staff/        портал сотрудников (страницы, компоненты, навигация, палитра ⌘K)
    hr/           кабинет HR
    insured/      приложение застрахованного
  shared/
    api/          client.ts (fetch + Bearer + ApiError + zod), схемы ответов, хуки TanStack Query
    auth/         permissions.ts (матрица прав), session.ts, guards, тайм-аут, выход
    domain/       бизнес-правила (переходы убытков, медэкспертиза, «четыре глаза»), подписи
    lib/          format, safeUrl, redirect, csv, logger, storage, image, masks, hooks
    schemas/      zod-схемы форм (их же применяет мок к телу запроса)
    types/        контракт API: index.ts (SPEC §5) и dto.ts
    ui/           компоненты в стиле shadcn/ui
  mocks/          «сервер»: БД в памяти, seed, обработчики, маскирование, аудит
  demo/           демо-модуль (подключается динамически только в демо-режиме)
  i18n/           ru.ts / uz.ts для приложения застрахованного
  styles/         токены двух тем (staff, client), базовые стили
e2e/              Playwright-сценарии SPEC §11
```

### Моки

- `src/mocks/seed.ts` — детерминированный seed (mulberry32, зерно `20260929`): 40 компаний, ~1 500 застрахованных, 30 клиник, 600+ убытков, 300+ записей, 12 сотрудников, 500 записей аудита, 8 запросов на лимиты. Даты считаются от сегодняшнего дня.
- `src/mocks/handlers/*` — обработчики всех эндпоинтов. Каждый начинается с `requireSession()` и `requirePermission()`; без сессии — 401, без права — 403, чужой ресурс — 404. Тело запроса проверяется той же zod-схемой, что и форма (ошибка — 422 с `fields`).
- Роль берётся только из серверной сессии; заголовки вроде `X-Role` игнорируются.
- Ответы с ПДн всегда маскированы; полное значение — только через `POST /api/insured/:id/reveal` с причиной (пишется в аудит).
- Задержка ответа 150–450 мс; состояние мока переживает перезагрузку вкладки.

## Коммерческое предложение (КП)

Андеррайтер нажимает «Подготовить КП» (очередь на рабочем столе, боковая панель и карточка клиента, карточка полиса) и попадает на экран `/staff/clients/:clientId/kp/new`: слева параметры, справа предпросмотр 17 страниц: обложка брошюры GOLD, страница-письмо с данными клиента, затем страницы брошюры со 2-й по 16-ю. Сохранённое КП лежит во вкладке «Документы» клиента, после отправки его видит HR компании в «Счетах и документах». ТЗ — [`docs/KP_SPEC.md`](docs/KP_SPEC.md).

- Эталон брошюры — `vendor/gold-brochure-generator/` (не редактировать). После обновления брошюры: `node scripts/import-gold-templates.mjs`, затем осознанно обновить хэш в `src/features/kp/templates/gold.test.ts`.
- Шрифты и картинки брошюры раздаются из `public/kp/gold/`.
- `src/features/kp/render.ts` — чистая функция `renderKp(params, ctx)` без DOM; все значения экранируются.
- КП показывается только в `KpFrame` — `<iframe sandbox>` без `allow-scripts`. «Скачать PDF» открывает окно печати фрейма (выбрать «Сохранить как PDF»).
- Мок хранит параметры и версию шаблона, а не PDF: документ воспроизводится из них.

### Как это будет работать с бэкендом

- `POST /api/clients/:id/kp` на сервере рендерит те же шаблоны в том же порядке страниц — обложка брошюры, страница-письмо, страницы брошюры 2–16 (как `renderKp` в `render.ts`, с той же подстановкой и тем же экранированием) — через headless Chromium — Playwright внутри FastAPI или отдельный контейнер Gotenberg на своём сервере. Получается векторный PDF; он сохраняется в файловое хранилище вместе с SHA-256 файла, и документ получает `fileUrl`.
- Фронт скачивает готовый файл по `GET /api/kp/:id/file`, а печать через iframe остаётся только для предпросмотра.
- Всё происходит на серверах в Узбекистане. Внешние сервисы рендеринга не используются.

## Подключение настоящего API

1. Реализовать эндпоинты из `src/mocks/handlers/*` на FastAPI с теми же путями и типами из `src/shared/types/` (список — в разделе «Что нужно от бэкенда» отчёта и в `docs/DECISIONS.md`).
2. Собрать фронт с `VITE_USE_MOCKS=false` и `VITE_API_BASE_URL=https://<api-host>/api` (и добавить этот хост в `connect-src` в `public/_headers`).
3. Экраны не меняются: они ходят только через `src/shared/api/client.ts` и хуки из `src/shared/api/queries/`.

## Безопасность

Коротко (подробно — SPEC §9 и CLAUDE.md): строгая CSP и заголовки в `public/_headers`, нет inline-скриптов; ESLint запрещает `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `localStorage` вне `storage.ts`, `sessionStorage` вне `session.ts`, `console` вне `logger.ts`; все URL из данных проходят через `safeUrl()`; сессия только в памяти и `sessionStorage`; выход синхронизируется между вкладками; тайм-аут неактивности 15/30 минут; CSV экранируется от формул; фото чеков перекодируются через canvas (EXIF и GPS удаляются); демо-кода нет в сборке без `VITE_DEMO_MODE` (проверяется тестом).

## Деплой (Cloudflare Pages)

Делает человек:

1. Cloudflare → Workers & Pages → Create → Pages → подключить репозиторий GitHub.
2. Build command `npm run build`, output `dist`, Node 20.
3. Переменные окружения: `VITE_USE_MOCKS=true`, `VITE_DEMO_MODE=true`.
4. Закрыть доступ: Cloudflare Zero Trust → Access → Applications → Self-hosted → домен проекта `*.pages.dev`. Политика: только перечисленные email коллег (вход по одноразовому коду на почту).
5. После деплоя проверить заголовки на securityheaders.com.

`public/_headers` и `public/robots.txt` уже лежат в репозитории. SPA-фолбэк задан в `wrangler.jsonc` (`not_found_handling: single-page-application`); для Cloudflare Pages вместо этого нужен `public/_redirects` с правилом `/*  /index.html  200` — Workers такое правило отклоняют как бесконечный цикл.

Для Cloudflare Workers Builds в корне лежит `wrangler.jsonc` (статические ассеты из `dist`, SPA-режим). Переменные `VITE_USE_MOCKS=true` и `VITE_DEMO_MODE=true` задаются в настройках сборки Worker'а.
